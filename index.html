How kube-scheduler picks a node

  1. Phase 1: filtering
  2. Filtering outcomes at a glance
  3. Phase 2: scoring plugins
  4. Score × weight
  5. When affinity loses to ImageLocality
  6. A worked example

Every pod goes through the same decision. The scheduler first chooses a node in two phases: it filters out the nodes that can't run the pod, then scores the ones that can. Then it binds the pod to the winner, which is a separate final step that just records the choice. This deep dive follows that decision step by step.

Phase 1: filtering

Scenario. A developer deploys a new service, but the pod never starts. It sits in Pending, and kubectl describe pod shows 0/12 nodes are available. The developer is confused: the monitoring dashboard shows every node at around 35% CPU, so there seems to be plenty of room. Why won't Kubernetes place the pod, and how do you find out which rule is blocking it?

What the picture shows. The scheduler chooses a node in two phases, filtering then scoring, and then binds the pod to the chosen node. This picture is the first phase: find every node that is physically and logically able to host the pod. Each node runs through a series of checks (filter plugins, formerly called predicates), and failing even one check removes it.

the "brain" that decides where every new pod lives.
2Phase 1: Filtering (the "predicate" phase)
the goal is simple, keep only the nodes that can run the pod.
3Insufficient resources (the fit check)
this is the answer to the scenario. The scheduler counts what pods request, not what they actually use, while the dashboard shows real usage. So a node can be 35% busy and still be fully booked on paper. How the check works: the scheduler takes the node's allocatable CPU and memory (its capacity minus what's reserved for the kubelet, the operating system and the eviction buffer), subtracts the requests of the pods already there, and checks that what's left is at least the new pod's request. This is a yes/no feasibility check, not bin-packing. "Not bin-packing" means this step only checks whether the pod fits on a node; it doesn't decide which of the fitting nodes is best.
  • Worked example, one node: 4 CPU cores of capacity, about 3.9 allocatable. Three pods already run there: pod A requests 1.5 cores and uses 0.3, pod B requests 1.5 and uses 0.5, pod C requests 0.8 and uses 0.6.
  • Reserved vs. used: together they request 3.8 cores but use only 1.4, about 35% of the node. The dashboard shows the 35%.
  • The new pod: it requests 0.5 cores. The scheduler computes 3.9 − 3.8 = 0.1 cores left. That's less than 0.5, so the node fails the filter, even though about 2.5 cores are sitting idle.
  • At a glance: the same numbers side by side.

  • Why it works this way: a request is a promise. If pod A suddenly needs its full 1.5 cores, it must be able to get them, so the scheduler can't hand that reserved space to another pod just because it's idle right now.
  • The usual fix: right-size the requests to match real usage (tools like Goldilocks or the Vertical Pod Autoscaler help) instead of adding nodes.
  • Which part of the scheduler runs the fit check: a plugin called NodeResourcesFit, one of the scheduler's internal modules (filtering and scoring are made of many of them). It's built into kube-scheduler and on by default, so there's nothing to install or enable.
  • What you write vs. what's built in: your pod only supplies the requests; you never name the plugin. The plugin's own settings live in the scheduler's configuration. The YAML just below this list shows both: first your pod, then the scheduler's configuration with its default values.
  • You normally don't write that configuration: the KubeSchedulerConfiguration in the second half of the YAML is only there to make the hidden defaults visible; they already apply without it. You'd write one only to change them, and on managed control planes like EKS you can't change the default scheduler at all.
  • Passing is a plain yes: a nearly full node with just enough room and an almost empty node pass equally. Choosing between them happens later, in scoring, where the default (LeastAllocated) spreads pods and bin-packing (MostAllocated) must be turned on deliberately (see Phase 2: scoring plugins).

Note: when would you actually write a KubeSchedulerConfiguration?

Only when you want to change the scheduler's built-in settings. Two things to know first:

  • It isn't a Kubernetes object. It has apiVersion and kind, but you don't kubectl apply it (the API would reject it). It's a config file the kube-scheduler program reads at startup, passed with --config.
  • Where you can use it depends on who runs the scheduler:
    • Self-managed clusters (for example kubeadm): point the scheduler's static pod at your own file, for example to switch to MostAllocated bin-packing or change plugin weights.
    • Managed clusters (EKS, GKE, AKS): the provider runs the default scheduler, so you can't change its file. Instead, run a second scheduler as a normal Deployment with its own KubeSchedulerConfiguration from a ConfigMap, and point specific pods at it with schedulerName. Volcano and KAI work the same way, as replacement schedulers. A complete, ready-to-apply example is in Appendix A: Running a second scheduler. For the full list of built-in plugins, and what changes once a second scheduler shares the cluster, see Built-in plugins, and what a second scheduler changes in the Kubernetes Multi-Scheduler deep dive.

6Affinity and anti-affinity violations

Note: can one pod use taints, tolerations, affinity and anti-affinity together? Does the order matter?

Yes, one pod can use all of them at once, and no, the order doesn't matter.

  • They're separate fields: tolerations, nodeSelector, affinity.nodeAffinity, affinity.podAffinity, affinity.podAntiAffinity and topologySpreadConstraints are all named fields of the pod spec, so you can write them in any order.
  • Every hard rule must pass: the scheduler runs its filters in its own fixed order, and a node survives only if it passes all of them. That's a logical AND, which gives the same answer in any order.

  • Inside node affinity: several nodeSelectorTerms are combined with OR (matching any one term is enough); several matchExpressions inside one term are combined with AND (the node must match all of them).

    apiVersion: v1kind: Podmetadata:  name: report-builderspec:  affinity:    nodeAffinity:      requiredDuringSchedulingIgnoredDuringExecution:        nodeSelectorTerms:          # term 1 OR term 2        - matchExpressions:         # term 1: zone a AND an SSD          - key: topology.kubernetes.io/zone            operator: In            values: ["us-east-1a"]          - key: disktype            operator: In            values: ["ssd"]        - matchExpressions:         # term 2: OR any m6i node          - key: node.kubernetes.io/instance-type            operator: In            values: ["m6i.2xlarge", "m6i.4xlarge"]  containers:  - name: builder    image: my-company/report-builder:3.1

  • Preferred (soft) rules are wishes with points: each node earns the weight of every preferred rule it matches, and the node with the most points is favoured. The order you list the rules in doesn't make one more important. In the example below, a node in zone a earns 90 points, an SSD node earns 10, a node with both earns 100 and a node with neither earns 0, and swapping the two rules in the YAML gives exactly the same result. (Those points then become NodeAffinity's score, which is added to the other plugins' scores.)

    apiVersion: v1kind: Podmetadata:  name: report-builderspec:  affinity:    nodeAffinity:      preferredDuringSchedulingIgnoredDuringExecution:      - weight: 10                  # listed first, but counts little        preference:          matchExpressions:          - key: disktype            operator: In            values: ["ssd"]      - weight: 90                  # listed second, but counts most        preference:          matchExpressions:          - key: topology.kubernetes.io/zone            operator: In            values: ["us-east-1a"]  containers:  - name: builder    image: my-company/report-builder:3.1

    What if these were required instead? The story changes. Required rules are pass/fail filters, not scores: there's no weight or preference, a node either passes or is removed, and if no node passes the pod stays Pending instead of running somewhere less ideal.

    One term or two: AND vs. OR. A required rule lists its conditions under nodeSelectorTerms, and how you group them decides the logic. Conditions inside the same term must all match (AND); separate terms are alternatives, and matching any one is enough (OR). So you have to decide whether you mean "SSD and zone a" or "SSD or zone a":

    # Both conditions in ONE term → AND: an SSD node that is also in us-east-1aapiVersion: v1kind: Podmetadata:  name: report-builderspec:  affinity:    nodeAffinity:      requiredDuringSchedulingIgnoredDuringExecution:   # no weights allowed        nodeSelectorTerms:        - matchExpressions:          # one term, two conditions = AND          - key: disktype            operator: In            values: ["ssd"]          - key: topology.kubernetes.io/zone            operator: In            values: ["us-east-1a"]  containers:  - name: builder    image: my-company/report-builder:3.1---# Each condition in its OWN term → OR: an SSD node anywhere, or any node in us-east-1aapiVersion: v1kind: Podmetadata:  name: report-builderspec:  affinity:    nodeAffinity:      requiredDuringSchedulingIgnoredDuringExecution:        nodeSelectorTerms:        - matchExpressions:          # term 1          - key: disktype            operator: In            values: ["ssd"]        - matchExpressions:          # term 2 (OR)          - key: topology.kubernetes.io/zone            operator: In            values: ["us-east-1a"]  containers:  - name: builder    image: my-company/report-builder:3.1

    Order still doesn't matter in any of them, and IgnoredDuringExecution still means a running pod isn't moved if labels change later. A common pattern is to mix them: a required rule for what's non-negotiable (say, the zone where the data lives) plus a preferred rule for nice-to-haves (say, SSD with weight 50).

  • Why you usually want them together: a toleration only allows a pod onto a tainted node; it doesn't send it there, so the pod could still land on any untainted node. Dedicated nodes therefore use three pieces: a taint on the nodes (keeps other pods off), a toleration on the pod (lets it in), and node affinity or nodeSelector on the pod (sends it there). Pod anti-affinity is often added to spread replicas across those nodes.

The long affinity names, decoded. Each name has two halves: when scheduling and while running.

  • requiredDuringScheduling…: a hard rule, checked in the filter phase. No matching node means the pod stays Pending.
  • preferredDuringScheduling…: a soft rule, checked in the scoring phase with a weight from 1 to 100. The pod still runs if nothing matches.
  • …IgnoredDuringExecution: the rule is checked only when the pod is placed. If a node's labels, or the other pods around it, change later, the running pod is not moved.
  • requiredDuringSchedulingRequiredDuringExecution: described in the Kubernetes docs as a possible future variant that would evict running pods when the rule stops matching. It has never been implemented, so affinity rules are never re-checked once a pod is running.

  • Both versions (required… and preferred…) exist for all three kinds of affinity: ("both" in the table means you can write either version)

    What topologyKey does. "Run near" or "run away from" another pod raises a question: how close is near? On the same node? In the same zone? topologyKey answers it. You give it the name of a node label, and the scheduler treats two nodes as the same place when they have the same value for that label.

    Example: a pod with anti-affinity "stay away from app: api pods" is being placed, and an api pod already runs on node A.

    Nodehostname labelzone labeltopologyKey: hostnametopologyKey: zone
    A (already runs an api pod)node-aus-east-1atogethertogether
    Bnode-bus-east-1aapart: allowedtogether: avoided
    Cnode-cus-east-1bapart: allowedapart: allowed

    With topologyKey: kubernetes.io/hostname: every node has its own value, so only node A counts as "the same place". Node B is fine, even though it's in the same zone.

    With topologyKey: topology.kubernetes.io/zone: nodes A and B both say us-east-1a, so they count as the same place. The pod avoids both and goes to node C in another zone.

    So the same anti-affinity rule spreads pods across nodes or across zones, depending only on which label you name.

  • If you need "move the pod when things change", use a different tool. Affinity can't do it, but two other features can:

    • Taints with effect: NoExecute: taints are a separate feature, set on the node. Their effect decides how strict they are: NoSchedule (hard rule for new pods), PreferNoSchedule (soft, scoring only) and NoExecute, which also evicts pods that are already running there without a matching toleration (tolerationSeconds lets a pod stay for a set time first). So the taint's NoExecute effect behaves like the "during execution" half that affinity never got.

      # The NODE carries the taints (here one of each effect, to compare them)apiVersion: v1kind: Nodemetadata:  name: gpu-node-1spec:  taints:  - key: dedicated    value: gpu    effect: NoSchedule           # new pods without a toleration: not scheduled here  - key: spot    value: "true"    effect: PreferNoSchedule     # new pods: avoided if possible (scoring only)  - key: maintenance    value: "true"    effect: NoExecute            # running pods without a toleration: evicted NOW---# The POD tolerates all three; for NoExecute it may stay 10 minutes, then is evictedapiVersion: v1kind: Podmetadata:  name: inferencespec:  tolerations:  - key: dedicated    operator: Equal    value: gpu    effect: NoSchedule  - key: spot    operator: Exists    effect: PreferNoSchedule  - key: maintenance    operator: Exists    effect: NoExecute    tolerationSeconds: 600       # stay up to 10 min after the taint appears, then leave  containers:  - name: server    image: vllm/vllm-openai:latest

      Add the NoExecute taint to a running node with kubectl taint nodes gpu-node-1 maintenance=true:NoExecute: pods without that toleration are evicted at once, and this pod is evicted after 600 seconds. Without tolerationSeconds, a pod with the toleration would stay forever.

      Note: doesn't that defeat NoExecute? Yes, if the pod's author wants it to. A toleration is an opt-out that whoever writes the pod controls: a toleration for maintenance with no tolerationSeconds means this taint never evicts that pod. Worse, a toleration with no key and operator: Exists matches every taint:

      tolerations:- operator: Exists      # no key, no effect: tolerates ALL taints, forever

      This is by design: taints and tolerations are a placement tool, not a security tool, and some pods legitimately must stay put (node agents run as DaemonSets, such as the CNI, log shippers and the GPU device plugin, get indefinite tolerations from Kubernetes itself). Why does this example have two tolerations? tolerations is a list, and each entry tolerates one kind of taint. A pod can tolerate as many as it needs; here the two entries do different jobs.

  • Entry 1, our own GPU taint (dedicated=gpu, NoSchedule): it matches the taint we put on the GPU nodes, so it decides where the pod may go. operator: Equal means the key and the value must both match.
  • Entry 2, a built-in taint (node.kubernetes.io/unreachable, NoExecute): nobody adds this one by hand. Kubernetes adds it automatically when a node stops talking to the control plane (a crash, a lost network). A NoExecute taint doesn't only block new pods; it evicts pods already running there. operator: Exists matches any taint with that key, whatever its value.
  • What tolerationSeconds: 60 changes: Kubernetes already gives every pod this toleration automatically, with a default of 300 seconds. Writing it yourself only changes the timing: the pod stays on an unreachable node for 60 seconds, then is evicted and recreated on a healthy node. For a GPU inference service, 5 minutes on a dead node is a long outage. The trade-off is that a short network blip could move the pod unnecessarily.
  • In short: entry 1 controls where the pod may go; entry 2 controls how quickly it leaves when its node fails.
7Topology spread constraints (keep replicas balanced)
A topologySpreadConstraints rule spreads a group of pods evenly across places, such as zones or nodes. It isn't a box in the picture, but with whenUnsatisfiable: DoNotSchedule it's another filter: a node is removed if placing the pod there would make the busiest place exceed the emptiest by more than maxSkew.
  • What counts as a "place": the topologyKey, the same field used in pod affinity. topology.kubernetes.io/zone means zones, kubernetes.io/hostname means nodes.
  • Hard or soft: DoNotSchedule filters nodes out; ScheduleAnyway only lowers their score.
  • How it differs from pod anti-affinity: anti-affinity says "not where a pod like me already runs", so a hard rule allows only one per place: 6 replicas in 3 zones means 3 stay Pending. A spread constraint allows several per place as long as they stay balanced, so all 6 run, 2 per zone.
  • When to use which: anti-affinity for "never two on one node" (say, one database replica per node); spread constraints for "balance across zones" (most web services). Even without either, the scheduler applies a soft default spread across nodes and zones.
# 6 replicas spread evenly across 3 zones: 2 per zone.apiVersion: apps/v1kind: Deploymentmetadata:  name: webspec:  replicas: 6  selector:    matchLabels: {app: web}  template:    metadata:      labels: {app: web}    spec:      topologySpreadConstraints:      - maxSkew: 1                                # zones may differ by at most 1 pod        topologyKey: topology.kubernetes.io/zone  # a "place" is a zone        whenUnsatisfiable: DoNotSchedule          # hard rule; ScheduleAnyway = soft        labelSelector:          matchLabels: {app: web}                 # which pods to count      containers:      - name: web        image: nginx:1.27

Note: using pod anti-affinity and topology spread together

A common case is a service that must survive both a node failure and a zone outage, say 6 replicas of an API. Each rule covers one level:

  • Pod anti-affinity (required, per node): never two replicas on the same node, so losing one node takes down at most one replica.
  • Topology spread (per zone): replicas stay balanced across zones, so losing a zone takes down about a third of them, not half.

How they work together: both are filters, and a node must pass every filter, so the scheduler keeps only nodes that have no api replica yet and sit in a zone that won't get too far ahead of the others. With 3 zones of 3 nodes each, the result is 2 replicas per zone, each on its own node.

Where they can collide: say zone c has only one node. Anti-affinity lets zone c hold just one replica. The spread rule then caps the other zones at 2 each (at most 1 more than zone c), so only 5 replicas can run and the 6th stays Pending, even though zones a and b have empty nodes. The fixes are to add a node to zone c, set whenUnsatisfiable: ScheduleAnyway so the zone spread becomes a preference, or make the anti-affinity preferred.

Could topology spread do both jobs? Yes: list two constraints, one with topologyKey: kubernetes.io/hostname and one with the zone key, each maxSkew: 1. The difference is that a per-node spread allows a second replica on a node once every node has one, while required anti-affinity never does.

8Port conflicts
if the pod asks for a hostPort (say port 80 on the EC2 instance) and another pod on that node already uses it, the node is out. Two tenants can't share one mailbox.

  • Filtering also runs one pod at a time: a distributed job's workers are judged separately, which is the root of the gang problem. Setting parallelism doesn't fix this; it only creates the pods together. "All 8 or none" needs something that knows the pods belong together:

Filtering outcomes at a glance

Scenario. It's 3 a.m. and the on-call engineer has a pod stuck in Pending with a long event message. They need a one-glance reference that turns "which rule failed" into "what to change", without re-reading the scheduler docs.

What the picture shows. A cheat sheet for the filtering phase, in two parts.

1Summary table (top)
each constraint, what kind of rule it is, and what happens when a node fails it.
  • Resources (physical): node ignored for insufficient CPU or memory.
  • Taints (policy): node ignored unless the pod tolerates the taint.
  • Affinity (logical): node ignored because it violates a placement rule.
  • Selector (label-based): node ignored because a label doesn't match.
2The funnel (bottom)
the Kubernetes scheduler starts with a pending pod and all 100+ cluster nodes. They pour through five filters in turn: resource filter (CPU/memory over capacity), node selector filter (label mismatch), taint filter (no toleration), affinity/anti-affinity filter (placement violation) and port conflict filter (hostPort in use). Nodes rejected at each layer drop out to the sides.
3Feasible nodes
whatever reaches the bottom of the funnel is the candidate list handed to the scoring phase. If nothing reaches the bottom, the pod stays Pending.

Phase 2: scoring plugins

Scenario. Three nodes pass filtering, yet a team notices the scheduler keeps putting their pods on the same node, even though another node is nearly empty. One day it places a critical API pod on a node that is already 90% full and the API slows down. Why did the scheduler prefer that node?

What the picture shows. Once filtering has narrowed the list, the scoring phase (also called the ranking phase) picks the best of the capable nodes. Every remaining node runs through several priority functions, gets a score from each, and the highest total wins.

1LeastAllocated (the "spreader")
the default strategy of the NodeResourcesFit plugin. It compares requested CPU and memory to capacity and gives emptier nodes higher scores, which spreads pods out and helps availability.
2BalancedResourceAllocation (the "balancer")
keeps CPU and memory use even on a node. A node with lots of CPU but almost no free RAM scores lower for a memory-heavy pod, so nodes don't become lopsided.
3ImageLocality (the "speedster")
scores nodes higher when the pod's images (say a 2 GB Java image) are already on local disk, so the pod skips the pull and starts faster. Bigger cached images count more. An image cached on only a few nodes is scaled down, so that one node with a popular image doesn't attract every new pod (the diagram's wording, "images on many nodes count less", has this backwards).
4Node / inter-pod affinity (the "socialite")
handles your preferred (soft) rules, such as "I'd like to run near my database". Nodes in the same rack or zone as the database score higher. It's the main score you steer from the pod spec (along with soft topology spread and PreferNoSchedule taints); the others are computed by Kubernetes.
5The default-weights trap
most of these plugins have the same small weight (1 or 2). In a large cluster that can lead to poor choices, and this is the scenario: the full node won because it already had the image cached, and the CPU contention showed up later.
Going deeper4 points
  • For GPU training I switch NodeResourcesFit to MostAllocated (bin-packing) and give nvidia.com/gpu a higher weight than CPU and memory.
  • Packing leaves whole nodes empty, so the autoscaler can remove them.
  • That matters when a GPU node costs tens of dollars an hour.
  • The catch is a bigger blast radius per node, so I offer it as a separate scheduler profile and let critical services keep spreading.

Score × weight

Scenario. In a design review, a new engineer asks how the scheduler turns "points" into a decision. "If one plugin likes node A and another likes node B, who wins?" You want to explain it on a whiteboard in two minutes.

What the picture shows. Every node's final score is built from two ingredients per plugin.

1The priority (score, or "grade")
a measure of quality, from 0 to 100. For example, "how empty is this node?" or "how many matching pods are already here?"
2The weight (the "multiplier")
a measure of importance, set per plugin.
3Adding it up
for each plugin, score × weight gives that plugin's points, and the node's points from all plugins are added together. The highest total wins.
4Example, LeastAllocated
a node with 10 cores and 2 cores requested is 80% free, so the plugin gives it a score of 80. With the default weight of 1, that's 80 × 1 = 80 points.
5Example, ImageLocality
the score grows with the total size of the images already cached, scaled down when only a few nodes have them. A big image (around 1 GB or more) cached scores close to 100; nothing cached, or only tiny images, scores 0.

When affinity loses to ImageLocality

Scenario. A team adds a preferred pod affinity so their API runs next to its cache. Most of the time it works, but some pods land on a different node: one that happens to have the API's image already pulled. The team asks why their affinity rule "lost" to an image cache.

What the picture shows. A worked conflict between two plugins, and two ways to fix it.

1The setup
ImageLocality prefers Node 1 (the image is cached there) and PodAffinity prefers Node 2 (the cache pod runs there). The scheduler scores each node from 0 to 100 per plugin, multiplies by the plugin's weight, and adds them up.
2Default weights
most plugins have weight 1, affinity and topology spread have 2, and taint toleration has 3.
3The conflict
ImageLocality (weight 1) gives Node 1 a score of 90, which is 90 points. InterPodAffinity (weight 2) gives Node 2 a weak 40, which is 80 points. Node 1 wins, even though you asked for affinity.
4Choice A, the hard rule (filtering)
change preferredDuringSchedulingIgnoredDuringExecution to requiredDuringSchedulingIgnoredDuringExecution. The rule moves from the scoring phase to the filtering phase, so Node 1 is never even considered.

5Choice B, scheduler configuration (advanced)
write a KubeSchedulerConfiguration profile with different weights, for example InterPodAffinity 100 and ImageLocality 1, so even a weak affinity match beats an image cache. On a managed control plane like EKS you can't change the default scheduler, so you run this as a second scheduler and point pods at it with schedulerName.

A worked example

Scenario. A developer writes a plain Deployment with no affinity rules at all and asks: "If I didn't set any weights, how does the scheduler decide anything?" They also tried adding a preferred rule without a weight, and kubectl apply rejected the YAML.

What the picture shows. The defaults that are always in play, even when your YAML says nothing.

1ImageLocality score
grows with the total size of the cached images, scaled down when only a few nodes have the image. A big image cached is close to 100; nothing cached is 0.
2Preferred rules need a weight
the YAML is fine, but the API server rejects a preferred affinity term without a weight (it must be 1–100), which is why the developer's apply failed.
3Built-in plugins still score every node
the plugins you never see in your YAML (like LeastAllocated or ImageLocality) run anyway, with these default weights:
  • NodeResourcesFit (LeastAllocated): 1
  • BalancedAllocation: 1
  • ImageLocality: 1
  • InterPodAffinity / NodeAffinity / TopologySpread: 2
  • TaintToleration: 3
4What this means
a simple pod still gets a reasoned placement, driven mostly by spreading, balance and image caching.

The weight field in your YAML

Scenario. A platform team reviews a Helm chart that has both required and preferred affinity blocks, with weights of 1 and 100 scattered around. Nobody is sure what the numbers actually do, or why the required block has no weight at all.

What the picture shows. How the weight field in your YAML plugs into the scheduler.

1Required (hard rule)
there is no weight field for requiredDuringSchedulingIgnoredDuringExecution, because "required" is a filter, not a score. A node either passes or is removed.
apiVersion: v1kind: Podmetadata:  name: report-builderspec:  affinity:    nodeAffinity:      requiredDuringSchedulingIgnoredDuringExecution:   # no weight: pass or fail        nodeSelectorTerms:        - matchExpressions:          - key: node.kubernetes.io/instance-type            operator: In            values: ["m5.2xlarge"]  containers:  - name: builder    image: my-company/report-builder:3.1
2Weight tunes scoring from the outside
whenever you see a weight in Kubernetes YAML, you are adjusting the scoring phase (never the filtering phase). You're telling the scheduler how much your rule matters compared to its built-in rules.
3How it's applied
for each node, the scheduler adds up the weights (1 to 100) of the preferred terms that node matches. Those sums are then normalized to 0–100 across the candidate nodes and multiplied by the plugin's own weight (2 for NodeAffinity and InterPodAffinity).
4Preferred + high weight (a strong suggestion)
weight 100 says "this term matters much more than my other preferred terms". Because of the normalization, a matched preference is worth at most about 200 points in total, so it usually wins but can still be outvoted by several other plugins together. If it must always win, make it required.
5Preferred + low weight (a nice-to-have)
weight 1 says "this would be nice, but it matters little compared with my other preferences". The weights only rank your preferred terms against each other.
apiVersion: v1kind: Podmetadata:  name: report-builderspec:  affinity:    nodeAffinity:      preferredDuringSchedulingIgnoredDuringExecution:      - weight: 100        # "I really want this"        preference:          matchExpressions:          - key: topology.kubernetes.io/zone            operator: In            values: ["us-east-1a"]      - weight: 1          # "nice to have"        preference:          matchExpressions:          - key: disktype            operator: In            values: ["ssd"]  containers:  - name: builder    image: my-company/report-builder:3.1

Scheduler score vs. OOM score

Scenario. A node runs out of memory and Kubernetes kills the team's most important pod. The team is surprised: "The scheduler gave that node a great score when it placed the pod, so why was our pod the one that died?" They are mixing up two different scores.

What the picture shows. Two "scores" that have nothing to do with each other.

1Don't mix them up
the scheduling score is about choosing a node for a pod. The QoS / OOM score is about choosing which pod to kill (covered in Memory: who gets killed).
2The scheduler's choice
at placement time the scheduler might see a node is 90% full and give it a low score, because it wants to spread the load. Once the pod is placed, that score is forgotten.
3The kubelet's reality
under memory pressure nobody looks at the scheduler's grade. The kubelet first picks pods that use more memory than they requested, then ranks them by priority, then by how far over their request they are. If the kernel's OOM killer fires first, it uses oom_score, which is memory usage plus a QoS-based oom_score_adj. So an "important" pod that uses more than it requested can still be the one that's killed.

The NVIDIA device plugin

Scenario. A team adds GPU nodes to their Kubernetes cluster and deploys a pod that requests nvidia.com/gpu: 1. The pod stays Pending with "Insufficient nvidia.com/gpu", even though the nodes clearly have GPUs installed. Kubernetes can't see them yet.

What the picture shows. How the NVIDIA device plugin turns physical GPUs into a count the scheduler can use, in numbered steps.

1AWS cloud and the GPU instance
an EC2 GPU instance (here a p4d.24xlarge with 8 A100s) gives the worker node its physical GPUs. The NVIDIA driver must already be on the node; the EKS-optimized accelerated AMIs include it.
2Control plane
the API server stores each node's status, including its GPU count; kube-scheduler checks that count the same way it checks CPU and memory.
3Step 1, the plugin registers
the device plugin runs on every GPU node as a DaemonSet. It finds the node's GPUs and registers with the kubelet over a local socket.
4Step 2, the kubelet reports the count
the kubelet adds nvidia.com/gpu: 8 to the node's capacity and allocatable. From then on GPUs are a countable resource. This is the missing piece in the scenario: without the plugin the node never reports any nvidia.com/gpu, so every node fails the fit check.
5Step 3, a pod asks for a GPU
the user or CI deploys a pod with nvidia.com/gpu: 1 under resources.limits.
apiVersion: v1kind: Podmetadata:  name: inferencespec:  containers:  - name: inference    image: vllm/vllm-openai:latest    resources:      limits:        nvidia.com/gpu: 1    # schedulable only after the device plugin registers GPUs
6Step 4, the scheduler subtracts and binds
a node fits if enough of its GPUs are still unreserved. The scheduler picks one and binds the pod to it.
7Step 5, the kubelet asks for a device
on that node, the kubelet asks the plugin to allocate one GPU. This happens on the node, not in the control plane.
8Step 6, the container gets the GPU
the plugin returns the device files and NVIDIA_VISIBLE_DEVICES, and the container starts with exactly that GPU. The scheduler never knew which GPU it would be, only that one was free.

  • The device plugin does four jobs:
    • it discovers the devices;
    • it advertises them as nvidia.com/gpu for scheduling;
    • it allocates them exclusively to containers;
    • it monitors their health, and an unhealthy GPU is taken out of the node's allocatable count.

How GPUs are advertised

Scenario. A platform team must make sure a new inference service lands only on GPUs with at least 40 GB of memory. Reading the docs, they find five things that all seem to "advertise GPUs" to Kubernetes: the device plugin, Node Feature Discovery, GPU Feature Discovery, Karpenter's labels and DRA. Which one does what, which ones do they actually need, and which one decides the GPU a pod gets?

What the picture shows. The three kinds of advertising side by side, and what each one lets the scheduler do.

1Labels (left column)
Node Feature Discovery, GPU Feature Discovery and the cloud/Karpenter labels write facts about the GPUs on the Node object. Pods match them with a nodeSelector or node affinity. They only help choose a node; nothing is reserved.
2Count (middle column)
the device plugin publishes nvidia.com/gpu: 8 in the node's capacity. Pods ask for a number, and the scheduler reserves against that count like CPU or memory.
3DRA (right column)
a DRA driver publishes every device as its own entry in a ResourceSlice, with its attributes. Pods bring a ResourceClaim that describes the device they need, and the scheduler matches it against individual devices.
4Bottom row, who picks the exact GPU
with labels, nobody; with a count, the device plugin picks one when the container starts; with DRA, the scheduler picks it and records it in the claim.
5The classic setup uses two of them together
labels to choose the node, plus the count to reserve a GPU on it. DRA replaces both with one mechanism.
Going deeper2 points
  • How a node tells Kubernetes about its GPUs is the main thing that sets DRA apart. There are two kinds of advertising, and before DRA they came from different tools:
    • Labels are information about the node ("this node has A100s with 80 GB"). They only help you choose a node, with a nodeSelector or node affinity.
    • A count is something the scheduler reserves ("this node has 8 GPUs, 3 are free"). The device plugin publishes it, and a pod asks for it with nvidia.com/gpu: 1. The scheduler only picks the node; the device plugin then hands over any free GPU on it.
    • DRA replaces both with one entry per device (a ResourceSlice) that carries that device's own attributes. The scheduler matches a claim against individual GPUs and records exactly which one the pod gets.

Steering pods to the right GPU

Scenario. Three teams share a cluster with T4, A10G, A100 and H100 nodes. The batch team wants exactly A100s, the inference team wants "at least 40 GB, Hopper if possible", and the web team's ordinary pods keep landing on expensive GPU nodes.

What the picture shows. Four GPU nodes with their labels and taint, and how three different pods are filtered and scored against them.

1The four GPU nodes
GPU Feature Discovery labels each one with its model, memory and family: a g4dn (T4, about 15 GB, Turing), a g5 (A10G, about 23 GB, Ampere), a p4de (A100, 80 GB, Ampere) and a p5 (H100, 80 GB, Hopper).
2The taint on every GPU node
nvidia.com/gpu=present:NoSchedule keeps away any pod without a matching toleration. This is the fix for the web team.
3Pod A, pin a model (Option 1)
a nodeSelector on nvidia.com/gpu.product set to the A100 model. Only the p4de passes.
4Pod B, a range plus a preference (Option 2)

it has no toleration, so every GPU node is filtered out and it runs on a regular CPU node.
6The GPU request
pods A and B still ask for nvidia.com/gpu: 1. The labels only choose the node; the count reserves a GPU on it.

Dynamic Resource Allocation

Scenario. The inference team wants "any NVIDIA GPU with at least 40 GB" without depending on node labels, and the training team needs each worker's GPU on the same PCIe root as its network card. Neither can be said with nvidia.com/gpu: 1.

What the picture shows. The DRA objects, who creates each one, and how a claim turns into one specific GPU in a container.

1DeviceClass (from the driver)
gpu.nvidia.com names a category of devices. The NVIDIA DRA driver creates it when installed (plus mig.nvidia.com for MIG slices).
2ResourceSlice (from the driver, per node)
lists every device on the node with its attributes, such as product name and architecture, and its capacity, such as memory.
3ResourceClaimTemplate (you write it)
describes the device a pod needs: a device class plus a CEL selector such as "memory at least 40Gi".
4ResourceClaim (Kubernetes creates it)
one claim per pod, made from the template when the pod is created and deleted with the pod.
5Pod
lists the claim under spec.resourceClaims and gives it to a container with resources.claims; there's no nvidia.com/gpu count.
6kube-scheduler (DynamicResources plugin)
filters out nodes with no free matching device, picks a node and a device, and writes that allocation into the claim.
7kubelet and the DRA driver's kubelet plugin
prepare exactly the allocated device on the node and expose it to the container.
Going deeper2 points
  • Dynamic Resource Allocation (stable since Kubernetes 1.34) lets a pod describe the device it needs, and the driver picks a match at scheduling time.

Note: what this example does, line by line

Together, the two manifests ask for "any NVIDIA GPU with at least 40 GiB of memory". Notice there is no nvidia.com/gpu: 1 anywhere in this YAML: that line belongs to the older device-plugin way used in the GPU labels example (Option 1 and Option 2), not to DRA.

Part 1: the ResourceClaimTemplate describes the GPU you want

  • name: gpu-40gb-plus: the name the pod uses to point at this request.
  • requests: - name: gpu: "I need one device, and I'll call it gpu."
  • exactly:: allocate exactly one device that matches. DRA can also list alternatives ("this, or else that"); here there's only one option.
  • deviceClassName: gpu.nvidia.com: only look at NVIDIA GPUs. The NVIDIA DRA driver creates this class when you install it.
  • The cel selector: a small filter in CEL (Common Expression Language) that reads "this device's memory compared with 40Gi is 0 or more", that is, at least 40 GiB. An A10G (24 GB) is filtered out; an A100 (40 or 80 GB) or an H100 (80 GB) qualifies. The memory attribute is published by NVIDIA's driver, which is why the names depend on the driver.

Part 2: the Pod uses it

  • spec.resourceClaims: create a claim for this pod from the gpu-40gb-plus template. Each pod gets its own ResourceClaim (named something like inference-dra-gpu-x7k2p), which is deleted with the pod. That's why it's a template: ten replicas get ten separate claims instead of fighting over one GPU.
  • containers[].resources.claims: - name: gpu: give the server container access to that device. In a pod with several containers, you choose which ones see the GPU.
  • No GPU count under resources.limits: the container lists claims instead. The claim is the request, so there is nothing to count.

What happens when you apply it

  1. The claim is created: Kubernetes makes the pod's ResourceClaim from the template.
  2. The scheduler filters and allocates: its DynamicResources plugin checks the devices each node publishes (as ResourceSlices, written by the driver) and filters out nodes with no free NVIDIA GPU of 40 GiB or more. Then it picks a node and records the exact GPU it chose in the claim.
  3. The kubelet prepares the device: on that node, the kubelet asks the driver's kubelet plugin to set up that GPU and expose it to the server container.
  4. The server starts: vLLM starts and sees exactly one GPU that's big enough.

Note: how do you install DRA?

You don't install DRA itself. The API (ResourceClaim, ResourceClaimTemplate, DeviceClass) is built into Kubernetes 1.34 and later. What you install is a DRA driver for your hardware: it advertises the devices on each node and allocates the one a claim asks for. For NVIDIA GPUs that's the NVIDIA DRA driver, installed with Helm:

Where DRA goes further: four cases

  • When GPUs on a node differ: a node label describes the node as one thing, so a node with one 80 GB and one 24 GB GPU can't be described honestly. DRA checks every GPU separately, so asking for two big GPUs only matches if both are big:

    apiVersion: resource.k8s.io/v1kind: ResourceClaimTemplatemetadata:  name: two-big-gpusspec:  spec:    devices:      requests:      - name: gpus        exactly:          deviceClassName: gpu.nvidia.com          count: 2                          # two devices...          selectors:          - cel:                            # ...and each one must pass this check              expression: device.capacity["gpu.nvidia.com"].memory.compareTo(quantity("40Gi")) >= 0

  • When several devices must fit together: a GPU and the network card it sends data through should sit on the same PCIe root, so traffic doesn't cross the CPU. Both drivers publish the standard attribute resource.kubernetes.io/pcieRoot, and matchAttribute requires the two devices to share it. On EKS the network card is an EFA device, offered by the dranet driver:

  • When pods share a GPU: create one ResourceClaim by name (not a template) and point several pods at it, so they all get the same GPU. How they share it is a driver setting; here NVIDIA's time-slicing (it may need to be turned on in the driver):

Built-in plugins, and what a second scheduler changes

Scenario. After learning in the scheduler deep dive that the fit check is done by "a plugin", the team wants the full list: which plugins run by default, what each one does, which ones filter and which ones score, and with what weight. Then the architect asks the follow-up: if we add a second scheduler, do these plugins still apply, and what can go wrong when two schedulers share one cluster?

What the picture shows. Every scheduling decision runs through the same stages, left to right, and each stage is made of plugins.

1Pending pod
its spec.schedulerName decides which of the three lanes handles it. Exactly one scheduler handles each pod.
2The stages (column headers)
  • Queue sort: decides which pending pod is considered next.
  • Filter: removes nodes that can't run the pod (Phase 1).
  • PostFilter: runs only when no node passed; this is where preemption happens.
  • Score: ranks the nodes that passed (Phase 2), each plugin's score multiplied by its weight.
  • Reserve / Permit: holds the chosen node's volumes and devices while the decision is finalized.
  • Bind: writes the chosen node into the pod (spec.nodeName).
3Blue lane, default-scheduler
the built-in kube-scheduler. On EKS it runs on the AWS-managed control plane, and every plugin shown is built in and on by default. The Score box lists the default weights (×1, ×2, ×3).
4Amber lane, a second kube-scheduler with your own profile
the same program and the same plugins, run as your own Deployment (the full example is in Appendix A). Only the highlighted Score box differs: InterPodAffinity weighted ×100, and NodeResourcesFit switched to MostAllocated (bin-packing).
5Teal lane, a replacement scheduler (Volcano, KAI, YuniKorn)
a different program with its own plugins (Volcano calls them "actions"): queues and PodGroups for gang scheduling, queue-based reclaim instead of plain preemption, GPU and network topology scoring, and binding a whole job together. It re-implements the basic fit checks, but the built-in plugins and weights above don't apply to its pods.
6Grey bar, shared by all three
the same nodes and the same API server. The schedulers don't coordinate with each other.

What a second scheduler changes:

7One pod, one scheduler
a pod is handled only by the scheduler named in its schedulerName. The other schedulers' plugins never see it.
8Same program, different profile (amber lane)
you can change weights, switch the scoring strategy, or disable plugins (for example turn off ImageLocality). One kube-scheduler process can even serve several profiles, each under its own schedulerName.
9Different program (teal lane)
you get features the built-in plugins don't have, such as gang scheduling, queues and GPU topology. In return, its pods follow its rules, not the table above.
10No coordination
two schedulers can pick the same free space at the same moment, because each one only sees its own decisions in flight. The kubelet then rejects the pod that arrives second (OutOfcpu / OutOfmemory) and its controller creates a new one. The usual fix is to give each scheduler its own nodes, with taints and node labels, or to send all pods of one kind (for example all GPU pods) to a single scheduler.
11Preemption crosses the boundary
the default scheduler's DefaultPreemption can evict pods placed by your scheduler if they have lower priority, and the other way round. Use PriorityClasses consistently across both.
12Autoscalers
Cluster Autoscaler and Karpenter decide whether to add nodes by simulating the default scheduler's rules. Check whether yours acts on pods with a custom schedulerName at all, and remember that custom filters it doesn't know about can lead to nodes being added that your scheduler then won't use.

Gang scheduling

Scenario. A research team submits a distributed PyTorch job with 8 GPU workers. The cluster only has room for 6, so the default scheduler starts 6 workers and leaves 2 Pending. The 6 running workers sit idle for hours, burning expensive GPU time while they wait for teammates that may never arrive. How do you stop that from happening?

What the picture shows. Gang scheduling (all-or-nothing) and why the default scheduler can't do it.

1The problem
standard Kubernetes schedules pods one at a time. In distributed training, all 8 workers must start together to run collective operations such as all-reduce. If only 6 fit, those 6 start and wait, wasting GPU time.
2The custom solution
a gang scheduler won't start any of the job's pods until the cluster has room for all of them.
3Can the standard scheduler do it?
No, it has no all-or-nothing start.
  • The workaround: you calculate cluster capacity yourself and make sure at least 8 GPU slots are free before you run kubectl apply.
  • The failure point: in a shared cluster, a coworker's 1-GPU pod submitted one second before yours can take a slot. Your job starts with 7 workers, hangs, and wastes money. Standard Kubernetes can't say "hold these 7 slots until the 8th is free."
4Best at this
Volcano and KAI are built specifically for this kind of atomic scheduling.
Going deeper3 points

The reason is the rendezvous barrier: distributed PyTorch workers wait until every rank has joined, so 7 of 8 workers will sit on their GPUs forever. The options sit at different layers:

  • the coscheduling plugin: a PodGroup with minMember and a timeout, inside kube-scheduler;
  • Kueue: decides at the job level whether a job may start;
  • KAI or Volcano: replace the scheduler.

Upstream Kubernetes added a native Workload API with gang scheduling as an alpha feature in 1.35 (off by default), and extended it in 1.36. Model-parallel inference has the same property: if one shard's pod is missing or dies, the whole replica is down, so it needs all-or-nothing scheduling and group restarts too.

Topology bin-packing

Scenario. A training job's two pods talk to each other constantly. The default scheduler puts them on two different GPU nodes because both nodes look "least allocated". Now every gradient exchange crosses the network instead of NVLink, and the training run takes several times longer than expected.

What the picture shows. Bin-packing for GPU topology: keeping chatty pods on the same fast interconnect.

1The problem
the default LeastAllocated scoring spreads pods across nodes. In ML that's bad for performance, because pod-to-pod traffic then goes over the much slower network.
2The goal
a scheduler that uses MostAllocated (bin-packing) to put the pods on the same physical GPU node.
3The benefit
pods can talk over NVLink, which has an order of magnitude or more bandwidth than the node's network, cutting training time sharply.
4Topology-aware bin-packing
goes further and looks at how the GPUs are wired. On an NVIDIA HGX system, it places pods that talk to each other on GPUs linked by NVLink (fast) rather than only PCIe (slow).
5Can the standard scheduler do it?
Partly.
  • The workaround: a required podAffinity with matchLabels: job: my-training-run and topologyKey: kubernetes.io/hostname, which forces pod 2 onto the node where pod 1 landed.
apiVersion: v1kind: Podmetadata:  name: trainer-2  labels:    job: my-training-runspec:  affinity:    podAffinity:      requiredDuringSchedulingIgnoredDuringExecution:      - labelSelector:          matchLabels:            job: my-training-run        topologyKey: kubernetes.io/hostname   # same node as the other trainers  containers:  - name: trainer    image: my-company/trainer:2.0    resources:      limits:        nvidia.com/gpu: 1
- **The failure point:** it only works if pod 1 finds a home first, and writing these rules for 100 pods is a management nightmare. A custom scheduler does it automatically for the whole batch.
6Best at this
the KAI Scheduler, NVIDIA's open-source scheduler with topology-aware placement for GPU fabrics.
Going deeper3 points

Placement depends on how the model is split:

  • Tensor parallelism splits every layer and exchanges results constantly. Keep it inside one node on NVLink/NVSwitch.
  • Pipeline parallelism splits by layers and only hands activations across once per stage, so it tolerates the slower links between nodes.
  • Hybrid: tensor parallelism inside nodes and pipeline parallelism between them is the common setup.

Even inside one server, not every GPU pair may share the same NVLink group. nvidia-smi topo -m shows it, and a job may rightly wait in the queue rather than start on badly connected GPUs.

Queueing and fair sharing

Scenario. In a shared research cluster, one user submits 100 training jobs on Monday morning and every GPU is taken. Other teams' jobs fail immediately with quota errors instead of waiting their turn, and over the weekend the GPUs reserved for one team sit idle while another team is desperate for capacity.

What the picture shows. Queueing and fair sharing, and where namespace quotas fall short.

1The problem
one greedy user can lock everyone else out of a shared cluster.
2Priority queues
queueing systems such as Kueue (a queue controller in front of the scheduler, not a scheduler itself) let you define resource flavors and workload priorities, so jobs wait in line instead of failing.
3Preemption
a high-priority inference pod serving a live model can evict a low-priority research training pod when GPUs run short. The default scheduler can already do this with PriorityClasses; what the custom tools add is preemption that understands quotas and whole jobs.
4Fair sharing
when the cluster is idle one team can use all of it, but as soon as another team submits work, the first team's over-quota pods are preempted to give the second team its fair share.
5Can the standard scheduler do it?
Only with static quotas.
  • The workaround: a ResourceQuota per namespace, for example 10 GPUs for the marketing team.
apiVersion: v1kind: ResourceQuotametadata:  name: gpu-quota  namespace: marketingspec:  hard:    requests.nvidia.com/gpu: "10"   # static: idle GPUs can't be lent to others
- **The failure point:** these quotas are static. If marketing isn't using its 10 GPUs, no one else can borrow them. And a team that hits its limit gets an immediate error; the pod doesn't queue and start later when space opens up.
6Best at this
Apache YuniKorn and Run:ai (via KAI), and Kueue, covered below.
Going deeper3 points

In Kueue terms:

  • ClusterQueues hold each team's nominal quota and borrowing limit.
  • Teams submit to LocalQueues.
  • A cohort lends idle quota between teams and takes it back by preemption when its owner needs it.

WorkloadPriorityClasses decide admission order, and fair sharing favors teams that have used less recently. Hard namespace ResourceQuotas can't do any of this: idle GPUs in one namespace never help another team's queue.

Hardware-aware scheduling

Scenario. A company buys a new rack of Blackwell GPUs connected by InfiniBand. Its inference team needs FP4 support, and its training team needs all workers on the same InfiniBand switch. The platform team wonders whether node labels are enough, or whether they need a custom scheduler.

What the picture shows. Hardware-aware scheduling for new GPU generations.

1What custom schedulers can look for
hardware features Kubernetes doesn't track well on its own.
  • RDMA / InfiniBand: placing pods on nodes that share the same high-speed InfiniBand switch.
  • Low-precision support: sending a workload only to GPUs that support the number formats it needs, such as FP8 (Ada and Hopper and newer) or FP4 (Blackwell).
2Can the standard scheduler do it?
Yes, to a point.
  • The workaround: label nodes by hand (gpu-gen=blackwell, network=infiniband) and add matching nodeSelectors to the AI pods, together with taints and tolerations.
apiVersion: v1kind: Podmetadata:  name: fp4-inferencespec:  nodeSelector:    gpu-gen: blackwell    network: infiniband  tolerations:  - key: nvidia.com/gpu    operator: Exists    effect: NoSchedule  containers:  - name: server    image: my-company/llm-server:1.0    resources:      limits:        nvidia.com/gpu: 1
- **The failure point:** this actually works well, and it's how most teams start. A custom scheduler only becomes necessary with thousands of nodes, when hand-managing labels for every hardware variation (FP8, HBM3, NVLink v4 and so on) becomes impractical.
3Leading example
NVIDIA's KAI Scheduler, aimed at rack-scale NVLink systems (GB200 NVL72 today, Vera Rubin racks next), where a whole rack behaves like one giant GPU.
Going deeper3 points
  • NVIDIA's GPU Feature Discovery labels every node with the GPU product (e.g. A100-SXM4-40GB), memory, architecture family, driver and CUDA versions, MIG capability, and the number of shared replicas.
  • Kueue turns these labels into ResourceFlavors: the premium flavor (NVLink + InfiniBand) is listed first, with a fallback flavor and TryNextFlavor.
  • Which hardware a job gets (flavor) and who goes first (priority) stay separate decisions.

Volcano vs. Kueue

Scenario. The platform team must pick a batch scheduler for a shared GPU cluster. One group runs PyTorch jobs with a master pod and 100 workers; another group is a set of departments that share 128 GPUs and want to borrow each other's idle capacity. Should they choose Volcano or Kueue?

What the picture shows. A side-by-side of the two most common choices, with a scenario for each.

1Volcano, the batch specialist
a full standalone batch scheduling system on Kubernetes, donated by Huawei and now a CNCF incubating project. Best for long training jobs, big data (Spark, Flink) and HPC. Its key feature is gang scheduling: it treats a group of pods as one job and starts none until there's room for all. You submit a Volcano Job custom resource (often called a vcjob) instead of individual pods.

2Kueue, the resource quota manager
a newer, cloud-native job queueing controller. Instead of replacing the scheduler, it is a gatekeeper in front of the default one. Best for shared clusters with many teams, multi-cloud and cloud bursting. It manages a global pool (say 100 A100s), holds jobs in a waitlist (a ClusterQueue), and admits a job when its quota allows; the standard scheduler then places the pods.
3The shared scenario
teams A and B each need 4 GPUs and the cluster has 4. The default scheduler might give each team 2, and both jobs wait forever. Volcano or Kueue gives all 4 to team A, which finishes, and then team B gets the cluster. Utilization goes up.
4Volcano's strength, task dependencies
in a PyTorch job with one master and many workers, if the master fails filtering (for example a port conflict), the workers would sit idle forever. Volcano can say "start the 100 workers only if the master is placed." Kueue admits a whole job's quota as one unit (and with waitForPodsReady it can requeue a job whose pods don't all start), but placement is left to the default scheduler, which doesn't order the pod types within a job.
5Kueue's strength, fair sharing and borrowing
marketing has a 10-GPU quota, data science has 50. On Friday night marketing is idle and data science needs 60. Both teams' ClusterQueues sit in the same cohort, so Kueue sees marketing's unused quota and lends its 10 GPUs. If someone in marketing submits a job on Saturday morning, Kueue preempts the borrowed work and returns the guaranteed GPUs. Volcano focuses on the performance of each job, not on sharing a budget between departments.

Going deeper6 points
  • The production answer is usually "both layers": Kueue for admission and quota on top of a gang-aware or topology-aware scheduler (kube-scheduler with plugins, KAI or Volcano), with a workload API that groups the pods (PyTorchJob/TrainJob, JobSet, LeaderWorkerSet).
  • Kueue stays vendor-neutral and keeps policy separate from mechanism.

  • A replacement scheduler is worth it when GPU-specific features (fractional GPUs, deep topology awareness) pay for the extra moving part.

  • For fine-tuning, Kubeflow Trainer shows the same layering.

  • The platform team publishes a TrainingRuntime (framework, image, defaults), and data scientists submit a TrainJob, often straight from a Python SDK.
  • The controller turns the pair into a JobSet, a group of Jobs that Kueue can then admit as one gang.

What every scheduler relies on

Scenario. Whichever scheduler the team picks, someone asks: "How does the scheduler even know a node has 8 GPUs, or that two nodes share an InfiniBand switch?" Without that information, no scheduler can make a smart decision.

What the picture shows. The plumbing every scheduler depends on, plus a note on YuniKorn.

1YuniKorn
originally built to bring the scheduling power of Hadoop YARN to Kubernetes. It runs as a replacement (or shim) for the default scheduler.
2The common foundation
whatever scheduler you choose, you'll almost certainly run the NVIDIA GPU Operator or the NVIDIA device plugin. These components tell the scheduler what hardware is in each node.
  • NVIDIA device plugin: advertises nvidia.com/gpu to the API server, so GPUs become a countable resource.
  • Network side: the NVIDIA Network Operator exposes RDMA / InfiniBand devices to pods, and switch-topology labels (from tools such as NVIDIA's Topograph) tell the scheduler which nodes share a switch, so it can group pods under one.
Going deeper6 points

  • the container toolkit, which injects /dev/nvidia* into containers;
  • the device plugin;
  • GPU Feature Discovery labels;
  • the MIG manager;
  • the DCGM exporter, which sends GPU utilization, memory, ECC errors, temperature and power to Prometheus.

Workloads and node tiers

Scenario. A company wants to run its customer-facing web API and its nightly batch jobs on the same Kubernetes cluster to save money. The web team is worried that a big batch run will slow the API down; the finance team wants batch to run as cheaply as possible. How do you design node pools so both groups are happy?

What the picture shows. A mind map of the mixed-workload strategy: first understand each workload, then give each one the right kind of node.

1Workload characteristic analysis
  • Real-time web services (the "VIPs"): latency-sensitive SLA (p99 under 100 ms, 99.9%+ uptime), predictable daily traffic patterns, CPU- and network-bound, must scale fast and tolerate almost no failure.
  • Batch processing jobs (the "opportunists"): latency-insensitive (minutes or hours are fine), bursty and CPU/memory heavy, fed from a queue, can retry and tolerate failure.
2Multi-tiered node architecture
  • Tier 1, web services (stability): On-Demand nodes (c6i family), tainted NoSchedule so batch jobs stay off.
  • Tier 2, batch processing (cost): diversified Spot instances, tainted for batch only and managed by Karpenter for fast, flexible scaling.
apiVersion: karpenter.sh/v1kind: NodePoolmetadata:  name: batch-spotspec:  template:    spec:      requirements:      - key: karpenter.sh/capacity-type        operator: In        values: ["spot"]      - key: karpenter.k8s.aws/instance-family        operator: In        values: ["m5", "m5a", "m6i"]      taints:      - key: workload        value: batch        effect: NoSchedule      nodeClassRef:        group: karpenter.k8s.aws        kind: EC2NodeClass        name: default  disruption:    consolidationPolicy: WhenEmptyOrUnderutilized    consolidateAfter: 30s
- **Tier 3, shared / burstable (utilization):** a mixed lifecycle pool, overprovisioned with placeholder pods so sudden spikes get capacity instantly.

apiVersion: scheduling.k8s.io/v1kind: PriorityClassmetadata:  name: placeholdervalue: -10                   # any real pod can preempt thesepreemptionPolicy: Never---apiVersion: apps/v1kind: Deploymentmetadata:  name: capacity-placeholderspec:  replicas: 5  selector:    matchLabels: {app: placeholder}  template:    metadata:      labels: {app: placeholder}    spec:      priorityClassName: placeholder      containers:      - name: pause        image: registry.k8s.io/pause:3.10        resources:          requests: {cpu: "1", memory: 2Gi}
3A note on CPU fairness
Kubernetes doesn't hand out CPU cycles itself; it delegates that to the Linux kernel, whose fair scheduler (CFS, replaced by the similar EEVDF scheduler in Linux 6.6) tries to give every process a fair slice (see CPU: shares and throttling).
Going deeper2 points

For LLMs, the latency-critical tier is the model server: vLLM, TGI, SGLang or NVIDIA NIM, each exposing an OpenAI-compatible API behind a Service. Large models need whole, dedicated GPUs and minutes to load, so I run them as plain Deployments (KServe's Standard mode) on tainted GPU nodes with warm capacity, rather than relying on scale-to-zero.

AI applications follow the same split:

  • Chat-style apps are synchronous: the user waits, so the orchestrator and model server stay warm and close together.
  • Event-driven AI backends (for example, scoring every new order for fraud) run asynchronously off a message bus. They can scale from zero with KEDA or Knative, and can live in the cheaper tier.

Priority, preemption and QoS

Scenario. During a traffic spike the web API needs more pods, but every node is full of batch jobs and a new node takes minutes to start. Later, a node runs out of memory and some pods are killed. The team wants web traffic to win in both cases, without starving batch work the rest of the time.

What the picture shows. Two separate tools that decide who wins when resources run short.

1Priority classes (for the scheduler), tool used: preemption, scope: cluster-wide.
  • web-critical (10000): the highest priority; it can preempt everything else.
  • batch-low (100): the lowest priority, with preemptionPolicy: Never, so batch never pushes anyone out.
apiVersion: scheduling.k8s.io/v1kind: PriorityClassmetadata:  name: web-criticalvalue: 10000---apiVersion: scheduling.k8s.io/v1kind: PriorityClassmetadata:  name: batch-lowvalue: 100preemptionPolicy: Never      # batch never pushes other pods out---apiVersion: v1kind: Podmetadata:  name: webspec:  priorityClassName: web-critical  containers:  - name: web    image: my-company/web:1.0
- **The effect:** when a node is full, high-priority web pods evict lower-priority batch pods, so web traffic never waits for a new node.
2QoS controls (for the kubelet at runtime), tool used: eviction, scope: per node.
The QoS class comes from the requests and limits in the manifest.
  • Guaranteed (web): requests equal limits. The most protected class and the last to be OOM-killed; with the static CPU manager and whole-number CPU requests it can even get exclusive cores.
  • Burstable (batch): requests lower than limits. Can scavenge spare capacity, but is evicted before Guaranteed pods.
  • BestEffort: no resources set. The first to be terminated under pressure.
apiVersion: v1kind: Podmetadata:  name: web                  # Guaranteed: requests == limitsspec:  containers:  - name: web    image: my-company/web:1.0    resources:      requests: {cpu: "1", memory: 2Gi}      limits:   {cpu: "1", memory: 2Gi}---apiVersion: v1kind: Podmetadata:  name: batch                # Burstable: requests < limitsspec:  containers:  - name: batch    image: my-company/batch:1.0    resources:      requests: {cpu: 250m, memory: 512Mi}      limits:   {cpu: "2",  memory: 2Gi}
- **The effect:** when a node runs out of RAM, the order usually works out as BestEffort → Burstable → Guaranteed. Strictly, the kubelet ranks by "using more than requested", then priority, then how far over the request; QoS follows from that.
3Shared tier
a mixed-lifecycle pool with no taints, where these two mechanisms do the arbitration.
Going deeper3 points
  • Kueue adds a job-level layer on top of these two.
  • WorkloadPriorityClasses decide admission order, and preemption can reclaim quota that another team borrowed.
  • Which hardware a job gets and who goes first are separate decisions.

Placement, autoscaling and cost

Scenario. The mixed cluster is running, but the team still has open questions: where exactly should each pod land, how fast should each tier scale, how should requests and limits be set, what happens when AWS takes back a Spot node, and which numbers should page someone at night?

What the picture shows. The tuning checklist, grouped into four areas.

1Placement logic
  • Node affinity: preferentially lands web services on their dedicated hardware.
  • Pod anti-affinity: spreads batch processors across hostnames so one node failure doesn't take them all down.
2Resource management
  • CPU: web services get high requests; batch jobs get low requests with high limits so they can soak up idle CPU.
  • Memory: memory can't be compressed and running out causes OOM crashes, so web services must be strict (requests equal limits), and batch jobs are sized to each job's needs.
3Autoscaling and Spot handling
  • HPA (web): aggressive scale-up (about 15 s) on CPU or request rate, conservative scale-down (about 5 min).
apiVersion: autoscaling/v2kind: HorizontalPodAutoscalermetadata:  name: webspec:  scaleTargetRef:    apiVersion: apps/v1    kind: Deployment    name: web  minReplicas: 4  maxReplicas: 100  metrics:  - type: Resource    resource:      name: cpu      target: {type: Utilization, averageUtilization: 60}  behavior:    scaleUp:      stabilizationWindowSeconds: 0      policies:      - {type: Percent, value: 100, periodSeconds: 15}    scaleDown:      stabilizationWindowSeconds: 300
- **Karpenter (batch):** intent-based scale-up; it removes empty nodes within about 30 s to cut waste. If one instance type isn't available at provisioning time, Karpenter picks whatever is available to get the job started. At runtime, as jobs finish and nodes are left half-used, it consolidates them.
- **Spot interruption:** catch the 2-minute warning so batch jobs can checkpoint and drain gracefully. With Karpenter, use its built-in interruption handling (an SQS queue); the AWS Node Termination Handler is for nodes Karpenter doesn't manage. Don't run both on the same nodes.
4Cost and monitoring
  • Optimization tactics: Spot diversification across several families (m5, m5a, m6i) in 3+ AZs for availability, and bin-packing pods tightly to reduce node count.
  • Metrics: p99 latency for web (typically under 100 ms), queue depth for batch, and the pending-pod count for capacity.
  • Alerting: immediate for web SLO breaches, threshold-based for batch failures.
Going deeper10 points
  • Packing pairs with the descheduler, which periodically evicts pods so they can be placed again on a tighter set of nodes.
  • Its strategy must match the scheduler's: HighNodeUtilization goes with MostAllocated, and LowNodeUtilization goes with LeastAllocated.
  • Mix them and you get an eviction loop.
  • For training, every eviction costs a checkpoint and restart, so PodDisruptionBudgets, maintenance windows and excluded namespaces matter.

  • Model-parallel inference scales in whole groups (a 4-GPU replica can't become 3), so autoscale on requests per second or latency with HPA or KEDA, and keep replicas warm because model loading is slow.

  • LLM servers break the usual autoscaling signals.

  • The default HPA watches CPU and memory, but the work happens on the GPU.
  • Request-based scaling (Knative's KPA) treats a 10-token answer and a 10,000-token answer as the same.
  • What works is KEDA on the model server's own metrics, such as vllm:num_requests_waiting or vllm:num_requests_running, or latency targets (TTFT, time per output token).
  • Scale-to-zero rarely fits: a new replica can take minutes to pull and load the model, so keep a warm minimum and alert on token latency and queue depth rather than CPU.

CPU: shares and throttling

Scenario. Users report that the web API is sometimes slow, with p99 latency spiking, but the CPU graphs for its pods look fine and the node is mostly idle. A batch job shares the node. Is the batch job stealing CPU, or is something else slowing the API down?

What the picture shows. Layer 1, CPU, a compressible resource: when CPU is short, pods slow down rather than die. Two kernel mechanisms are at work.

1CPU shares, who wins under contention
in a noisy-neighbour situation, Kubernetes relies on CPU shares, which come from your requests.
  • Requests become priority: a cpu: 1000m request becomes 1024 shares, and a 500m request becomes 512 shares. (On cgroup v2, which Kubernetes 1.35+ requires, the file is cpu.weight on a different scale, but the ratio is the same.)
apiVersion: v1kind: Podmetadata:  name: webspec:  containers:  - name: web    image: my-company/web:1.0    resources:      requests: {cpu: 1000m}   # -> 1024 shares---apiVersion: v1kind: Podmetadata:  name: batchspec:  containers:  - name: batch    image: my-company/batch:1.0    resources:      requests: {cpu: 500m}    # -> 512 shares
- **The CFS logic:** the kernel's fair scheduler (CFS, or EEVDF on Linux 6.6+) tracks how much CPU time each process has had and favours the ones that have had less.
- **When the CPU is 100% busy:** the web service (1024 shares) is guaranteed 2/3 of the time and the batch job (512 shares) 1/3.
- **When the web service is idle:** the batch job can use the spare CPU, but the moment the web service wakes up, batch is squeezed back to its 1/3.
2Throttling, the 100 ms quota window
a CPU limit is a speed limit the kernel enforces per 100 ms period.
  • Example: a limit of 0.5 CPU (500m) gives 50 ms of run time every 100 ms.
apiVersion: v1kind: Podmetadata:  name: apispec:  containers:  - name: api    image: my-company/api:1.4    resources:      requests: {cpu: 250m}      limits:   {cpu: 500m}    # 50 ms of CPU time per 100 ms window
- **The sprint:** a multi-threaded app can use all 50 ms in the first 10 ms of the window, and is then frozen for the remaining 90 ms.
- **The wait:** even if the node's CPU is 90% idle, the app can't run until the next window starts.
- **Normal vs. throttled:** a request that normally takes 10 ms takes about 100 ms when it's frozen mid-calculation (10 ms of work plus about 90 ms of waiting).
3The impact, latency jitter
throttling stops and starts the app in tiny bursts, so average latency looks fine while p99 spikes wildly. This is the answer to the scenario: the API is hitting its own CPU limit, not losing CPU to the batch job.

Kernel vs. Kubernetes

Scenario. A developer asks a fair question: "I set cpu: 250m, but my pod uses a whole core when the node is quiet, and slows down when it's busy. So what does the request actually do, and who enforces it?"

What the picture shows. How a Kubernetes CPU request turns into kernel behaviour. The Linux kernel is the enforcer; Kubernetes is the policy maker that tells it who matters.

1The kernel doesn't know Kubernetes
it has no idea what a pod or "100m CPU" is. It only understands control groups (cgroups) and CPU shares.
2The handshake, in three steps
  • Kubernetes (the policy maker): you write cpu: 250m in your YAML.
  • The kubelet (the translator): it converts that number into something the kernel understands.
  • The Linux kernel (the enforcer): the kubelet and container runtime write the value into the pod's cgroup (cpu.shares on cgroup v1, cpu.weight on cgroup v2), and the kernel enforces it; 1000m (one core) equals 1024 shares.
3When the node is idle
a pod that requests 100m but is the only thing running may use 100% of the CPU. The request isn't a cage.
4When the node is under contention
if five pods all want 100%, the kernel divides time by shares. A pod with 1000m (1024 shares) gets 10 times more time than one with 100m (102 shares).
5Admission control, Kubernetes' real job
the one thing the kernel can't do is stop a node from getting too crowded. The scheduler treats requests as reservations: on a 4-core node that already has 3.8 cores requested, it refuses to add more pods.
6The consequence of skipping requests
the scheduler might pack 100 pods onto one node, and even with perfect fairness each pod would get about 1% of a CPU, so the whole application crawls.
7Bridge to memory
CPU can be stretched by slowing things down, but memory is all-or-nothing.

Memory: who gets killed

Scenario. A node runs low on memory and Kubernetes kills a pod that was using only 150 MiB, while a much bigger pod using 510 MiB survives. The owner of the small pod is angry: "Why did you kill the small one?"

What the picture shows. Layer 2, memory, a non-compressible resource: you can't slow memory down, so when it runs out someone has to die.

1Two levels of OOM
  • Container level: if a container goes over its own memory limit, the kernel kills processes inside that container.
  • Node level: if the whole server runs out of memory, even when no pod hit its limit, the kernel's OOM killer looks at every process on the node and picks a victim.
2QoS classes set the eviction risk
Kubernetes gives every pod a QoS class from its requests and limits: BestEffort (highest risk), Burstable (medium), Guaranteed (lowest).
3The scoreboard, oom_score_adj
the kubelet tags every process with an OOM score adjustment so the kernel knows who matters. A higher score means more likely to be killed.
  • BestEffort: 1000, "kill me first".
  • Burstable: 1000 − 1000 × (memory request ÷ node memory), kept between 2 and 999, so a bigger request makes the pod safer.
  • Guaranteed: −997, "don't kill me".
4The worked example (two Burstable pods)
pod A requested 100 Mi and uses 150 Mi (50 Mi over). Pod B requested 500 Mi and uses 510 Mi (10 Mi over). Both use more than they requested and (here) have the same priority, so the kubelet evicts the pod furthest over its request: pod A goes first, even though it uses far less memory than pod B. That's the scenario's answer.
5Not the scheduling score
this score is about killing a pod, not about choosing a node (see Scheduler score vs. OOM score).

Network: the unmanaged resource

Scenario. An API pod's latency suddenly spikes and it starts dropping connections, yet its CPU and memory graphs look perfectly normal. Hours later someone notices that a backup pod in a different namespace, on the same node, started a large transfer at exactly that time.

What the picture shows. Layer 3, network, an unmanaged resource: unlike CPU and memory, standard Kubernetes doesn't control it at all.

1The Wild West, unmanaged bandwidth
Kubernetes treats the network as an all-you-can-eat buffet. There is no network-requests or network-limits field in the pod spec.
  • The problem: a busy API pod and a backup-sync pod share a node, and the backup pod starts a 10 Gbps transfer.
  • The result: the node's physical NIC is saturated. The API's latency spikes or it drops connections, while its CPU and memory look normal.
2The noisy-neighbour effect
  • Shared fate: every pod on the node shares the same pipe to the outside world.
  • Silent failures: most monitoring is per pod, so you see your app failing without realizing an unrelated pod in another namespace is hogging the bandwidth.
3Solutions, taming the traffic
  • A. Linux tc (traffic control): shape traffic on the node at the kernel level.
  • B. CNI bandwidth plugins: most modern CNIs (Calico, or the standard bandwidth plugin) let you set ingress and egress limits with annotations in the pod YAML; Cilium's bandwidth manager supports the egress annotation.
apiVersion: v1kind: Podmetadata:  name: backup-sync  annotations:    kubernetes.io/ingress-bandwidth: 1G   # needs a CNI with the bandwidth plugin    kubernetes.io/egress-bandwidth: 1Gspec:  containers:  - name: sync    image: my-company/backup-sync:1.0
4Architecture tip, the EKS benefit
current Nitro instances are EBS-optimized by default, so EBS traffic has its own dedicated bandwidth and doesn't compete with user traffic. The n variants (such as m5n and c5n) add much higher network bandwidth on top. (The diagram's wording, that only m5n/c5n separate the two, is outdated.)

Storage I/O: the other unmanaged resource

Scenario. The production database's disk latency jumps from 1 ms to 200 ms, its liveness probe starts failing, and Kubernetes restarts it, which makes things worse. The database itself is doing nothing unusual; a log-archiver pod sharing the same volume has just started a huge read.

What the picture shows. Layer 4, storage I/O, also unmanaged at the container level. AWS limits the speed of the whole EBS volume, but Kubernetes has no way to say "pod A gets 80% of the disk and pod B gets 20%".

1Per-volume vs. per-container mismatch
  • AWS's view: you pay for performance per volume (for example 3,000 IOPS on gp3). AWS only sees the volume; when it hits 3,000 IOPS, the whole disk is throttled, no matter which pod caused it.
  • Kubernetes' view: several pods on the same node can share one ReadWriteOnce volume, a node's local disk, or the node's bandwidth to EBS.
  • The example: a background log archiver uses all 3,000 IOPS, and the production database on the same disk goes from 1 ms to 200 ms latency.
2The missing controller, blkio
the Linux kernel has a block I/O cgroup controller (blkio on cgroup v1, io with io.max and io.weight on cgroup v2) that can set weights or byte-per-second limits. Kubernetes exposes CPU and memory in the pod spec but not blkio; there is no resources.limits.iops field.
3The consequences of unmanaged I/O
a saturated disk causes a blocking ripple effect.
  • I/O wait: the CPU sits idle waiting for the disk, so CPU graphs look low while the app feels very slow.
  • Stuck processes: a process writing to a saturated disk enters uninterruptible sleep (the D state in top) and can't be killed until the I/O finishes.
  • Liveness probe failures: if the health check writes a small file and the disk is too slow, the probe fails and Kubernetes restarts the pod, making things worse. That's the scenario.
4How to fix it (the hard way)
  • Dedicated volumes: give every critical pod its own EBS volume through its own PVC, so pod A's disk use physically can't affect pod B.
  • Static guardrails: set the cgroup I/O limits on worker nodes yourself, for example with a privileged DaemonSet or a node agent. The kubelet has no setting for it. It works, but it's hard to maintain.
  • Instance selection: EBS-optimized instances keep disk and network traffic off the same physical pipe on the EC2 host.

Policy maker, translator, enforcer

Scenario. A web service and a batch job run on the same node. The web pod asks for 1 CPU with a limit of 2; the batch pod asks for 250m with a limit of 500m. An engineer wants to know what actually happens inside Linux to those four numbers, both when the CPU is busy and when it's idle.

What the picture shows. Three columns showing how a pod spec becomes kernel behaviour.

11. Kubernetes (the policy maker)
two pod specs.
  • Web service pod (high priority): requests cpu: 1000m, limit cpu: 2000m.
  • Batch job pod (low priority): requests cpu: 250m, limit cpu: 500m.
apiVersion: v1kind: Podmetadata:  name: web-servicespec:  containers:  - name: web    image: my-company/web:1.0    resources:      requests: {cpu: 1000m}      limits:   {cpu: 2000m}---apiVersion: v1kind: Podmetadata:  name: batch-jobspec:  containers:  - name: batch    image: my-company/batch:1.0    resources:      requests: {cpu: 250m}      limits:   {cpu: 500m}
- **Kubelet (the translator):** reads these specs and writes them into cgroups.
22. Linux cgroups (the translator's output)
a cgroup per pod (with one per container inside it), each with two files.
  • Web service cgroup: cpu.shares = 1024 and cpu.cfs_quota_us = 200000 per 100 ms period.
  • Batch job cgroup: cpu.shares = 256 and cpu.cfs_quota_us = 50000.
  • The rule: the request becomes shares (a weight); the limit becomes a quota (a speed limit).
33. Linux kernel CFS (the enforcer)
the CPU cores and the CFS scheduler, shown over one 100 ms period.
  • A. Contention (CPU busy): the web service (1024 shares) gets about 80% of the time and the batch job (256 shares) about 20%. Shares keep the split proportional under heavy load.
  • B. Idle / throttling (CPU free): the web service runs, then the batch job runs for its 50 ms, then is throttled for the remaining 50 ms because it reached its quota, even though the CPU is idle. Limits cap a process even when there's spare capacity.
4A note on cgroup versions
the picture uses the cgroup v1 file names. Kubernetes 1.35+ requires cgroup v2, where the same settings live in cpu.weight (the shares, on a 1–10000 scale) and cpu.max (for example 200000 100000, quota then period). The behaviour is the same.
5Summary banner
Kubernetes sets the policy (weights and limits), the kubelet translates it into cgroups, and the kernel enforces it with shares (for contention) and quotas (for capping).

From a limit to a quota

Scenario. A pod has a CPU limit of 2000m. An engineer looks inside the node and finds cpu.cfs_quota_us = 200000, which is 200 ms. But the scheduling window is only 100 ms. How can a pod have 200 ms of CPU inside a 100 ms window?

What the picture shows. The arithmetic that turns a CPU limit into a kernel quota.

1Linux cgroups use two files for a CPU limit
  • cpu.cfs_period_us, the scheduling window: in Kubernetes almost always 100,000 µs, which is 100 ms of real time.
  • cpu.cfs_quota_us, the allowance: how much CPU time the pod may use within each window.
2The formula Kubernetes uses
quota = limit in cores × period.
3Worked example, a 2000m limit
2000m ÷ 1000 = 2.0 cores; 2.0 × 100,000 µs = 200,000 µs (200 ms).
4How can 200 ms fit in a 100 ms window?
Quotas add up across all CPU cores. A node with 4 cores has 400 ms of CPU time available in every 100 ms of real time.
5cgroup v2
on current nodes the same two numbers sit in one file, cpu.max, as 200000 100000.
6What the kernel is really saying
"your pod may do 200 ms of work per window, for example by running at 100% on two cores for the whole 100 ms."

The stuck volume

Scenario. A worker node running a database crashes suddenly. Kubernetes reschedules the database pod onto a healthy node, but the pod is stuck in ContainerCreating because its volume won't attach. The EBS console still shows the volume as attached to a node that no longer exists.

What the picture shows. Pod crash loop after a node failure: the stuck volume.

1Why it happens
when a node dies suddenly, AWS doesn't always notice that its EBS volume is free.
2The problem
the volume stays Attached to the dead node. When Kubernetes tries to start the pod elsewhere, AWS refuses to move the disk because it thinks it's still in use.
3The symptom
the new pod sits in ContainerCreating with a FailedAttachVolume / Multi-Attach error event.
4The fix
once you're sure the old node is really gone, delete its Node object or add the node.kubernetes.io/out-of-service taint, so Kubernetes force-detaches the volume. Force-detaching in the AWS console is the last resort.
5Prevention
keep the EBS CSI driver up to date; newer versions handle multi-attach and node-unstage timeouts more gracefully.

Snapshot restored in the wrong AZ

Scenario. After an incident, an engineer restores a database from an EBS snapshot. The volume is created successfully, but the database pod never starts. All the database nodes are in us-east-1b, and nobody noticed that the restored volume landed in us-east-1a.

What the picture shows. Snapshot restored in the wrong Availability Zone.

1The rule
EBS volumes are regionally resilient but AZ-locked; a volume can only attach to nodes in its own AZ.
2The problem
a snapshot restored into us-east-1a can never be used by database nodes in us-east-1b. Kubernetes can't stretch a cable between data centres.

Force delete and filesystem corruption

Scenario. A database pod is stuck in Terminating, and an impatient engineer runs kubectl delete pod --force --grace-period=0. The pod comes back on another node, but the database won't start: its filesystem is corrupted.

What the picture shows. Filesystem corruption after a forced delete.

1The problem
--force --grace-period=0 deletes the pod from the API immediately, without waiting for the kubelet to confirm the container has stopped. If the node is still alive, the old database process may keep running and writing, or be killed without a clean shutdown, while a replacement starts. Two writers, or an unclean stop in the middle of a write, can corrupt the data.
2The fix
never force-delete a database pod unless the node is already physically gone.
3Recovery
if corruption happens, restore from the last known good snapshot and let the database replay its write-ahead log (WAL) to catch up to the last valid transaction.

IOPS throttling cascade

What the picture shows. IOPS throttling and the cascading failure it causes.

1The problem
gp3 volumes include 3,000 IOPS for free. If the database suddenly needs 10,000 IOPS, AWS throttles the disk.
2The cascade
disk latency goes from 1 ms to 100 ms or more, so database connections pile up, the connection pool fills, and the whole application crashes.

watch BurstBalance (for gp2) or the volume throughput and IOPS metrics in CloudWatch. For heavy databases don't rely on the baseline; provision exactly the IOPS you need (for example iops: 10000 in the StorageClass).

Cross-AZ transfer costs

Scenario. The finance team asks why the AWS networking bill for the data platform is now higher than the compute bill. The platform runs a 3-node Kafka cluster spread across three Availability Zones for resilience.

What the picture shows. Cross-AZ data transfer costs.

1The problem
a 3-node Kafka cluster in 3 AZs replicates every message 3 times. Ingesting 100 TB means that data crosses AZ boundaries twice (once to each replica), and AWS charges for every cross-AZ byte. At scale, networking can cost more than compute.
2Fix 1, compression
compress with Zstd or Snappy before the data leaves the node.
3Fix 2, rack awareness
configure Kafka or Cassandra with rack awareness so clients read from a replica in their own AZ (free) instead of one in another AZ (paid).

The page-cache memory trap

Scenario. A nightly ML batch job keeps getting OOM-killed, and when it does, other pods on the same shared node get evicted too. The engineers are sure there's no memory leak: the job only reads a large training dataset from disk, over and over. So where is the memory going?

What the picture shows. The page-cache memory trap, which looks like a leak but isn't.

1Memory "leak" in a batch job
the job's memory slowly grows until it is OOM-killed, and on a shared node the kubelet then starts evicting other pods.
2Why it happens
when a job reads a 100 GB dataset, the kernel keeps that data in the page cache (RAM) so a second read is fast. It keeps filling RAM with cache until the node is nearly full.
3The confusion
to the kernel, cache counts as "available" because it can be dropped instantly. To Kubernetes, part of that cache is charged against the container's limit.
4Kubernetes' point of view
it doesn't look at "used RAM"; it looks at the working set size, and that's the number that triggers OOM kills.
5The trap in ML
training loops read the same data many times. The first read is inactive cache, which Kubernetes ignores. The second read promotes it to active cache, the working set jumps, and the pod hits its limit, even though that memory is just a copy of a file on disk.
6Why do pods die if cache can be dropped?
A memory limit creates a cgroup "box". When the memory charged to the box reaches the limit, the kernel must reclaim memory inside it before granting more. Clean cache can usually be dropped, so the real killers are: dirty pages that can't be written out fast enough, files on a memory-backed emptyDir (tmpfs), which can't be dropped at all, and node-level eviction by the kubelet, which looks at a working set that includes active cache.
7The solutions
  • Don't set a memory limit: with only a request, the pod can use the node's free cache and is killed only if the node itself runs out.
apiVersion: v1kind: Podmetadata:  name: etl-workerspec:  containers:  - name: etl    image: my-company/etl:1.0    resources:      requests:        memory: 8Gi     # no limit: killed only if the node itself runs out
- **Widen the gap:** set the limit well above the request to pay the "page cache tax".
- **Monitor the right metric:** `container_memory_working_set_bytes` shows what Kubernetes sees.
- **App-level tuning:** in Python or C++, call `posix_fadvise(POSIX_FADV_DONTNEED)` after processing a range of a file. It's a hint that tells the kernel "I'm done with this part, you can evict it", which puts you, not the kernel, in charge of what stays cached even on a 1 TB dataset.
8The opposite advice, for shared nodes
  • Don't skip the limit: it's better for one batch job to die than for it to make the node evict everyone else.
  • Request = limit: give batch jobs Guaranteed QoS so the kubelet can't over-schedule the node.
apiVersion: v1kind: Podmetadata:  name: etl-workerspec:  containers:  - name: etl    image: my-company/etl:1.0    resources:      requests: {cpu: "4", memory: 16Gi}      limits:   {cpu: "4", memory: 16Gi}   # Guaranteed QoS

Thundering herd

Scenario. A data team launches 100 identical batch jobs in parallel. They all finish within the same second and all write their results to the database at once. The database connection pool is exhausted, and the customer-facing web service starts failing its queries.

What the picture shows. The thundering herd: your own jobs attacking your own database.

1Why they finish together
AI and big-data pipelines often start jobs in parallel, and if every job processes the same amount of data (say 1 GB each), they finish at almost the same moment.
2The incident
100 batch jobs complete at once and all write to the database. The connection pool runs out, and web service queries fail.
3The root cause
batch jobs aren't rate-limited when they talk to shared services. By crossing the finish line in the same millisecond, they effectively run a DDoS attack on your own infrastructure.
4The solution, a queue as shock absorber
put a message queue (SQS, RabbitMQ or Kafka) in between. Batch jobs publish their results, and a separate consumer with controlled parallelism writes them to the database.
5The quick fix, jitter
if you can't add a queue yet, have each pod sleep for a random time before writing, so the writes spread out.
Going deeper

Event-driven AI services and agents hit the same problem when a burst of events arrives at once. Put a message queue in front so events wait while pods restart, make every handler idempotent so duplicate events are harmless, and use a compensating action (the Saga pattern) to undo half-finished multi-step work.

Scheduler thrashing

Scenario. During a traffic spike the cluster becomes unstable: the same batch pods are created, evicted, created again and evicted again, over and over. Nodes churn, nothing finishes, and the scheduler is busier than ever. Two controllers are fighting each other.

What the picture shows. Scheduler thrashing: a feedback loop between priorities and controllers.

1The symptom
pods are repeatedly scheduled and evicted, and the cluster becomes unstable.
2The two players
the Horizontal Pod Autoscaler (HPA) is trying to save production traffic, and the Job controller is trying to finish its work.
3The loop, step by step
  • The trigger: the high-priority web service gets a traffic spike and the HPA adds 50 pods.
  • The conflict: the cluster is full, so the scheduler finds 50 low-priority batch pods and preempts them to make room.
  • The loop: the Job (or CronJob) controller sees its pods are gone ("I should have 50 workers but I have 0") and creates them again. They grab any capacity that frees up (or make the autoscaler add nodes), and the next scale-up preempts them again. Create → evict → create → evict.
4Why restartPolicy isn't the fix
Jobs use Never or OnFailure, but either way the Job controller immediately creates a replacement when a pod is preempted, so restartPolicy alone doesn't stop the loop.
5The solution, queue instead of retry
admit Jobs through Kueue only when capacity actually exists; when a Kueue job is preempted it is suspended and requeued as a whole, instead of being recreated pod by pod. Add preemptionPolicy: Never on batch so it never pushes others out, and a podFailurePolicy so preempted pods don't use up the Job's retry budget (backoffLimit).
apiVersion: batch/v1kind: Jobmetadata:  name: nightly-batch  labels:    kueue.x-k8s.io/queue-name: batch   # admitted only when capacity existsspec:  parallelism: 50  completions: 50  backoffLimit: 6  podFailurePolicy:    rules:    - action: Ignore                  # preemption doesn't burn the retry budget      onPodConditions:      - type: DisruptionTarget  template:    spec:      priorityClassName: batch-low    # preemptionPolicy: Never      restartPolicy: Never      containers:      - name: worker        image: my-company/batch:1.0
Going deeper

The same kind of loop appears when a descheduler's strategy disagrees with the scheduler's scoring: pods get evicted, land back on the same node, and get evicted again. A steadily rising eviction count with no consolidation is the signal.

CPU limit vs. request gap

Scenario. The web service's p99 latency spikes, yet the node's average CPU use is only 60%. The web pods aren't busy and nothing looks saturated. The only clue is a batch job on the same node with a 1-core request and an 8-core limit.

What the picture shows. The CPU limit vs. request gap, and how it creates latency jitter.

1The symptom
web service latency spikes while node CPU utilization sits at 60%.
2The setup
the batch job has a 1-core request but an 8-core limit. When it has work, it tries to use all 8 cores at once.
3Why the batch job isn't throttled
its quota is 8 × 100 ms = 800 ms per window, so it can burst freely. But the scheduler reserved only its 1-core request, so web pods on that node suddenly compete with 7 extra busy cores.
4What the request actually does
it only sets CPU shares. Under contention CFS splits CPU by shares, but the batch burst still grabs cores, caches and memory bandwidth in spikes.
5The result
if the web pods have tight CPU limits, those spikes throttle them, giving p99 jitter at a 60% average.
6The solution
for CPU-heavy batch jobs, set requests close to limits. That tells Kubernetes "this pod is heavy, don't pack too much else here", and the batch job gets a steady share instead of violent bursts. For I/O-bound batch work (mostly waiting on network or disk), low requests are fine.
apiVersion: batch/v1kind: Jobmetadata:  name: feature-builderspec:  template:    spec:      restartPolicy: Never      containers:      - name: builder        image: my-company/feature-builder:1.0        resources:          requests: {cpu: "6"}          limits:   {cpu: "8"}   # small gap: a steady share, no 7-core surprise

A SaaS platform hosts standard, premium and regulated tenants on a shared Kubernetes cluster. The question running through this deep dive: if one tenant is compromised, what can it reach?

Tenant classes, soft and hard isolation

Scenario. A SaaS company is moving all its customers onto one shared Kubernetes cluster. Most customers are small, but a few are banks with PCI and data-residency rules, and one noisy customer once took down a shared database. The architects need a plan for which customers can share and which need walls between them.

What the picture shows. A mind map of the multi-tenancy strategy, from classifying tenants to the two isolation styles.

1Tenant classification
decide what each tenant needs based on data sovereignty, compliance (PCI, HIPAA, SOC 2), acceptable blast radius and SLA requirements.
2Soft isolation (namespace)
  • ResourceQuotas and LimitRanges: stop one tenant from exhausting cluster resources.
  • NetworkPolicies (default deny): block traffic between tenants unless explicitly allowed.
apiVersion: networking.k8s.io/v1kind: NetworkPolicymetadata:  name: default-deny  namespace: tenant-aspec:  podSelector: {}          # every pod in the namespace  policyTypes: ["Ingress", "Egress"]
- **Pod Security Standards, enforced by Pod Security Admission (PSA):** three levels, Privileged (no restrictions, the danger zone), Baseline (reasonable defaults) and Restricted (maximum, production-grade hardening). The example labels the `prod` namespace with `pod-security.kubernetes.io/enforce: restricted`.

apiVersion: v1kind: Namespacemetadata:  name: prod  labels:    pod-security.kubernetes.io/enforce: restricted
- **RBAC-scoped service accounts:** the identity each pod runs as. Service accounts always live in a namespace; the point is to grant them namespace `Role`s and `RoleBinding`s, never cluster-wide `ClusterRoleBinding`s.
3Hard isolation (node / cluster)
  • Dedicated node groups: different instance families per workload type.
  • Taints and tolerations: make sure a tenant's pods run only on its designated nodes.
  • VPC subnet segmentation: separate subnets per tenant tier for network-level separation.
  • Dedicated clusters (highly regulated tenants): complete isolation, at the cost of operational complexity and money.
4The key warning
namespaces are authorization boundaries, not trust boundaries. They protect against configuration mistakes, but not against kernel exploits or host-level resource exhaustion.
Going deeper5 points
  • GPUs need the same soft vs. hard choice.
  • Time slicing advertises several virtual GPUs per physical GPU, with no memory or fault isolation: one pod can exhaust the memory or crash the GPU for everyone.
  • MIG (on data-center GPUs such as A100, H100 and newer) carves a GPU into hardware-isolated slices with their own memory, for example up to 7 on an A100-40GB.
  • That's the right choice for strict multi-tenancy.
  • Quota between tenants (who gets how many GPUs) is a separate problem, handled by Kueue's ClusterQueues and cohorts.

Identity, data, network and observability

Scenario. The same SaaS company now has to prove to an auditor that tenant A can never read tenant B's data, even if a pod is compromised or credentials leak. That has to hold across AWS permissions, the databases, the network and the logs.

What the picture shows. Tenant isolation beyond Kubernetes, in four areas.

1Identity and access
  • IRSA (IAM Roles for Service Accounts) with an OIDC provider: each tenant's pods get their own IAM role, mapped to their Kubernetes service account through the cluster's OIDC provider.
  • Fine-grained AWS permissions: per-tenant roles shrink the blast radius and enforce tenant isolation at the AWS level.
2Data layer
  • RDS (Proxy, IAM auth, RLS): RDS Proxy prevents connection-storm crashes. The app uses IAM to get a short-lived database token, and row-level security inside the database maps IAM role → DB role → RLS policy.
  • S3 (bucket policies, VPC endpoints): a bucket per tenant, with bucket policies that allow only that tenant's role and only through your VPC endpoint, so leaked credentials are useless outside your network.
  • ElastiCache (dedicated or logical): separate clusters per tier, with logical databases per tenant in shared tiers.
3Network architecture
  • Shared ALB vs. dedicated NLB: a shared ALB with host-based routing for the standard tier; dedicated NLBs for the premium tier, with client IP preservation and no noisy neighbours.

Network isolation and egress

Scenario. A regulated customer requires that traffic between their pods is encrypted, and that their pods can only reach approved external services. The platform team also struggles with egress rules: pod IPs change all the time, so a firewall can't tell which tenant sent a packet.

What the picture shows. Network-level isolation between tenants: overlays, eBPF, encryption and egress.

2Cilium with eBPF
a CNI that can replace kube-proxy and iptables. Instead of a huge rulebook, it uses eBPF programs to reprogram the kernel's network path on the fly. That gives fast packet filtering plus L7 policies (filtering on HTTP method and path) and DNS-aware policies.

for regulated workloads, the CNI intercepts each packet just before it leaves the node, wraps it in an encrypted tunnel, decrypts it on the receiving node and hands it to the target pod. This gives pod-to-pod encryption at L3, in the kernel, without a service mesh.

  • Even better on Nitro: AWS encrypts traffic in transit automatically, in hardware, between certain Nitro instance types.
4Egress control
use VPC endpoints for AWS services and a NAT gateway with security group rules, or a transparent egress proxy with tenant-aware filtering.

the problem in the scenario is that the proxy doesn't know which tenant sent a packet, and pod IPs keep changing. Tenant-aware filtering bridges that identity gap: the proxy first works out who sent the packet, then applies that tenant's rules.

NUMA and CPU pinning

Scenario. A database on a large r6i.8xlarge instance has inconsistent query latency. The CPU isn't saturated and the disk is fine, but some queries are mysteriously slower than others. Profiling shows many accesses to memory that is "far away" from the CPU running the query.

What the picture shows. CPU pinning and NUMA awareness on large multi-socket servers.

1NUMA nodes
a large two-socket server (such as an r6i.32xlarge or a metal instance) is split into NUMA nodes, each with its own CPU cores and its own bank of local RAM.
2Local access
a core reading RAM attached to its own socket is very fast.
3Remote access
if the data is in RAM on the other socket, the request must cross a bridge (Intel UPI or AMD Infinity Fabric), which adds latency and cuts bandwidth.
4Without awareness
Kubernetes treats all CPUs and RAM as one pool. If a database's vCPUs are on socket 0 but its data is in socket 1's RAM, every query pays a remote-memory tax.
5Context switching and cache thrashing
the kernel also moves the database process between cores to balance load, and each move throws away warm CPU caches.
6The solution, kubelet configuration
enable the static CPU manager and topology manager policies, so Guaranteed pods with whole-number CPU requests get exclusive cores, and their CPU and memory come from the same NUMA node.

  • Without it, the CPU manager and the device manager can give a pod CPUs from one NUMA node and GPUs from another.

How EBS really behaves

Scenario. A database team plans its IOPS budget on gp2 volumes: 3,000 IOPS sounds like plenty. In production, large sequential writes and a long, heavy reindex exhaust the budget within hours, and latency jumps. They misunderstood how EBS counts IOPS and how gp2 bursting works.

What the picture shows. The rest of the active-passive failover, then Layer 1 of the storage stack: EBS itself.

1Failover event (AZ-A goes down)
restore the latest snapshot as a new volume in AZ-B, change the StatefulSet's nodeSelector to AZ-B, and the pod restarts there and attaches the new volume.
2Layer 1, AWS block storage (EBS)
EBS volumes are network-attached block devices.
3Latency composition
network round trip (0.2–0.5 ms within an AZ) + EBS service latency (under 1 ms for io2 Block Express) + the effect of queue depth.
4IOPS accounting
one IOPS is one I/O operation of 256 KiB or smaller. A single 1 MB (1024 KiB) write counts as 1024 ÷ 256 = 4 IOPS. With a 3,000 IOPS limit and lots of large sequential writes, you run out much faster than you'd expect.
5gp2 burst credits vs. gp3
  • gp3: a flat 3,000 IOPS baseline with no burst credits; provision more explicitly if needed.
  • gp2 burst: idle gp2 volumes earn credits and spend them to burst to 3,000 IOPS (for example a quick index rebuild).
  • The cliff: if load stays high for hours, the gp2 "fuel tank" empties and AWS drops you to the baseline of 3 IOPS per GiB (minimum 100). That's the scenario.
6The metrics
for gp2/st1/sc1 watch BurstBalance (0% means you've hit the cliff). For gp3 watch actual vs. provisioned IOPS and VolumeQueueLength.

File system, mount options and O_DIRECT

Scenario. A team wants two database nodes to share one EBS volume for faster failover, and also wants to tune the filesystem for speed. After enabling Multi-Attach and a few "fast" mount options, they get corrupted data. Each of these settings has a catch.

What the picture shows. Volume and filesystem choices, each with its trade-off.

1Multi-Attach, the shared-drive trap
most EBS volumes attach to one instance at a time; Multi-Attach allows up to 16.
  • The constraint: only available on Provisioned IOPS SSD (io1 and io2), not gp2 or gp3.
  • The application-level warning: two servers plugged into the same disk don't automatically know how to share it. You need a clustered filesystem (like GFS2) or an application that does its own distributed locking; EBS doesn't do it for you. That's what corrupted the data in the scenario.
2Volume manager and filesystem, ext4 vs. XFS
  • ext4: very reliable and efficient with directories of millions of small files; great for web servers with many small images or logs.
  • XFS: built for performance and large files; excels at parallel I/O, with several CPU cores writing to the same disk without locking up.
3Filesystem block size
  • Default 4 KB: a 1 KB file still uses 4 KB. Fine for small files, but a lot of metadata ("paperwork") for large ones. On x86 Linux, ext4 and XFS blocks are normally limited to the 4 KB memory page size (XFS supports larger blocks only on recent kernels), so in practice you tune the database's page size and the filesystem's extent or stripe settings instead.
  • Large I/O units (16 or 64 KB): less paperwork for the CPU. 64 KB is faster for large sequential workloads like a data warehouse, but if the database writes 4 KB pages (like standard PostgreSQL), a 16 KB block size causes write amplification (WAF, write amplification factor): the disk does more work than needed.
4Mount options
  • noatime: Linux records file access times. The default, relatime, already limits this to about once a day per file; noatime removes the remaining access-time writes, which is a small but free saving for databases.
apiVersion: storage.k8s.io/v1kind: StorageClassmetadata:  name: db-xfsprovisioner: ebs.csi.aws.comvolumeBindingMode: WaitForFirstConsumermountOptions:- noatimeparameters:  type: gp3  csi.storage.k8s.io/fstype: xfs
- **`data=writeback` (ext4 journaling):** only metadata is journaled, so data may reach the disk after the metadata pointing to it. It's faster, but after a crash a file can contain stale or garbage blocks. Most production databases keep the default `data=ordered` and rely on their own write-ahead log plus `fsync`.

The EBS CSI driver

Scenario. A developer creates a PVC for a new database and, a few seconds later, a formatted disk appears inside the pod. They want to know what happened in between: who called AWS, who formatted the disk, and why databases often bypass the Linux page cache entirely.

What the picture shows. Direct I/O, then the EBS CSI driver and the five-step volume attachment flow.

1Direct I/O (O_DIRECT)
  • The normal path: app → Linux page cache (RAM) → filesystem → disk.
  • The problem: databases already keep their own RAM cache (the buffer pool), so caching the same data again in the page cache wastes memory and CPU.
  • The solution: O_DIRECT lets the database talk to the filesystem and disk directly. MySQL/InnoDB (innodb_flush_method=O_DIRECT) and Oracle use it; PostgreSQL still relies on the page cache by default (direct I/O is only experimental there).
2The CSI driver
the EBS CSI driver translates between Kubernetes and AWS, turning a YAML request (a PVC) into real disk operations. It has two parts that live in different places.
  • Controller pods: a Deployment on worker nodes (on EKS the control plane is AWS-managed). They call the AWS API: CreateVolume for new disks, plus attaching volumes to EC2 instances and taking snapshots.
  • Node pods: a DaemonSet with one pod per worker node. Once AWS has attached a disk, the node pod formats it (XFS or ext4) and mounts it so the pod can see it.
3Volume attachment flow
  • 1. The request: you create a PVC.
  • 2. The provisioner: the CSI controller sees it and calls the EC2 API to create an EBS volume.
  • 3. The attachment: once the scheduler knows which node the pod will run on, the controller calls AttachVolume for that instance.
  • 4. The formatting: the CSI node pod on that instance sees the new device (for example /dev/nvme1n1) and formats it if it has no filesystem yet.
  • 5. The mount: the node pod mounts the disk on the host, and it is mapped into the running container.
4Next
a critical optimization for multi-AZ clusters, handling WaitForFirstConsumer.

VPC CNI architecture and ENI limits

Scenario. A team running many small pods on t3.medium nodes notices that new pods stay Pending once a node has 17 of them, even though CPU and memory are mostly free. They don't understand why a pod count, not resources, is the limit.

What the picture shows. The core architecture of the AWS VPC CNI and where the per-node pod limit comes from.

1VPC CNI plugin (the aws-node DaemonSet), core architecture
  • L-IPAM (local IP address manager): runs on each node, keeps a warm pool of IP addresses and manages the lifecycle of network interfaces (ENIs).
  • ipamd (IP management daemon): talks to the EC2 API to add and remove ENIs and IPs, and updates the node's routing.
  • CNI plugin binary: called by the kubelet whenever a pod is created; it sets up the pod's network namespace and the veth pair that connects it to the host.
2ENI and IP management
  • Primary ENI (eth0): permanent; it holds the node's own identity.
  • Secondary ENIs: added and removed as demand changes, each providing more IPs for pods.
3Limits
set by the instance type, because every pod needs a real VPC IP. A t3.medium allows 3 ENIs × (6 IPs − 1 primary) + 2 = 17 pods. That's the scenario's answer.

Warm pools and prefix delegation

Scenario. Pods on a busy node take several seconds longer to start during traffic bursts, while they wait for an IP address. Meanwhile, another subnet is running out of IP addresses altogether. The team wants to tune how many IPs each node keeps ready, and how to fit many more pods per node.

What the picture shows. Tuning the warm pool, and two advanced IP strategies.

1Warm pool configuration
  • WARM_ENI_TARGET, extra ENIs kept ready (aggressive): always keeps a number of completely empty ENIs attached, with all their IPs already allocated. Best for big, sudden bursts: when one ENI fills up, the next pod jumps onto the warm one instantly.
  • WARM_IP_TARGET, extra IPs kept ready (balanced): keeps a set number of free individual IPs instead of whole ENIs. With 5 pods and a target of 5, the node holds 10 IPs; when a 6th pod starts, the CNI requests 1 more to keep the buffer at 5.
  • MINIMUM_IP_TARGET, a baseline (conservative): a floor on the total number of IPs, however many pods are running. Set to 10 with 0 pods, the node still has 10 IPs; at 12 pods this setting stops mattering and WARM_IP_TARGET takes over.
kubectl set env daemonset aws-node -n kube-system \  WARM_IP_TARGET=5 MINIMUM_IP_TARGET=10
2IP allocation strategies
  • Prefix delegation (advanced): assigns /28 blocks (16 IPs) instead of single secondary IPs. If you hit the per-instance limit often, you don't need a bigger, pricier instance; an m5.large goes from 29 to 110 pods.

- **Custom networking (`ENIConfig`):** puts pod IPs in a dedicated secondary subnet, which solves IP exhaustion in specific AZs.
3Wiring inside the node
pod A's eth0 → veth pair → host network namespace.

Packet paths

Scenario. A developer asks whether pod-to-pod traffic on EKS goes through an overlay network or a tunnel, and why calls between pods on the same node are so much faster than calls to pods on other nodes.

What the picture shows. Detailed packet flows for the two pod-to-pod cases.

1Pod-to-pod, same node
  • Path: pod A → host namespace → pod B's veth.
  • Routing: the host kernel has a /32 route pointing at the target pod's veth.
  • Speed: plain L2/L3 switching inside the node, with microsecond latency.
2Pod-to-pod, across nodes
  • Path: pod A → host namespace → node 1's primary ENI → VPC → node 2's ENI → host namespace → pod B's veth.
  • VPC routing: the native VPC fabric routes the traffic directly to node 2's ENI, with no encapsulation or overlay, because pod IPs are real VPC addresses.

kube-proxy: iptables vs. IPVS

Scenario. A cluster grows to over 2,000 Services, and the team notices that new connections take longer, CPU on each node rises, and some connections are dropped at peak. They're still running kube-proxy in its default iptables mode.

What the picture shows. Service networking with kube-proxy: iptables mode vs. IPVS mode.

1iptables mode
  • Linear search: for each new packet, the kernel reads the rule list from top to bottom until it finds a match, so more Services means slower lookups.
  • Random-probability NAT: to balance traffic it uses a statistics module; with 3 pods, the first is picked with 33% probability, the second with 50% of the remainder, and so on.
  • conntrack: relies heavily on the Linux connection-tracking table to remember where packets go. If that table fills up, the node starts dropping connections.
  • Use it when: the cluster is small to medium (under about 500 Services) and you want the simplest setup.
2IPVS mode
  • Hash-table based: Services are stored in a hash table, so lookup is nearly instant whether there are 10 or 10,000 (O(1)). High performance beyond about 1,000 Services.
  • Real load-balancing algorithms: Round Robin (RR), Least Connection (LC), Destination Hashing (DH) and more.
  • Use it when: you have thousands of Services and rule updates are slow. Note that IPVS mode was deprecated in Kubernetes 1.35; the recommended replacement is the nftables mode (stable since 1.33), which also scales well.
Going deeper3 points

For LLM backends, round-robin is the wrong algorithm, whichever kube-proxy mode delivers it:

  • requests vary hugely in cost;
  • a replica that already holds a conversation's KV cache can skip most of the prefill work;
  • LoRA adapters mean one endpoint serves several models.

The Gateway API Inference Extension adds an InferencePool and an endpoint picker that chooses a pod by queue length, KV-cache contents or loaded adapter, and can shed low-priority requests when the pool is saturated.

conntrack: the connection ledger

Scenario. A busy node starts dropping new connections at random, and the kernel log shows nf_conntrack: table full, dropping packet. The pods themselves look healthy. The team needs to understand what this table is and why it filled up.

What the picture shows. conntrack, the kernel's connection ledger.

1What it is
the stateful memory of the Linux networking stack. Without it, the network would be "forgetful" and most modern traffic would break.
2How it works
it keeps a notebook entry such as "I just sent a packet from pod A to database X; if a packet comes back from X, give it to pod A."
3Timeouts
every entry has a time-to-live. Each packet on the connection resets the timer; if no packets arrive, it counts down and the entry is deleted.
4Why the table fills
the table has a fixed size (nf_conntrack_max, which kube-proxy sets from the CPU count). Every connection holds an entry until it times out; the kernel default for an idle established TCP connection is 5 days, which kube-proxy lowers to 1 day. A node with very many short-lived or abandoned connections can still fill the table. That's the scenario.
5Solution
raise nf_conntrack_max (through kube-proxy's conntrack.maxPerCore setting) and shorten timeouts for idle and closing connections, so stale entries are cleared sooner.

Security groups for pods and network policies

Scenario. A payment service must, for PCI compliance, be protected by an AWS security group of its own, not only by Kubernetes rules. But all pods on a node normally share the node's security group. Separately, the team wrote NetworkPolicies and discovered they weren't being enforced at all.

What the picture shows. Security groups for pods, network policies, and why IPVS still needs conntrack.

1IPVS still uses conntrack
IPVS picks the target pod with a fast hash table, but it still has to rewrite the destination IP (NAT), so it still uses conntrack, just much more efficiently than iptables mode.
2Security groups for pods (SGP)
treats a pod as a first-class AWS citizen with its own firewall rules, instead of sharing the node's security group. It allows isolation with standard AWS security group rules, not only Kubernetes NetworkPolicies.
3How it works, trunk and branch ENIs
standard EKS networking hands pods secondary IPs from the node's ENI; SGP switches to a trunking model.
  • The trunk ENI (aws-k8s-trunk-eni): a special "master" interface attached to the node.
  • The branch ENI (aws-k8s-branch-eni): one per pod that needs its own security group, a physical-to-virtual mapping designed for isolation.
  • The connection: each branch ENI is plugged into the trunk ENI.
  • The security: the security group is applied to the branch ENI. Since that ENI belongs to one pod, the pod gets its own firewall.
apiVersion: vpcresources.k8s.aws/v1beta1kind: SecurityGroupPolicymetadata:  name: payments-sg  namespace: paymentsspec:  podSelector:    matchLabels:      app: payment-service  securityGroups:    groupIds: ["sg-0123456789abcdef0"]
- **Density cost:** the trunk ENI uses one of the instance's ENI slots, so fewer regular pods fit on the node.
4When to avoid trunking
stay with normal networking unless a compliance rule (like PCI-DSS) requires AWS-level firewalls. For most AI and web workloads, NetworkPolicies with Calico or Cilium are faster and don't reduce pod density.
5Network policies
a NetworkPolicy is a specification without an implementation. The original VPC CNI only handled routing (giving pods IPs and moving packets) and didn't read your rules, which is why the scenario's policies did nothing.
  • Calico: enforces policies through iptables or eBPF while the VPC CNI keeps doing the routing; a security guard on top of the CNI's roads.
  • Requirement: VPC CNI 1.14+ now enforces policies natively with eBPF; Calico or Cilium are still the choice for advanced rules.

The packet's journey through netfilter

Scenario. An engineer debugging a Service wonders where the "magic" actually happens: a pod sends traffic to a virtual Service IP that no machine owns, yet it reaches a real pod, and the reply finds its way back. Which part of Linux does that?

What the picture shows. The kernel's Netfilter gates and where conntrack sits, the machinery kube-proxy programs.

1Netfilter
a subsystem built into the Linux kernel. Its hooks are the "gates": fixed points in the networking stack where the kernel pauses to ask "does anyone have a rule for this packet?" They exist even without Kubernetes; on a fresh server they're just empty.
2conntrack (nf_conntrack)
a kernel module that keeps the state table, tracking every connection through the machine, on a laptop, a web server or a Kubernetes node.
3What kube-proxy adds
it writes the instructions, using iptables or nftables: "when a packet hits PREROUTING with this Service IP as its destination, pick a pod and rewrite the address (DNAT)."
4The packet journey through three gates (chains)
  • PREROUTING, the entry gate: the first stop. DNAT happens here, changing the Service IP to a pod IP before routing. It's the most important chain in Kubernetes because it does Service translation.
  • FORWARD, the hallway: used only for packets passing through (outside world to pod, or pod to pod). Once the destination is a pod IP, the packet enters here. It's for filtering, and it's where network policies usually live.
  • POSTROUTING, the exit gate: the last stop before the network card. SNAT / masquerade happens here: a pod's private IP (say 192.168.1.5) can't receive replies from the internet, so the node's primary private IP is stamped over it, and a NAT gateway or public IP handles the internet hop.
5Where conntrack sits in the gates
  • At the entry (PREROUTING): DNAT asks conntrack "have I seen this conversation?" If yes (a reply packet), conntrack rewrites the addresses itself without walking the rules again. If no (a new packet), it creates a new entry.
  • At the exit (POSTROUTING): conntrack records the return address (the node's IP) so it knows exactly which pod gets the answer when it comes back.

the high-level intent you write in YAML ("pod A may talk to pod B"). On its own it does nothing; it's just a record in the Kubernetes database.

22. The translator, Calico
Calico is the controller on every node, watching the Kubernetes API. When it sees a new NetworkPolicy, it works out what this node must allow or block, and translates the YAML into something the kernel understands.
33. The enforcement, iptables (the rulebook)

Calico vs. Cilium

Scenario. As the cluster grows to thousands of pods, the team notices that iptables rule updates take longer and per-packet CPU cost rises. They wonder whether to switch from Calico to Cilium, and what Cilium's kubeProxyReplacement setting actually changes.

What the picture shows. Calico vs. Cilium, and Cilium's three kube-proxy modes.

1Calico (the common EKS choice)
  • Policy-only mode: it leaves IP management to AWS and only handles security rules.
  • How it works: it reads pod labels (for example role: frontend) and translates them into iptables rules on the fly. A packet arriving through the AWS ENI hits Calico's iptables chain first; if allowed, it passes to the pod.
  • The heavy lifting: "allow frontend to backend" means finding every role: frontend pod and every role: backend pod, so 10 of each needs rules for every IP combination.
2Cilium (the eBPF specialist)
  • eBPF: instead of iptables chains, it injects tiny, fast programs directly into the kernel.
  • Efficiency: the eBPF program sees the packet the moment it touches the network card and makes an instant allow/deny decision, instead of walking a rule list.
  • Identity-aware: it understands identities, not just IPs; it knows pod A is the "payment service" and can stop it talking to anything but the database.
3Three ways to process packets, compared
iptables walks a long list of if/then rules; IPVS uses a hash table but fixed kernel logic; Cilium runs custom compiled code at the network card's front door, with its own eBPF hash maps. It can even catch packets at the XDP layer, before the kernel allocates a packet buffer (sk_buff), much earlier than IPVS.
4Cilium's three modes (Helm setting kubeProxyReplacement)
  • Disabled (false): Cilium acts as a traditional CNI, giving pods IPs and enforcing policies, while kube-proxy keeps handling Services with iptables or IPVS. You still pay the "iptables tax" on Service traffic.
  • Partial / hybrid (partial, older releases): Cilium handles ClusterIP (internal pod-to-pod) traffic with eBPF but leaves NodePort or LoadBalancer traffic to kube-proxy. Current Cilium versions accept only true or false and switch these pieces with individual settings instead.
  • Full (true, formerly strict): Cilium takes over every Service type (ClusterIP, NodePort, LoadBalancer, ExternalIPs) with eBPF hash tables, and you can delete the kube-proxy DaemonSet. It also enables Direct Server Return (DSR): replies go straight from the pod to the client instead of back through the load-balancing node, saving a hop and keeping the client's IP.

What runs on a worker node

Scenario. A pod is stuck in ContainerCreating with a "failed to set up sandbox network" error. To debug it, the on-call engineer needs a clear picture of which components on the worker node run, in which order, when a pod starts and gets its network.

What the picture shows. The components on a worker node and the numbered steps that start a pod and connect it to the network.

1Step 1, kubelet → container runtime
the kubelet talks to the runtime through the CRI (Container Runtime Interface), a standard API that hides which runtime is underneath (containerd or CRI-O). It uses it to start, stop and monitor containers.
2Step 2, CRI → container runtime
the runtime creates the containers.
3Step 3, runtime → CNI
the CNI (Container Network Interface) is an open API that lets Kubernetes use any compatible plug-in, such as Cilium, Calico or the Amazon VPC CNI. When the kubelet asks the runtime for a pod sandbox, the runtime creates the network namespace and calls the CNI plug-in to wire it up (the diagram draws this arrow from the kubelet). A failure here is exactly the scenario's error.
4Step 4, CNI → IPAM
the plug-in asks IP address management (IPAM) for the pod's IP.
5Step 5, CNI → kernel
the plug-in programs the Linux kernel, through iptables or eBPF, for packet filtering and traffic handling.
6Step 6, kube-proxy → kernel
kube-proxy also uses iptables to manage Service traffic on the node.

Network optimization levers

Scenario. A high-traffic cluster shows rising network latency and DNS timeouts as it grows. The team lists the network optimizations available to them: hardware NIC sharing, eBPF, a different kube-proxy mode, CoreDNS scaling and EC2 placement.

What the picture shows. A mind map of network optimizations, branch by branch.

1SR-IOV (Single Root I/O Virtualization)
splits one physical NIC (the physical function) into several virtual functions. Each VM or container gets a dedicated, isolated path straight to the hardware, and packet processing is offloaded to the NIC, cutting CPU overhead.
2eBPF (extended Berkeley Packet Filter)
runs programs in the kernel for network observability, fine-grained security, load balancing and monitoring.
3kube-proxy
keeps the network rules that send Service traffic to the right backend pod.
  • Default: uses iptables to intercept and redirect traffic, which becomes a bottleneck in large clusters.
  • IPVS mode: an in-memory hash table for Service-to-pod routing that scales much better.
4CoreDNS scaling
DNS is central to service discovery, so autoscale CoreDNS (for example with the cluster proportional autoscaler) and run a DNS caching agent on every node (NodeLocal DNSCache) to reduce load and latency.
5Network latency, EC2 placement groups
place nodes physically close to reduce latency between them.

Standard vs. SR-IOV vs. RDMA

Scenario. A distributed training job spends more time waiting for gradients to arrive from other GPUs than computing. Even with fast instance networking, every packet still passes through software layers and the CPU. The team wants to understand which layers are in the way.

What the picture shows. Three generations of the data path between two GPU servers, from slowest to fastest.

1Standard path
data goes through several software layers, the host hypervisor and a software virtual switch. It's CPU-intensive and adds latency at every hop.
2SR-IOV path
bypasses the slow hypervisor and software switch, giving data a direct hardware path. But the standard TCP/IP stack is still there, so the CPU still has to process every packet.
3RDMA transfer
GPU memory on one physical server is copied directly to GPU memory on the other, without involving the operating system or CPU on either side. This is the path distributed training needs (see the next section for how EFA provides it on AWS).
Going deeper7 points
  • For GPU collectives, NCCL is the library doing the all-reduce and all-gather.
  • Across nodes it should run over RDMA (InfiniBand or RoCE, with GPUDirect RDMA moving data straight between GPU memories).
  • On Kubernetes that often means setting NCCL_SOCKET_IFNAME and making sure pods can find each other by name.

  • In a synchronized job the slowest node sets everyone's pace, so one congested link shows up as a fleet-wide slowdown.

  • Training stresses this path even more than inference.

  • With sharded data parallelism (PyTorch FSDP2), every layer's forward and backward pass gathers weight shards from all GPUs, which adds up to many GB per second of steady traffic.
  • A fine-tuning job that fits in a few GPUs can still end up network-bound if those GPUs sit on different nodes.

Latency and EFA

Scenario. A team moves its multi-node training to EC2 instances with EFA, but NCCL still runs over plain TCP and nothing gets faster. The hardware supports RDMA; Kubernetes just doesn't know about it yet.

What the picture shows. Two levers for faster GPU-to-GPU networking on AWS.

1Network latency, EC2 placement groups
keep the training nodes physically close together.
2Throughput enhancement, EFA (Elastic Fabric Adapter)
uses RDMA to move data directly between the memory of two nodes, across the network, without the OS or CPU. CPU use for the copy is close to zero (zero-copy), and EFA works with NCCL for GPU communication.
3Making Kubernetes see EFA, step 1
install aws-efa-k8s-device-plugin, so nodes advertise EFA devices as a resource.

  • Disaggregated LLM serving pushes this further.

Three tickets arrive in one morning: "pods stuck Pending", "service unreachable" and "everything is slow when calling external APIs". This deep dive is the runbook for all three.

IP exhaustion

Scenario. After a successful product launch, new pods across the cluster are stuck in Pending or ContainerCreating. CPU and memory are fine, but the subnets have run out of free IP addresses. The team needs to find the cause and pick a fix that doesn't require rebuilding the cluster.

What the picture shows. Runbook 1: IP exhaustion, pods stuck because there are no IPs left.

1Check the source of truth, the VPC CNI logs
the aws-node pod manages IPs, and its logs show exactly why the call to AWS failed.
2Fix 1, increase subnet size (the "hard" fix)
you can't expand an existing subnet; you must create a new, larger one and migrate nodes to it. Best for small clusters that were accidentally started on a tiny /27 or /26.
3Fix 2, prefix delegation (the "efficiency" fix)
run kubectl set env daemonset aws-node -n kube-system ENABLE_PREFIX_DELEGATION=true. Pro: pod density jumps immediately (for example 17 → 110 pods on a t3.medium). Con: it can fragment a subnet that's already messy.
4Fix 3, custom networking (the "separation" fix)
attach a secondary CIDR to the VPC (for example 100.64.0.0/16) and point the CNI at it with an ENIConfig resource, so pods get IPs from a separate, much larger range.

Service connectivity drops

Scenario. A pod can't reach a Service: requests hang or are refused, while other pods work fine. The network team insists the VPC is healthy. The on-call engineer needs a step-by-step way to find where the "pipe" between the two pods is broken.

What the picture shows. Runbook 2: connectivity drops.

1What it means
the path between the source pod and the destination pod is broken somewhere. Services are virtual, so the failure is usually in the translation layer (the switchboard) or in the target list (the endpoints). Common root causes are conntrack table exhaustion and MTU mismatches.
2Step A, are there any targets?
If the Service's ENDPOINTS is <none>, it's a dead end, usually because of a typo in the Service's selector.
3Step B, are the rules programmed?
Check whether the node knows how to handle the traffic: you should see rules jumping to a KUBE-SVC chain. If they're missing, kube-proxy has probably crashed or is stuck.
4What to check
  • Selector mismatch (the typo): the Service doesn't select any pods.
  • Failing readiness probes: Kubernetes doesn't send traffic to pods that aren't Ready.
  • NetworkPolicy blocking: an installed NetworkPolicy acts as a silent firewall.
  • kube-proxy failure: if kube-proxy dies, the iptables or IPVS rules on that node stop updating.

DNS issues

Scenario. Users report that "the network is down": pods can't reach other services or external APIs. But ping by IP works fine. Meanwhile, an AI service calling an external LLM API is mysteriously slow on every request. Both problems turn out to be DNS.

What the picture shows. Runbook 3: DNS issues, where pods can't find the address of who they want to talk to.

1Why DNS looks like a network outage
the network is fine, but names don't resolve. In Kubernetes this almost always points to CoreDNS, the cluster's internal phonebook: usually 2 pods that answer queries such as "what is the IP of my-service.default.svc.cluster.local?"
2Troubleshooting 1, Corefile misconfiguration
the Corefile (CoreDNS's config, stored in a ConfigMap) can break the phonebook.
  • Looping: if DNS plugins forward to each other, CoreDNS detects a loop and shuts down. Example: a pod asks for google.com; CoreDNS forwards using forward . /etc/resolv.conf; the node's resolv.conf points to a local stub (127.0.0.1 or 127.0.0.53), which sends the query back, and the request spirals.
  • Upstream failure: that forward line normally sends external names to the VPC DNS (169.254.169.253). If the node's resolv.conf is broken, nothing outside the cluster resolves.
  • Memory limits: in large clusters CoreDNS can run out of RAM indexing every Service, get OOM-killed, and all DNS stops.
3Troubleshooting 2, Service selector mismatch
a "DNS" problem that's really a labelling problem. nslookup my-service returns a valid ClusterIP, but connecting gives "connection refused", because the Service's selector (for example app: web) matches no running pods. The DNS record exists but leads to a dead end.
4Troubleshooting 3, the ndots problem (the performance killer)
every pod's /etc/resolv.conf has ndots:5 by default, which says "a name with fewer than 5 dots might be a local service, so try the cluster search paths first". Resolving google.com tries google.com.default.svc.cluster.local, google.com.svc.cluster.local, google.com.cluster.local (all fail) and finally google.com. One lookup becomes at least 4 queries (more with the node's own search domains, and doubled when IPv6 AAAA lookups are made too), which hammers CoreDNS and adds latency to every call to S3, RDS or an LLM API. That's the slow AI service in the scenario.
5How to fix ndots
  • Method A, the fully qualified trick: write google.com. with a trailing dot.
  • Method B, change the pod spec: lower ndots in dnsConfig for deployments that talk to the outside world a lot.

Latency by distance

Scenario. A team splits a chatty microservice across three Availability Zones for resilience, and its p99 latency doubles. They want to know how much latency each kind of network hop actually adds.

What the picture shows. Three levels of distance between two pods, and what each one costs.

1Same-node communication (under 100 µs)
pod A and pod B on one EC2 node talk through their virtual interfaces (eth0) and the Linux kernel. There's no physical network at all; data moves through the node's memory and CPU.
2Cross-node, same AZ (0.2–1 ms)
traffic leaves node 1 through its ENI, passes a top-of-rack switch and enters node 2's ENI. Low latency: physical switches and cables, but still inside one data centre building.
3Cross-AZ (1–5 ms)
traffic crosses the inter-AZ backbone (high-speed fibre) between geographically separate data centres. Significant latency, including encryption and distance, plus a data-transfer charge. That's why the scenario's p99 doubled.

Bandwidth and MTU

Scenario. A data-processing pod on a t3.medium is far slower than expected, even though its CPU is barely used. Separately, a team that moved to an overlay CNI kept the pod MTU at 9001, and now large responses hang while small requests work.

What the picture shows. Two hidden network ceilings: instance bandwidth and MTU.

1Throughput is capped by the instance type
however strong your CPUs are, the node can only move as much data as its virtual hardware allows. Examples: t3.medium up to 5 Gbps, m5.large up to 10 Gbps, m5.4xlarge up to 10 Gbps, m5.12xlarge a steady 12 Gbps and m5.24xlarge 25 Gbps. (The diagram lists 25 Gbps for m5.12xlarge; that figure belongs to m5.24xlarge.)
2Burstable vs. guaranteed
"up to" means burstable; sustained transfers fall back to a much lower baseline. That explains the slow t3.medium in the scenario.
3MTU, how data is chopped up
  • VPC default, 9001 bytes (jumbo frames): works inside a VPC (and over Direct Connect if configured). The VPC CNI already gives pods MTU 9001 by default; AWS_VPC_ENI_MTU changes it.
kubectl set env daemonset aws-node -n kube-system AWS_VPC_ENI_MTU=9001
- **Internet, 1500 bytes:** the standard Ethernet size. Traffic leaving the VPC through an internet or NAT gateway is limited to 1500, and path-MTU discovery normally shrinks packets automatically, unless something blocks the ICMP "fragmentation needed" messages.
- **The mismatch:** an overlay (VXLAN) adds about 50 bytes of headers, so on a 9001 network the pod MTU must be about 8951. Leave it at 9001 and full-size packets no longer fit: small requests work, large responses hang. That's the second part of the scenario.

Finance asks why the EKS bill grows faster than traffic. This deep dive is my checklist, split into compute, network and storage.

Compute

Scenario. The CFO asks why the EKS bill grew 40% this quarter while traffic grew only 10%. The platform team suspects oversized pod requests, too much On-Demand capacity and expensive GPUs that sit idle, and needs a structured plan to bring compute costs down.

What the picture shows. Compute cost optimization, as a mind map.

1Right-sizing resources with tools
Kubecost, Goldilocks, StormForge and KRR compare what pods request with what they actually use, and recommend smaller requests.
2Compute capacity options
  • EC2 On-Demand: full price, no commitment.
  • EC2 Reserved Instances: standard RIs for the biggest discount on a fixed instance type, convertible RIs if you might change families.
  • Savings Plans: an alternative to RIs that is flexible across instance sizes and types.
  • EC2 Spot instances: large discounts with a 2-minute interruption notice. Good candidates are batch processing, stateless web servers and CI/CD pipelines. Karpenter can fall back to On-Demand when Spot isn't available, and Ray, Kubeflow and Horovod can use Spot for distributed training by relying on checkpointing and interruption handling.
  • AWS Graviton instances: ARM-based, cheaper for the same work.
  • AWS Fargate: serverless compute, paying per pod.
  • EC2 Capacity Blocks for ML: reserve accelerated (GPU) capacity for a fixed window, delivered in UltraClusters.
3EndpointSlices
route traffic between services to the nearest pod in the same AZ, which also cuts cross-AZ charges (see the next section).
Going deeper3 points

For GPU nodes, the biggest waste is idle GPUs, not instance pricing:

  • Bin-pack (MostAllocated with GPUs weighted highest), so empty nodes can be removed.
  • Share GPUs that small models use only partly: MIG for isolation, time slicing for dev and bursty inference.
  • Quantize where quality allows: a 70B model needs about 280 GB at fp32 but about 35 GB at 4-bit.

Weigh every consolidation against the checkpoint-and-restart it forces on training jobs.

Networking

Scenario. The cost report shows that data transfer is now the third-largest line item. Services talk across Availability Zones all day, nodes pull large images over the internet, and traffic to S3 goes through a NAT gateway. None of it was designed with cost in mind.

What the picture shows. Network cost optimization, by branch.

1Pod-to-pod communication
traffic across AZs costs money.
  • Topology-aware routing: kube-proxy directs traffic based on the zone it came from, keeping it in the same AZ when possible.
apiVersion: v1kind: Servicemetadata:  name: backendspec:  selector: {app: backend}  ports:  - port: 80    targetPort: 8080  trafficDistribution: PreferClose     # stay in the caller's zone when possible

2Load balancer configuration, IP mode
pods are registered directly as ELB targets, skipping the extra hop (and possible cross-AZ hop) through a node.
apiVersion: v1kind: Servicemetadata:  name: web  annotations:    service.beta.kubernetes.io/aws-load-balancer-type: external    service.beta.kubernetes.io/aws-load-balancer-nlb-target-type: ipspec:  type: LoadBalancer  selector: {app: web}  ports:  - port: 443    targetPort: 8443
3Data transfer
  • VPC endpoints: reach AWS services (S3, ECR, DynamoDB and others) directly, without the public internet or a NAT gateway.
  • VPC peering and Transit Gateway: connect VPCs privately. Peering has no per-GB processing charge; Transit Gateway adds one but scales better across many VPCs.
4Image pull
  • ECR endpoint: pull images over a VPC endpoint.
  • Pre-cache images in a custom AMI: large images are already on the node at boot, saving transfer cost and start-up time.
Going deeper6 points
  • Model images are a special case: tens or hundreds of GB.
  • Layered OCI images let ten fine-tuned variants share one cached copy of the base model on a node.
  • Pre-pulling or prefetching images is what keeps scale-up times predictable (see Getting model weights into pods).

Startup time is a cost too: a slow-starting replica means paying for extra warm capacity. For model servers:

  • Use imagePullPolicy: IfNotPresent, and pin images by version or digest instead of latest.
  • Avoid downloading weights at startup (PVCs or OCI images instead).
  • Use a parallel loader (Run:ai Model Streamer, Tensorizer).

Together these cut a replica's time-to-ready from minutes to tens of seconds.

Storage

Scenario. Storage costs keep creeping up: old EBS volumes from deleted PVCs are still around, logs are kept forever, every volume is gp2, and container images are several gigabytes each. The team wants a checklist of storage savings that won't hurt performance.

What the picture shows. Storage cost optimization, by branch.

1Pod ephemeral storage
doesn't outlive the pod, which makes it a cheap, efficient scratch space.
2Mountpoint for S3 CSI driver
exposes S3 as a file system (not block storage), supporting S3 Standard and S3 Express One Zone. Cheap for large read-mostly data.

(see StorageClass, PV and PVC):
  • gp3 over gp2: gp3 is about 20% cheaper.
  • Reclaim policy: Delete or Retain. Delete is cheaper because volumes don't pile up; use Retain in production. Orphaned volumes from Retain are the scenario's hidden cost.
4IOPS considerations
  • High performance, io2 Block Express: expensive, but up to 256,000 IOPS.

5Container image size
multi-stage builds keep images small.
6Data retention policy
set retention for CloudWatch Logs and Elasticsearch so old data expires.
Going deeper4 points
  • For model weights, the storage choice is a cost-vs-speed trade-off.
  • A shared ReadOnlyMany PersistentVolume stores one copy for all replicas but pays network latency on every read.

  • OCI images sit in between (see Getting model weights into pods).

What we protect

Scenario. Before launching an AI serving platform, the CISO asks a simple question: "Where can an attacker get in?" The team realizes a container is not a single thing to secure; it's a stack of layers, each with its own risks.

What the picture shows. The layers of a container, each of which carries risk.

1Container risks
come from every layer you ship and run:

  • Application code: your own code.

  • Host: the node the container runs on.

2The takeaway
securing a container means securing all of these, which is what the rest of this deep dive walks through, layer by layer.

The build pipeline

Scenario. An auditor asks the platform team to prove that a production image hasn't been tampered with, contains no known critical vulnerabilities, holds no hard-coded secrets and runs on a hardened node. The team needs controls at every stage from build to runtime.

What the picture shows. Securing the container lifecycle, stage by stage.

1Build
a trusted, minimal base image to shrink the attack surface (Alpine Linux, distroless or scratch); immutable tags; multi-stage builds; and DockerSlim to minimize image size.
2Test
automated security testing in CI/CD, for example with Snyk.
3Store
sign images with Docker Content Trust or Cosign.
4Encrypt
keep secrets out of images, using Kubernetes Secrets with HashiCorp Vault, AWS KMS, AWS IAM and the Secrets Store CSI driver.
5Scan
scan images for vulnerabilities with Amazon Inspector or Trivy.
6Deploy
verify signatures with AWS Signer and enforce rules with policy-as-code (OPA Gatekeeper).
7Monitor, the runtime environment
run nodes in private subnets, disable SSH, block the instance metadata service (IMDS) from pods, encrypt all storage and use a hardened AMI.
Going deeper4 points
  • Model files belong in the supply chain too.
  • Classic PyTorch .pt files use Python pickle, which can execute arbitrary code when loaded.
  • Safetensors stores only tensors and can't, which makes it the safer default for weights from outside the organization.
  • Signing and scanning model images works the same way as for application images.

Runtime security

Scenario. A security scan finds that several production pods run as root, with privileged mode and every Linux capability enabled, "because it was easier". Nobody would notice if one of them started behaving maliciously. The team needs runtime guardrails and detection.

What the picture shows. Runtime security: limit what a container can do, then watch what it does.

1Least privilege
give each container only what it needs for normal operation.
2Restrict root and privileged access
set this in the container's securityContext.
3Drop all unnecessary Linux capabilities.

enforce them with Pod Security Admission, and isolate workloads in namespaces with different levels (privileged, baseline, restricted).
5Monitor the runtime
the goal is to detect and prevent malicious activity inside containers and on worker nodes. Tools include Falco (deployed as a DaemonSet to watch containers) and Prisma Cloud container security.

Network security

Scenario. A compromised pod in one namespace scans the whole cluster and reaches an internal database, because nothing blocks pod-to-pod traffic. The security team wants a zero-trust network, protection at the edges and visibility into what talks to what.

1Network segmentation and isolation
namespaces together with NetworkPolicies, following zero-trust principles (deny by default, allow explicitly).
2Securing pod-to-pod communication

3Securing external connections

7Security monitoring
a central monitoring tool or SIEM helps spot suspicious access and respond quickly.

Before the deep dives, here's the workload most of them end up hosting: a large language model behind an API. This post covers what it takes to go from a model on a laptop to a production endpoint on Kubernetes.

From a Python script to a model server

Loading a model with the Transformers library and calling it works for a demo, but it is one process, one hard-coded prompt and no API. Wrapping it in FastAPI is the next step, and at that point you are rebuilding a model server: a runtime that loads the model, exposes it over REST or gRPC, and is tuned for throughput and latency. Memory is the first constraint: at 16-bit precision, a 7B model's weights alone take about 14–15 GB and a 70B model's about 140 GB, plus room for the KV cache.

The serving runtimes worth knowing

  • vLLM: the most widely used open-source server, with an OpenAI-compatible API, PagedAttention and continuous batching.
  • TGI (Hugging Face): similar, and can switch backends (CUDA, TensorRT-LLM, llama.cpp, AWS Neuron for Trainium/Inferentia).
  • llama.cpp: for laptops and edge devices; it is where the GGUF format comes from.
  • NVIDIA NIM: curated, pre-optimized images per model family, with a model cache on a PersistentVolume.
  • SGLang: strong at reusing the KV cache across requests that share a prompt prefix (agents, multi-turn chats).

A platform team doesn't need to master every inference optimization (quantization, speculative decoding, FlashAttention). Pick an actively maintained server and watch the settings that change the topology: multi-GPU and multi-node serving make the deployment stateful and need extra coordination.

Deploying by hand

A plain Deployment for vLLM already needs a GPU limit, a toleration for tainted GPU nodes, a Secret for gated models, and a PVC as a model cache so a restart doesn't re-download 100 GB. Multiply that by every model and the case for a controller is obvious. → See The NVIDIA device plugin.

KServe: separate the runtime from the model

KServe splits ServingRuntime (the model server image and defaults, owned by the platform team) from InferenceService (one model, owned by data scientists), so runtime upgrades and model releases can move at their own pace.

  • Standard mode creates plain Deployments, which is the usual choice for large LLMs.
  • Knative mode adds scale-to-zero.
  • ModelMesh packs many small models together.

The newer LLMInferenceService adds KV-cache-aware routing, disaggregated serving and tensor/data/expert parallelism for 7B–405B models. → See Workloads and node tiers and Placement, autoscaling and cost.

Ray Serve and KubeRay

Ray defines its own cluster (a head node plus workers) and its own scheduling, and KubeRay's RayService maps it onto Kubernetes. Python teams get full control from code, at the cost of a second orchestration layer on top of Kubernetes. → See How a Pod finds its scheduler.

Getting model weights into pods

LLM weights range from a few GB (Mistral 7B is about 14 GB) to nearly a terabyte (Llama 3.1 405B is about 800 GB at 16-bit). Moving that much data into pods quickly and cheaply is a storage, network and startup-time problem. This post covers the formats, the registries, and four ways to get weights to a model server.

What's in a model file

  • Weight-only formats (PyTorch .pt/.pth, TensorFlow checkpoints, NumPy) need the original code to rebuild the network.
  • "Mostly self-contained" formats carry more:
    • Safetensors is safe to load (unlike pickle, it can't execute code), memory-maps tensors without copies, and shards large models into many files with an index.
    • GGUF packs quantized weights plus tokenizer data into one file for llama.cpp and vLLM.
    • ONNX carries the graph but not the tokenizer.

None is fully self-contained yet. config.json and tokenizer.json still travel alongside the weights. → See The build pipeline.

Model registries

A registry tracks versions, metadata, lineage, stage (experiment → staging → production) and access, but usually stores only pointers to the weights in object storage. Common choices are the Hugging Face Hub (public), MLflow, the Kubeflow Model Registry, and plain OCI registries.

Why OCI images fit models well

Container images are layered, cached per node and content-addressed. Put a base model in one layer and LoRA adapters on top, and ten fine-tuned variants share one copy of the base on each node. Pick the access method per tier. Use PersistentVolumes in development for easy updates and OCI images in production for speed and repeatability. Always measure time from pod scheduled to model ready, because that is where large-model autoscaling breaks down.

Running LLMs in production

  1. 1. Choose the model with numbers, not vibes
  2. 2. Compress, then evaluate again
  3. 3. Do the memory math
  4. 4. Tune the runtime for the workload
  5. 5. Benchmark like production
  6. 6. Scale, start fast, route smartly

Getting a model to answer once is easy. Keeping it fast, affordable and correct under real traffic is the hard part. These are the steps I'd go through before calling an LLM deployment production-ready.

1. Choose the model with numbers, not vibes

Two models of the same size can behave very differently on your task. Use public leaderboards (MMLU for knowledge, HellaSwag for commonsense, TruthfulQA for truthfulness) only to build a shortlist, because published scores can't be verified. Then re-run the evaluations yourself with tools like EleutherAI's lm-evaluation-harness. Benchmarks take minutes to hours, so run them as asynchronous jobs in a pipeline. TrustyAI wraps the harness as an LMEvalJob custom resource. Add task-specific checks too: Ragas for RAG quality and garak for security probing.

2. Compress, then evaluate again

An 8B model at 16 bits needs about 16 GB for its weights alone. Quantization to FP8 or INT8 roughly halves that and can raise throughput substantially on the same GPU (up to about 2× on GPUs with native FP8), often keeping 99% or more of the accuracy. Two conditions apply: the runtime must have native kernels for the quantized format (vLLM does), and the result must be re-evaluated, because a bad quantization can quietly ruin quality. Pre-quantized, validated models are the low-risk option.

3. Do the memory math

A rough GPU memory budget for one replica:

  • the weights (parameters × bytes per parameter);
  • about 1 GB of runtime overhead;
  • activations, which grow quickly with sequence length;
  • the output tensor;
  • everything left goes to the KV cache.

Example: an 8B fp16 model without grouped-query attention, with a 2k context and batch size 1, needs about 17 GB; at batch size 10 it needs about 28 GB. Models with grouped-query attention (like Llama 3) need several times less KV cache. vLLM prints this breakdown at startup, and warns when it has to evict KV-cache blocks because it ran out of room.

4. Tune the runtime for the workload

vLLM's defaults are good. The settings that matter most are:

  • gpu-memory-utilization: how much of the GPU it may claim.
  • max-model-len: caps the context, which sizes the KV cache. Don't cut it below what RAG prompts need.
  • max-num-seqs: batch size, a trade between throughput and memory.
  • tensor-parallel-size / pipeline-parallel-size: more GPUs, and more KV-cache room.
  • cpu-offload-gb: lets bigger models fit, but is too slow for production.

5. Benchmark like production

Use LLM-aware load generators that report TTFT and inter-token latency: GuideLLM, inference-perf (from Kubernetes WG-Serving), MLPerf Inference, or vLLM's benchmark scripts. Run them in CI on the same GPU type and count as production, store the results, and use them for capacity planning, rate limits and autoscaling targets.

6. Scale, start fast, route smartly

Autoscaling, startup time and routing each have their own section with the details:

  • Placement, autoscaling and cost: scale on token metrics with KEDA.
  • Networking (cost): from minutes to seconds to ready.
  • kube-proxy: iptables vs. IPVS: KV-cache- and LoRA-aware routing.
  • Latency and EFA: disaggregated serving.

At the largest scale, disaggregated serving (llm-d, NVIDIA Dynamo) splits prefill (compute-heavy, drives time to first token) from decode (memory-heavy, drives time per token). The two pools scale separately and share a distributed KV cache (LMCache, NIXL) over very fast networks.

Observing LLMs

  1. 1. The usual stack still applies
  2. 2. Measure tokens, not requests
  3. 3. Fast isn't enough: watch quality
  4. 4. Responsible AI

Kubernetes heals crashed pods, but it can't tell you that answers got slow, or wrong. LLM observability starts with the usual logs, metrics and traces, then switches to tokens instead of requests, and finally adds a layer most services never need: checking that the answers are any good.

1. The usual stack still applies

  • Logs go to stdout and need a log store such as Loki. A vLLM startup log already tells you a lot: version and arguments, the model config, how much GPU memory the weights took and how much is left for the KV cache, and the routes it serves.
  • Metrics are scraped in Prometheus/OpenMetrics format. KServe has annotations that turn scraping on for a model, plus an aggregator for multi-container pods.
  • Traces: vLLM emits OpenTelemetry spans (send them to Jaeger, for example), and OpenTelemetry is defining semantic conventions specifically for generative AI.

2. Measure tokens, not requests

The GPU does the work, so CPU usage says little. The two phases also behave differently: prefill is compute-heavy and decode is memory-heavy. The core metrics:

  • Time to first token (TTFT): what a chat user feels as "waiting". It reflects the prefill phase.
  • Time per output token (TPOT), or inter-token latency: reading speed. About 4–5 tokens per second keeps up with a human reader.
  • Throughput: prompt and generated tokens per second.
  • End-to-end latency per request.
  • Queue: num_requests_waiting and num_requests_running, the earliest sign of overload.

Turn them into SLIs and SLOs (for example "TPOT under 0.3 s for 99.9% of requests"), alert on them with PrometheusRules, and link a runbook. GPU health comes from vendor exporters (NVIDIA DCGM, AMD, Intel) alongside these. → See What every scheduler relies on.

3. Fast isn't enough: watch quality

A model rarely crashes on bad input. It answers confidently and wrongly, which is a hallucination. Benchmarks before deployment help, but in production I'd sample 1–10% of responses into an asynchronous LLM-as-a-judge pipeline. Its quality scores are exported as Prometheus metrics, so they can be trended and alerted on like latency. For narrow tasks a cheap metric can work instead, such as ROUGE overlap for summaries. Judges work best with specific questions ("Does this reply include personal data?") rather than "Is this answer good?"

4. Responsible AI

Explanations are expensive to compute, so capture requests and responses with an inference logger and explain only the disputed cases later. Bias can appear at runtime through data drift even if training was clean, so monitor fairness metrics on protected attributes continuously (KServe with TrustyAI can do this). Input and output guardrails are covered in Identity and model endpoints.

Customizing models: prompts, RAG, LoRA and training jobs

  1. 1. Try the cheap options first
  2. 2. Full fine-tuning vs. LoRA
  3. 3. Running tuning jobs on Kubernetes

Almost nobody trains an LLM from scratch. Pre-training takes thousands of GPUs for weeks, and alignment then teaches the base model to follow instructions safely. What platform teams actually run is post-training: adapting an already aligned model to their domain. The first question is whether you need to train at all.

1. Try the cheap options first

  • Prompt engineering: a system prompt that sets the scenario, the role and the boundaries. It is not a security control, because prompt injection can bypass it.
  • Context engineering and RAG: fetch relevant documents at request time and put them in the prompt. Update the knowledge base in minutes, with no training job.

Training becomes worth it when large, slow-changing knowledge would otherwise ride along in every prompt. Long contexts cost GPU memory on every request, so a bank might bake lending and risk knowledge into a model and keep RAG for fresh facts. A small, specialized model (8–16B parameters), possibly distilled from a large one, can match a big general model at a fraction of the serving cost.

2. Full fine-tuning vs. LoRA

  • Full fine-tuning updates every weight. It needs hundreds of thousands of labelled examples and many GPUs, risks "catastrophic forgetting", and produces a separate model that needs its own GPUs to serve.
  • Parameter-efficient fine-tuning (PEFT), mainly LoRA, freezes the base model and trains small adapter matrices, often under 1% of the parameters. It needs only 100–1,000 examples and finishes in hours. At serving time one base model can host many adapters (vLLM loads them side by side), which is why LoRA-aware routing matters. QLoRA adds quantization to cut training memory further.

Hugging Face TRL's SFTTrainer handles both, and newer methods (DPO, GRPO, reward modelling) show up as multi-step pipelines with several GPU components.

3. Running tuning jobs on Kubernetes

  • Even small fine-tunes usually span several GPUs and often several nodes. Sharded training (PyTorch FSDP2) moves weights between GPUs on every layer, so the network becomes the bottleneck.
  • Kubeflow Trainer separates the roles:
    • the platform team defines TrainingRuntimes (PyTorch, DeepSpeed, MLX, MPI);
    • data scientists submit TrainJobs from Python, where their function is serialized into the job, so there is no image rebuild per experiment;
    • the controller turns them into a JobSet.
  • Alternatives: Ray/KubeRay (RayJob on a RayCluster; code ships in images or repos), DeepSpeed as a training library, and Unsloth for fast single-GPU fine-tuning.
  • Checkpoints must go to persistent storage, and multi-node jobs need gang scheduling and quota.

RAG and agents on Kubernetes

  1. 1. Two application shapes
  2. 2. RAG, end to end
  3. 3. Agents

In a real product, the model is one service among many. The application owns the logic: it fetches context, calls tools, keeps state, and uses the LLM for generation and reasoning. This post maps those pieces onto Kubernetes.

1. Two application shapes

  • Chat apps: gateway → orchestrator → LLM → state store, all within one synchronous request. Latency rules, so everything stays warm, and browser-based sign-in (OAuth2) is easy.
  • Backend AI services: triggered by events (an order placed, a payment made) or by a schedule. They need idempotency, buffering and eventual consistency more than raw speed, and can scale to zero.

Around these sit nightly CronJobs, always-on agent loops (single-replica Deployments that watch a feed, like a controller with an LLM inside), and multi-step automations that run as Jobs. → See Workloads and node tiers and Thundering herd.

2. RAG, end to end

Ingestion (offline, as Jobs or CronJobs):

  1. parse documents (e.g. with Docling);
  2. split them into chunks by sentence, paragraph or heading;
  3. embed each chunk;
  4. upsert the vectors with metadata (source, section, version) into a vector database.

Query time: embed the question with the same embedding model, run a similarity search (optionally hybrid with keyword ranking), optionally rerank, build the prompt from a template, generate, then add citations and run guardrails before returning.

Component Kubernetes shape
Vector DB (Milvus, Weaviate, Qdrant, pgvector) StatefulSet + PVC, snapshots, NetworkPolicy
Embedding model Deployment, sidecar, or in-process
Orchestrator Deployment + Service/Ingress; prompts in ConfigMaps, keys in Secrets
Reranker Optional Deployment for high-stakes queries
Ingestion CronJob / Job with limits so it can't starve users

If you change the embedding model, you must re-embed every document. → See Workloads, node groups and scheduling.

3. Agents

An agent wraps the model in a loop: perceive → think → act (call a tool) → observe → reflect → remember. ReAct is the classic form.

  • Tools run either on the client (the model asks your code to run a function) or on the server, increasingly through MCP servers.
  • Frameworks: client-side libraries (LangChain, LangGraph, CrewAI) or server-side runtimes behind an API (the OpenAI-style Responses API, Llama Stack, vLLM's emerging support). Server-side runtimes handle state and human approval steps for you.
  • On Kubernetes: operators like Kagent declare agents, tools and A2A skills as custom resources. Agents are Deployments, tools are Services, memory lives in StatefulSets, and heavy work goes to Jobs.
  • Multi-agent systems use either a coordinator or peer-to-peer messaging, plus shared memory. Plan for failures (sagas) and require human approval for risky actions.

Running agents in production

  1. 1. MCP: one protocol for tools
  2. 2. Whose identity reaches the backend?
  3. 3. A2A: agents talking to agents
  4. 4. Memory and long-running work

Agents bring three problems that plain microservices don't: who they act as, how they talk to each other, and what they remember. The protocols are still young, but the operational patterns below hold regardless of framework.

1. MCP: one protocol for tools

The Model Context Protocol replaces one-off integrations between every agent and every tool (M×N) with a single protocol (M+N). Tools describe themselves with a name, a description and a JSON schema, and calls use JSON-RPC. On Kubernetes:

  • Run each MCP server as a Deployment behind a Service, keep session state external, and scale with HPA.
  • Use a sidecar only when the tool must share the agent's files.
  • Group related tools into a single server to keep the number of services manageable. Watch the total tool count, because agents choose less well from very long lists.

MCP now sits under the Linux Foundation's Agentic AI Foundation, together with goose and AGENTS.md.

2. Whose identity reaches the backend?

Pattern How Strength Watch out for
Token passthrough Agent forwards the user's OAuth token Existing per-user RBAC and audit just work Token expiry on long tasks, broad scopes, stolen tokens
ServiceAccount delegation Pod ServiceAccount tokens; validate with TokenReview, authorize with SubjectAccessReview on app-specific "virtual" resources No extra identity provider inside the cluster Workload identity only, no user
Token exchange (RFC 8693) Identity provider issues a token with the user in sub and the agent in act User and agent visible; composite policies Run and cache an exchange service

Production setups combine them: SPIFFE mTLS between workloads, the user's identity in a header or exchanged token, and a policy engine (OPA) that requires both. MCP gateways (Envoy AI Gateway, agentgateway, ContextForge and others) centralize authentication, authorization, rate limits and audit, at the cost of an extra hop that must be highly available. → See Identity and model endpoints.

3. A2A: agents talking to agents

MCP connects an agent to tools. The Agent-to-Agent (A2A) protocol connects an agent to other agents, which can reason and take time. It has three building blocks:

  • an agent card that advertises skills and formats, like an OpenAPI spec;
  • a task lifecycle (submitted → working, possibly pausing at input-required → completed, failed or canceled) that outlives any single HTTP call;
  • streamed artifacts for partial results.

Each agent is its own Deployment, with NetworkPolicies between them and circuit breakers in the mesh. Treat the agent card as a contract you check in CI, and alert on tasks stuck in the working state.

4. Memory and long-running work

  • In-memory state is fine for development and lost on the first restart or scale-out.
  • Short-term memory (the session) belongs in a key-value store such as Redis, run as a StatefulSet with a TTL per session, so any replica can serve the next turn.
  • Long-term memory (preferences, audit trail, cross-session analytics) belongs in a database, written asynchronously.
  • Long-running agents checkpoint after each major step to a PVC and run as Jobs with restartPolicy: OnFailure, so an evicted pod resumes where it left off. The checkpoints double as a debugging trail.

Start with plain Deployments, Services, RBAC and StatefulSets, and add meshes, gateways and operators only when a real limitation shows up.

Appendix A: Running a second scheduler on a managed cluster

  1. What the example contains
  2. Checking that it works
  3. Things to keep in mind

This appendix is a complete, ready-to-apply example for one specific situation: you want different scheduling rules for some of your workloads (different plugin weights, or bin-packing instead of spreading), but you're on a managed cluster such as EKS, GKE or AKS, where you can't change the default scheduler's configuration.

The answer is to run a second scheduler next to the default one. It's the same official kube-scheduler program, deployed by you as an ordinary Deployment, with its own KubeSchedulerConfiguration. Pods choose it by setting schedulerName; every other pod keeps using the default scheduler. For background, see Phase 1: filtering (the note on KubeSchedulerConfiguration) and Built-in plugins, and what a second scheduler changes.

What the example contains

  1. Identity: a my-scheduler ServiceAccount, bound to the built-in system:kube-scheduler and system:volume-scheduler ClusterRoles (so it can read pods and nodes, bind pods and handle volumes), plus a role to read the API server's authentication settings. You reuse the standard permissions instead of writing your own.
  2. Configuration: a ConfigMap holding the scheduler's KubeSchedulerConfiguration. It defines one profile, affinity-first-scheduler, that weights InterPodAffinity at 100 and ImageLocality at 1, and switches NodeResourcesFit to MostAllocated (bin-packing). Leader election is on.
  3. The scheduler itself: a Deployment with 2 replicas in kube-system. Thanks to leader election only one replica is active at a time; the other takes over if it fails. It runs the official kube-scheduler image with --config pointing at the mounted ConfigMap.
  4. A workload that opts in: an api Deployment that sets schedulerName: affinity-first-scheduler.

The highlighted lines are the ones that matter. Set the image tag to your cluster's Kubernetes version (v1.35.0 is a placeholder).

Checking that it works

  • The scheduler is running: kubectl -n kube-system get pods -l component=my-scheduler shows two pods, and kubectl -n kube-system get lease affinity-first-scheduler shows which one is the leader.
  • Your pods used it: kubectl get events --field-selector reason=Scheduled lists each placement with the scheduler that made it, so the api pods show affinity-first-scheduler.
  • A pod stays Pending with no events at all: no scheduler has picked it up. Usually the schedulerName has a typo, or the scheduler's pods aren't running.

Things to keep in mind

  • Two schedulers don't coordinate. If both place pods on the same nodes, they can occasionally pick the same free space at the same time, and the kubelet rejects the second pod. For workloads that matter, give this scheduler its own node pool (taints and node labels).
  • Keep it in step with the cluster. Upgrade the image when you upgrade the cluster, so the scheduler understands the same API fields as the control plane.
  • Autoscalers simulate the default scheduler. Check that Cluster Autoscaler or Karpenter handles pods with a custom schedulerName the way you expect.
