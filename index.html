Reading notes: job scheduling for AI training on Kubernetes

These are my notes on the "Job Scheduling Optimization" chapter of Generative AI on Kubernetes, in my own words, with links to the sections of my diagrams where each idea shows up. The chapter's starting point is that a distributed training job is not a normal Kubernetes app: it holds scarce GPUs for days, its pods only work as a group, it moves huge amounts of data between nodes, and many teams want the same hardware. Each of those facts needs its own scheduling answer.

1. The default scheduler is built for web apps

kube-scheduler decides one pod at a time: filter out nodes that can't run the pod, score the rest, bind to the winner, and hand off to the kubelet. Its default scoring spreads pods out for availability. For GPU training, the chapter argues for the opposite: bin-packing with the MostAllocated strategy of the NodeResourcesFit plugin, with GPUs weighted more heavily than CPU and memory. Packing leaves whole nodes empty, so the autoscaler can remove them. The trade-off is that one node failure hits more jobs, so a common setup offers two scheduler profiles: bin-packing for experiments and spreading for critical work. → See Phase 1: filtering, Phase 2: scoring and Score × weight.

2. Placement decays, so something has to re-pack

Good initial placement doesn't last: jobs finish at different times and the cluster fragments. The descheduler periodically evicts pods so the scheduler can place them again. Its strategy must match the scheduler's: HighNodeUtilization goes with MostAllocated, and LowNodeUtilization goes with LeastAllocated. Mixing them up creates an eviction loop. For training, every eviction costs a checkpoint and restart, so PodDisruptionBudgets, quiet maintenance windows and namespace exclusions matter. → See Scheduler thrashing, which is the same kind of feedback loop between controllers.

3. Gang scheduling: all or nothing

PyTorch workers meet at a rendezvous barrier before training starts. If 7 of 8 workers are placed and the 8th can't be, the 7 sit on GPUs doing nothing, and that capacity is wasted. Gang scheduling (coscheduling) keeps the whole group pending until all of it fits. The options sit at different layers:

  • the coscheduling plugin (PodGroup with minMember and a timeout) inside kube-scheduler,
  • Kueue, which decides at the job level whether a job may start,
  • KAI Scheduler and Volcano, which replace the scheduler.

A native Workload API for gang scheduling is also being worked on upstream (KEP-4671). → See Gang scheduling and Volcano vs. Kueue.

4. Topology: the right GPUs, not just enough GPUs

Where the GPUs sit matters as much as how many there are. NVLink inside a node is far faster than InfiniBand between nodes, which is far faster than plain Ethernet. Tensor parallelism and FSDP talk on every forward and backward pass, so they suffer most from a bad placement. The approaches differ:

  • Kueue models topology as ResourceFlavors (node labels such as interconnect and fabric) and lists the premium flavor first, with a fallback.
  • KAI reads GPU topology directly from the NVIDIA stack.
  • Volcano scores nodes using topology labels.

Inside a node, the kubelet's Topology Manager keeps a pod's CPUs and GPUs on the same NUMA node. → See Topology bin-packing, Hardware-aware scheduling and NUMA and CPU pinning.

5. Quota as a service, not a wall

Plain ResourceQuotas are hard walls per namespace: one team's idle GPUs can't help another team's queue. The chapter's "GPU as a Service" model uses Kueue in two tiers:

  • ClusterQueues hold nominal quota and borrowing limits.
  • LocalQueues are what teams submit to.
  • A cohort lets teams borrow each other's idle quota, and the owner reclaims it by preemption when it needs it back.

WorkloadPriorityClasses decide admission order, and fair sharing favors teams that have used less recently. Flavor order and fungibility (TryNextFlavor) decide which hardware a job gets. Priority decides who goes first. These are separate decisions. → See Queueing and fair sharing and Priority, preemption and QoS.

6. How the pieces fit

The recommended stack layers the tools by job: Kueue for admission and quota on top, a gang-aware or topology-aware scheduler underneath (kube-scheduler with plugins, KAI or Volcano), and a workload API such as PyTorchJob/TrainJob, JobSet or LeaderWorkerSet that groups the pods. That is also the stack I would start from on EKS.

Every pod goes through the same decision: filter out the nodes that can't run it, score the ones that can, and bind it to the best one. This tab follows that decision step by step.

Phase 1: filtering

Scenario. A pod stays Pending with 0/12 nodes are available. The developer says there's "plenty of room".

What the picture shows. Filtering drops any node that fails a hard rule: requested CPU or memory doesn't fit, nodeSelector doesn't match, an untolerated taint, required affinity or anti-affinity, or a hostPort that's already taken. "Plenty of room" usually means free usage, but the scheduler only counts requests. The event message lists which rule removed how many nodes.

From the chapter: filter, score and bind decide placement one pod at a time. That's fine for web apps, but it's the root of the gang problem for training jobs (see Gang scheduling).

Filtering outcomes at a glance

Scenario. On-call needs a quick way to map an event message to a cause.

What the picture shows. A cheat sheet linking each kind of constraint (resources, taints, affinity, selector) to its consequence, and a funnel from all nodes to the feasible set that goes on to scoring.

Phase 2: scoring plugins

Scenario. Three nodes pass filtering. Why does the pod always land on the same one?

What the picture shows. Each plugin gives every node a 0–100 score: LeastAllocated (the spreader), BalancedAllocation (keeps CPU and memory even), ImageLocality (image already cached) and preferred affinity. The node with the highest weighted total wins. Preferred affinity is the only one you set directly in the pod spec.

From the chapter: for GPU training, switch NodeResourcesFit to MostAllocated (bin-packing) and give nvidia.com/gpu a higher weight than CPU and memory. Packing frees whole nodes for the autoscaler to remove. Offer it as a separate scheduler profile so critical workloads can still spread.

Score × weight

Scenario. You need to explain on a whiteboard how "points" become a decision.

What the picture shows. final score = Σ (plugin score × plugin weight). The score measures quality ("how empty is this node?") and the weight measures importance. Worked examples: LeastAllocated gives 80 for a node that's 80% free, and ImageLocality rises with how much of the image is cached.

When affinity loses to ImageLocality

Scenario. A pod has a soft affinity to run near its cache service, but keeps landing on a node far away that happens to have its big image.

What the picture shows. A weak affinity match times weight 2 can still lose to a strong image-cache score. There are two ways to fix it: make the rule required, which moves it into filtering, or raise the plugin weight cluster-wide in KubeSchedulerConfiguration.

A worked example

Scenario. Two candidate nodes and three plugins. Which one wins?

What the picture shows. Node 2 wins on the total even though Node 1 wins one plugin. The picture uses equal weights to keep the arithmetic simple. In the real default profile, affinity has weight 2, which only makes Node 2's lead bigger.

The weight field in your YAML

Scenario. A teammate asks what weight: 80 in a pod spec actually does.

What the picture shows. weight (1–100) only exists on preferred rules and tunes scoring. Required rules have no weight because they're filters. A high weight means "a strong suggestion", and a low one means "nice to have".

Scheduler score vs. OOM score

Scenario. "The scheduler gave this node a low score, so why did my important pod get killed there?"

What the picture shows. The scheduler's score only matters at placement time. Under memory pressure, the kubelet evicts pods by how far they're over their memory request (then by priority), and the kernel's OOM killer uses oom_score. These are separate systems that use separate numbers (see Memory: who gets killed).

The default scheduler places pods one at a time and knows nothing about jobs, teams or GPU topology. This tab covers the problems that pushed the ecosystem toward Kueue, Volcano, KAI and YuniKorn, and how to choose between them.

How a Pod finds its scheduler

Scenario. On EKS, some pods run on Fargate and others on EC2 nodes, and nobody set schedulerName by hand.

What the picture shows. Every scheduler watches for unscheduled pods whose schedulerName matches its own. For Fargate, a mutating webhook sets fargate-scheduler on pods that match a Fargate profile. The table compares the default scheduler with an ML-oriented one.

Gang scheduling

Scenario. An 8-worker PyTorch job only fits 6 workers. Six GPUs sit allocated, and nothing trains.

What the picture shows. Pod-by-pod placement vs. all-or-nothing placement. A gang scheduler keeps every pod pending until the whole group fits.

From the chapter: the reason is PyTorch's rendezvous barrier: no worker starts until all of them have joined. The chapter's options: the coscheduling plugin (a PodGroup with minMember and a timeout), Kueue's job-level admission, or a replacement scheduler (KAI, Volcano). Upstream Kubernetes is also designing a native Workload API for this.

Topology bin-packing

Scenario. Two pods that exchange tensors constantly end up on different nodes, and step time doubles.

What the picture shows. Spreading vs. packing onto one NVLink-connected node. For tightly coupled training, the default spreader is the wrong instinct.

From the chapter: NVLink inside a node is far faster than InfiniBand across nodes, and Ethernet is slower still. Tensor parallelism and FSDP talk on every forward and backward pass, so placement matters most for them. A job may rightly wait in the queue rather than start on badly connected GPUs.

Queueing and fair sharing

Scenario. One researcher submits 100 jobs on Friday night, and nobody else gets a GPU all weekend.

What the picture shows. A greedy FIFO vs. queues with priorities and fair share, and preemption of low-priority research work when inference needs capacity.

From the chapter: this is the "GPU as a Service" model. In Kueue, a ClusterQueue holds nominal quota and borrowing limits, teams submit to LocalQueues, and a cohort lends idle quota and takes it back by preemption. Fair sharing favors teams that have used less recently.

Hardware-aware scheduling

Scenario. An FP8 training job lands on older GPUs and runs at a fraction of the expected speed.

What the picture shows. A scheduler that matches workloads to hardware features (RDMA/InfiniBand switch, newer GPU generation) instead of only counting GPUs. Labels and selectors work to start with, and become painful across many hardware generations.

From the chapter: Kueue expresses this as ResourceFlavors chosen by node labels (interconnect, fabric, GPU type). The premium flavor is listed first, with a fallback flavor and TryNextFlavor. KAI reads GPU topology directly from the NVIDIA stack.

Volcano vs. Kueue

Scenario. The team has to pick one, and the debate keeps going in circles.

What the picture shows. Volcano replaces the scheduler and understands dependencies between task types (start workers only once the master is placed). Kueue sits in front of the default scheduler and manages quota, borrowing and fairness between teams.

From the chapter: the common production answer is "both layers": Kueue for admission and quota on top of a gang- or topology-aware scheduler, with a workload API (PyTorchJob/TrainJob, JobSet, LeaderWorkerSet) that groups the pods.

The landscape

Scenario. Leadership asks for one page that compares the options.

What the picture shows. KAI, Volcano and YuniKorn compared on gang scheduling, GPU bin-packing, fair sharing and hardware awareness, plus a market matrix that includes Kueue and Armada.

What every scheduler relies on

Scenario. Whichever scheduler we choose, how does it know what hardware a node has?

What the picture shows. The NVIDIA device plugin advertises nvidia.com/gpu, and topology operators label nodes with InfiniBand/RDMA details. Every scheduler reads these labels and resources from the API server.

One cluster runs a latency-critical web API next to cost-driven batch jobs. This tab follows the isolation stack from node tiers down to CPU, memory, network and disk.

Workloads and node tiers

Scenario. Every evening the batch wave arrives and the API's p99 latency jumps above 100 ms.

What the picture shows. Web services are latency-sensitive and need stability, while batch is retry-capable and opportunistic. Each gets its own tier: on-demand, tainted nodes for web (with placeholder pods for headroom), diversified Spot capacity for batch, and a shared, untainted tier for utilization.

Priority, preemption and QoS

Scenario. The cluster is full when a traffic spike hits. Who gets evicted, and who decides?

What the picture shows. Two different mechanisms. PriorityClasses are the scheduler's tool, applied cluster-wide (web-critical preempts, batch-low never does). QoS (Guaranteed > Burstable > BestEffort) is the kubelet's tool, applied on one node under resource pressure.

From the chapter: Kueue adds a job-level layer on top. WorkloadPriorityClasses decide admission order, and preemption can reclaim borrowed quota. Which hardware a job gets (flavor) and who goes first (priority) are separate decisions.

Placement, autoscaling and cost

Scenario. Batch costs are climbing even though most nodes look half empty.

What the picture shows. Affinity for web, anti-affinity for batch, and requests and limits per workload type. Autoscaling uses HPA for web (fast up, slow down) and Karpenter for batch (diversified Spot, consolidation). Spot interruptions are handled by checkpointing, and the key alerts are pending pods, queue depth and p99.

From the chapter: bin-packing (MostAllocated) plus a matching descheduler policy (HighNodeUtilization) keeps nodes full, so empty ones can be removed. Never combine it with the opposite policy, or the two will fight each other.

CPU: shares and throttling

Scenario. The API's average latency looks fine, but p99 spikes every few seconds.

What the picture shows. Requests become CPU shares, which split the CPU under contention. Limits become a quota per 100 ms window. A multi-threaded pod can use up its quota early in the window and then freeze until the next one, which is where the p99 jitter comes from.

Kernel vs. Kubernetes

Scenario. "Why do requests matter if the kernel shares CPU fairly anyway?"

What the picture shows. Kubernetes sets the policy, the kubelet translates it into cgroups, and the kernel enforces it. The one thing the kernel can't do is stop a node from being overpacked. Only the scheduler's request accounting does that.

Memory: who gets killed

Scenario. A node runs out of memory. Which pod dies first, and why that one?

What the picture shows. Memory can't be compressed: the OOM killer runs at container or node level. QoS sets oom_score_adj (BestEffort 1000, Guaranteed -997, Burstable in between, depending on its memory request). Among Burstable pods, the kubelet evicts the one furthest over its request first.

Network: the unmanaged resource

Scenario. A backup pod starts a 10 Gbps transfer and the API on the same node starts dropping connections, yet CPU and memory look perfect.

What the picture shows. Kubernetes has no network requests or limits. The fixes are Linux tc shaping, CNI bandwidth annotations, and instance types with separate bandwidth for EBS.

Storage I/O: the other unmanaged resource

Scenario. A log archiver saturates a volume, and the database pod sharing it goes from 1 ms to 200 ms latency.

What the picture shows. EBS throttles per volume, not per pod, and Kubernetes doesn't expose the blkio controller. The symptoms are I/O wait, processes stuck in the D state, and failing liveness probes. The fixes are dedicated volumes per critical pod, EBS-optimized instances, and node-level guardrails.

Tab 04 · 2 sections

From a YAML limit to a kernel quota

  1. Policy maker, translator, enforcer
  2. From a limit to a quota

This tab follows how resources.requests and resources.limits turn into cgroup settings that the Linux CFS scheduler enforces.

Policy maker, translator, enforcer

Scenario. A web pod (request 1 core, limit 2) and a batch pod (request 250m, limit 500m) share a busy node. How much CPU does each get?

What the picture shows. The kubelet writes shares (1024 vs. 256) and quotas into each pod's cgroup. Under contention, CFS splits the CPU 80/20 by shares. When the batch pod hits its quota, it is throttled even if the CPU is otherwise idle.

From a limit to a quota

Scenario. "How can a pod use 200 ms of CPU inside a 100 ms window?"

What the picture shows. quota = limit in cores × 100,000 µs. A 2-core limit gives 200 ms per window because quota is counted across all cores, so two threads can run flat out for the whole window. On cgroup v2 (recent EKS AMIs) the files are cpu.weight and cpu.max, but the model is the same.

These are real incidents written as problem → why → fix, one per section.

Volume attachment limit

Scenario. Database pods 29 and 30 stay Pending on a big node that has plenty of free CPU.

What the picture shows. Nitro instances can attach only about 28 volumes. The fix is to spread stateful pods with anti-affinity or topology spread constraints, so the scheduler stops piling them onto one node.

The stuck volume

Scenario. A node dies, and the database pod crash-loops on its replacement node.

What the picture shows. The EBS volume still appears attached to the dead node, so the new node can't attach it. The quick fix is to force-detach it. The lasting fix is to keep the EBS CSI driver up to date.

Snapshot restored in the wrong AZ

Scenario. A restored database never starts.

What the picture shows. EBS volumes are tied to one AZ. If you restore into the zone your nodes are in, or let WaitForFirstConsumer choose the zone, the volume and the pod end up in the same place.

Force delete and filesystem corruption

Scenario. Someone runs kubectl delete pod --force --grace-period=0 on a database mid-write.

What the picture shows. Never force-delete a database pod unless its node is already gone. To recover, restore the last good snapshot and replay the WAL.

IOPS throttling cascade

Scenario. Latency goes from 1 ms to over 100 ms, the connection pool fills up, and the whole app falls over.

What the picture shows. gp3 gives a 3,000-IOPS baseline. Provision the IOPS you actually need in the StorageClass, and watch IOPS (or BurstBalance on gp2) before you hit the limit.

Cross-AZ transfer costs

Scenario. The Kafka bill's networking line is bigger than its compute line.

What the picture shows. Every replicated message crosses AZs, and each crossing costs money. The fixes are compression (zstd or snappy) and rack-aware reads from replicas in the same AZ.

The page-cache memory trap

Scenario. An ML job that loops over the same dataset gets OOM-killed, but its own memory use looks small.

What the picture shows. Active page cache counts toward the container's working set. Watch container_memory_working_set_bytes, leave headroom between request and limit, and use posix_fadvise(DONTNEED) on data you have finished reading.

Thundering herd

Scenario. 100 batch jobs finish at the same moment, all write to the database, and the web service's queries start failing.

What the picture shows. The batch jobs effectively DDoS your own database. Put a queue (SQS or Kafka) in between with controlled consumers, or add random jitter to the batch jobs as a quick fix.

Scheduler thrashing

Scenario. A traffic spike makes HPA add 50 web pods, which preempt 50 batch pods. The Job controller recreates them, and they get preempted again, over and over.

What the picture shows. A feedback loop between controllers. Changing restartPolicy alone doesn't stop it. The fix is to queue instead of retry: admit batch jobs through Kueue only when capacity exists, give batch preemptionPolicy: Never, and set a Job podFailurePolicy.

From the chapter: the same kind of loop happens when a descheduler's strategy disagrees with the scheduler's scoring. A steadily rising eviction count with no consolidation is the signal.

CPU limit vs. request gap

Scenario. Web latency spikes even though node CPU is only at 60%.

What the picture shows. A batch pod with a 1-core request and an 8-core limit can burst to 8 cores, but the scheduler only reserved 1 core for it. Neighbours see sudden contention. For CPU-heavy batch, set requests close to limits.

Tab 06 · 1 section

How GPUs become schedulable

The NVIDIA device plugin

Scenario. A new GPU node group joins the cluster, but pods that request nvidia.com/gpu: 1 stay Pending.

What the picture shows.

  1. The device plugin runs as a DaemonSet.
  2. It registers with the kubelet, which advertises GPU capacity.
  3. The scheduler can now count GPUs and place the pod.
  4. The kubelet asks the plugin to attach specific devices to the container.

In our setup, the plugin is installed by the EKS Terraform module.

From the chapter: device plugins expose counts, not topology. That's why topology-aware placement needs node labels (or GPU Feature Discovery), Kueue ResourceFlavors, or a scheduler like KAI that reads the GPU fabric. Inside a node, the kubelet's Topology Manager keeps CPUs and GPUs on the same NUMA node.

A SaaS platform hosts standard, premium and regulated tenants on shared EKS. The question running through this tab: if one tenant is compromised, what can it reach?

Tenant classes, soft and hard isolation

Scenario. Sales has just signed a healthcare customer with HIPAA requirements. Can they live next to free-tier tenants?

What the picture shows. Tenants are classified by data sovereignty, compliance, blast radius and SLA. Soft isolation is namespace-based: ResourceQuotas and LimitRanges, default-deny NetworkPolicies, Pod Security Admission restricted, and namespace-scoped service accounts. Hard isolation means dedicated node groups with taints, subnets per tier, or a dedicated cluster for highly regulated tenants.

From the chapter: quota between tenants (who gets the GPUs) is a separate problem from isolation between tenants (who can see what). Kueue's ClusterQueues and cohorts handle the first; the tools on this tab handle the second.

Identity, data, network and observability

Scenario. Tenant A's leaked credentials must not be able to read tenant B's data.

What the picture shows. The tenant boundary is enforced at three layers:

  • Identity: a per-tenant IAM role through IRSA.
  • Data: RDS with IAM auth and row-level security, per-tenant S3 bucket policies and VPC endpoints, and separate ElastiCache by tier.
  • Network: a shared ALB for the standard tier and a dedicated NLB plus PrivateLink for premium tenants.

Logs, metrics and traces all carry tenant labels.

Sandboxed runtimes: gVisor and Kata

Scenario. A premium tenant asks whether a kernel exploit in another tenant's container could reach their workload.

What the picture shows. With standard runC, all containers share the host kernel, so a kernel bug can lead to escape. gVisor puts a user-space kernel in between, and Kata runs each pod in a lightweight VM (similar in spirit to Fargate's Firecracker). You opt in per workload with a RuntimeClass.

Hardening runC: seccomp, AppArmor, user namespaces

Scenario. Most workloads stay on runC. How do we shrink the attack surface without changing runtimes?

What the picture shows.

  • seccomp: an allow-list of the syscalls the app actually needs.
  • AppArmor/SELinux: mandatory access control, for example "nginx may only read /var/www".
  • User-namespace remapping: root inside the container is an unprivileged user on the host.

Control plane security

Scenario. An audit finds the EKS API endpoint is reachable from the internet.

What the picture shows. A private endpoint with VPC endpoint policies, admission webhooks (OPA Gatekeeper or Kyverno) for rules that built-in admission can't express, and audit logs to CloudWatch with tenant context for anomaly detection.

Network isolation and egress

Scenario. A regulated tenant needs encryption between pods and control over what its pods can call on the internet.

What the picture shows. Calico VXLAN overlays per tenant, Cilium's eBPF L7 and DNS-aware policies, and transparent WireGuard/IPsec encryption without a service mesh (or Nitro's hardware encryption in transit). Egress goes through VPC endpoints, or through a tenant-aware egress proxy that knows which pod sent each packet.

A team moves PostgreSQL, Kafka and Cassandra onto EKS next to stateless services. This tab is everything I'd check before trusting that setup in production.

Workloads, node groups and scheduling

Scenario. Spot interruptions keep restarting a database replica that ended up on a Spot node.

What the picture shows. Stateless "cattle" and stateful "pets" get separate node groups: Spot-heavy with Karpenter for stateless, on-demand only and EBS-optimized for stateful. A stateful=true:NoSchedule taint keeps them apart. StatefulSets give ordered startup, stable names and per-pod PVCs, and a PodDisruptionBudget protects quorum.

Storage and StatefulSet mechanics

Scenario. Which volume type, binding mode and reclaim policy should a new database use?

What the picture shows.

  • Volume type: gp3 by default, io2 Block Express for very high IOPS, and EFS only for shared files, never for databases.
  • Binding mode: WaitForFirstConsumer, so the volume is created in the AZ where the pod lands.
  • Reclaim policy: Retain in production, Delete in dev.
  • Updates: partitioned rolling updates, or OnDelete for manual control.

Performance, networking and backup

Scenario. Replication traffic between database nodes adds latency to every commit.

What the picture shows.

  • I/O: local NVMe for scratch data, and EBS metrics to watch.
  • Network: cluster placement groups for "chatty" peers, ENA/SR-IOV, ENA Express (SRD), and ENI trunking for pod density.
  • Backup: Velero for the cluster, plus native consistent dumps to S3.

Spreading across AZs and nodes

Scenario. All three Kafka brokers end up in one AZ, and an AZ outage takes the cluster down.

What the picture shows. Two topologySpreadConstraints: a hard spread across zones (maxSkew 1) and a soft spread across nodes, illustrated with topologyKey and maxSkew examples.

NUMA and CPU pinning

Scenario. A database on an r6i.8xlarge is 15–20% slower than on bare metal, with the same configuration.

What the picture shows. Memory access is local or remote depending on which socket holds the data. When the kernel moves a process between sockets, it loses its cache. Setting the kubelet's cpuManagerPolicy: static and topologyManagerPolicy: single-numa-node keeps a Guaranteed pod's CPUs and memory on one NUMA node.

From the chapter: the same Topology Manager matters for GPU training. Without it, the CPU manager and device manager can hand a pod CPUs from one NUMA node and GPUs from another. The policies range from best-effort to single-numa-node. The strictest gives the best locality but makes scheduling harder.

I/O scheduler tuning

Scenario. The database dashboard shows high I/O wait.

What the picture shows. none for NVMe-backed EBS (the device's own controller already schedules I/O), mq-deadline for mixed workloads, and bfq to share one disk fairly between noisy neighbours.

EBS is AZ-locked: three strategies

Scenario. us-east-1a goes down. What happens to a database whose volume lives there?

What the picture shows. Three strategies:

  1. One StatefulSet per AZ, with the database replicating across zones itself.
  2. Topology-aware provisioning, which is simple, but the pod is stuck if its AZ fails.
  3. Active-passive, with restore from snapshot into another AZ.

How EBS really behaves

Scenario. Large sequential writes hit the IOPS limit much sooner than expected.

What the picture shows. EBS is network-attached, so latency is network round trip plus service time. SSD IOPS are counted in chunks of up to 256 KiB. gp3 has a flat baseline (3,000 IOPS) with no burst credits, while gp2 bursts on credits. Multi-Attach is only for io1/io2 and needs a clustered file system.

File system, mount options and O_DIRECT

Scenario. Tuning a Postgres volume beyond the defaults.

What the picture shows. ext4 vs. XFS (XFS has better parallel I/O), block size and write amplification, noatime, why data=writeback is risky, and O_DIRECT, which skips the page cache so the database's own buffer pool isn't duplicated.

The EBS CSI driver

Scenario. A PVC stays Pending. Which component should we look at?

What the picture shows. The CSI controller (a Deployment on worker nodes) calls the AWS API to create, attach and snapshot volumes. The node plugin (a DaemonSet) formats and mounts them. The picture walks through PVC → create → attach → format → mount, and shows how WaitForFirstConsumer waits for the scheduler's decision.

The PV subsystem end to end

Scenario. Explaining dynamic provisioning to a new teammate in one picture.

What the picture shows. StorageClass ("the brochure"), PVC ("the rental application") and PV ("the apartment"), and the six steps from creating a PVC to the volume being mounted in the pod.

This tab follows a packet from the moment a pod gets its IP, through Services and network policies, down into the kernel's netfilter hooks.

VPC CNI architecture and ENI limits

Scenario. A t3.medium refuses to run an 18th pod, even though it has free CPU.

What the picture shows. The aws-node DaemonSet runs ipamd (which talks to the EC2 API and manages ENIs) and the CNI binary (which sets up the pod's network namespace and veth pair). Pod capacity comes from ENIs × IPs per ENI: 3 × (6 − 1) + 2 = 17 on a t3.medium.

Warm pools and prefix delegation

Scenario. A batch burst launches 200 pods at once, and they wait several seconds for IPs.

What the picture shows. WARM_ENI_TARGET (aggressive), WARM_IP_TARGET (balanced) and MINIMUM_IP_TARGET (a floor) trade IP waste against startup speed. Prefix delegation assigns /28 blocks instead of single IPs, so an m5.large goes from 29 to 110 pods.

Packet paths

Scenario. Is pod-to-pod traffic slower across nodes than within a node, and by how much?

What the picture shows. On the same node, traffic goes veth → host routing table → veth (microseconds). Across nodes, it goes through the primary ENI and native VPC routing with no overlay, then the destination node's ENI and veth.

kube-proxy: iptables vs. IPVS

Scenario. With 5,000 Services, every new connection gets slower.

What the picture shows. iptables mode walks a linear list of rules and picks backends with probabilistic NAT. IPVS uses hash lookups and real load-balancing algorithms (round robin, least connections). Both still rely on conntrack.

conntrack: the connection ledger

Scenario. Under heavy load, a node starts dropping new connections even though CPU is fine.

What the picture shows. conntrack remembers every flow so reply packets find their way back. Entries expire on timeouts. An established TCP connection's default timeout is 5 days, so a busy node can fill the table. A shorter nf_conntrack_tcp_timeout_established is one fix.

Security groups for pods and network policies

Scenario. Compliance requires AWS security groups on the payment pods specifically.

What the picture shows. A trunk ENI and per-pod branch ENIs, each with its own security group. The cost is pod density, so use them only where AWS-level firewalls are required. Kubernetes NetworkPolicies need an engine: the VPC CNI's native one, Calico, or Cilium.

The packet's journey through netfilter

Scenario. "Where exactly does a Service IP get rewritten?"

What the picture shows. PREROUTING (DNAT from Service IP to pod IP), FORWARD (filtering, where policies live) and POSTROUTING (SNAT/masquerade when traffic leaves the VPC), with conntrack consulted at the entry and recorded at the exit.

From NetworkPolicy YAML to kernel rules

Scenario. A NetworkPolicy is applied, but traffic still flows.

What the picture shows. The YAML is only intent. Calico (the translator) turns it into iptables chains at the FORWARD hook (the enforcement). If no engine is running, nothing enforces the policy.

Calico vs. Cilium

Scenario. Choosing a policy engine for a cluster with thousands of pods and frequent label changes.

What the picture shows. Calico's policy-only mode writes iptables rules per IP pair. Cilium uses eBPF and identity-aware policies at tc/XDP, so a packet is checked before the kernel builds its buffer. The kubeProxyReplacement modes run from off to full, with DSR for return traffic.

Node networking and the high-performance path

  1. What runs on a worker node
  2. Network policy limits
  3. Network optimization levers
  4. Standard vs. SR-IOV vs. RDMA
  5. Latency and EFA

This tab covers what happens on a worker node when a pod starts, and the path that large training jobs need: SR-IOV, RDMA and EFA.

What runs on a worker node

Scenario. A new engineer asks what actually happens between "pod scheduled" and "pod has an IP".

What the picture shows.

  1. The kubelet calls the runtime through CRI (containerd or CRI-O).
  2. The runtime calls the CNI plugin (VPC CNI, Calico or Cilium).
  3. The CNI plugin gets an IP from IPAM and programs iptables.
  4. kube-proxy keeps the Service rules in iptables.

Network policy limits

Scenario. Pods must be allowed to call api.anthropic.com and nothing else on the internet.

What the picture shows. Native NetworkPolicies only match IPs, ports, protocols, pods and namespaces. DNS-based rules and cluster-wide policies need Cilium or Calico.

Network optimization levers

Scenario. DNS timeouts and Service latency grow with the size of the cluster.

What the picture shows. SR-IOV (one NIC split into virtual functions), eBPF for observability and policy, IPVS instead of iptables at scale, and CoreDNS with a proportional autoscaler plus a node-local DNS cache.

Standard vs. SR-IOV vs. RDMA

Scenario. GPUs sit idle waiting on the network during gradient synchronization.

What the picture shows. Standard virtualization goes through the hypervisor and a software switch. SR-IOV gives a direct hardware path, but the TCP/IP stack still costs CPU. RDMA copies memory to memory between nodes with near-zero CPU.

From the chapter: all-reduce, all-gather and FSDP traffic grow with model size, so on a large job the network decides the step time. That's why the scheduling side (topology-aware placement) and the network side (RDMA fabrics) have to be designed together.

Latency and EFA

Scenario. Scaling a training job from 2 to 16 nodes makes each step slower.

What the picture shows. Cluster placement groups for latency, and EFA (RDMA with NCCL support) for throughput. On EKS, the aws-efa-k8s-device-plugin advertises EFA interfaces as a schedulable resource, so pods can request them like GPUs.

Tab 11 · 5 sections

Troubleshooting networking

  1. IP exhaustion
  2. Service connectivity drops
  3. DNS issues
  4. Latency by distance
  5. Bandwidth and MTU

Three tickets arrive in one morning: "pods stuck Pending", "service unreachable" and "everything is slow when calling external APIs". This tab is the runbook for all three.

IP exhaustion

Scenario. New pods stay Pending or ContainerCreating with "failed to assign an IP address".

What the picture shows. Start with the aws-node logs. Then pick a fix: a bigger subnet (the hard way), prefix delegation (17 → 110 pods on a t3.medium), or custom networking on a secondary CIDR such as 100.64.0.0/16 through ENIConfig.

Service connectivity drops

Scenario. One service can't reach another by its Service IP.

What the picture shows. Step A: does the Service have endpoints? An empty list usually means a selector typo. Step B: are the iptables or IPVS rules there? Also check readiness probes, NetworkPolicies, and whether kube-proxy is healthy.

DNS issues

Scenario. Calls to external APIs are slow, and CoreDNS CPU usage is high.

What the picture shows. Corefile mistakes and forward loops, CoreDNS running out of memory, Services with no endpoints, and ndots:5: one external lookup becomes several queries through the search domains. Fix it with fully qualified names (a trailing dot) or a lower ndots in dnsConfig.

Latency by distance

Scenario. Why does the same call take 0.1 ms, 1 ms or 5 ms?

What the picture shows. Same node: memory copy only. Same AZ: the top-of-rack switch (0.2–1 ms). Across AZs: the inter-AZ backbone (1–5 ms), plus a data transfer charge.

Bandwidth and MTU

Scenario. Three pods on one node want 12 Gbps together through a 10 Gbps ENI.

What the picture shows. Instance bandwidth caps all pods on a node together ("up to" vs. guaranteed). The VPC supports 9001-byte jumbo frames, but the internet uses 1500, so raising pod MTU helps east-west traffic and breaks internet traffic that has no translation.

Tab 12 · 3 sections

Cost optimization on EKS

  1. Compute
  2. Networking
  3. Storage

Finance asks why the EKS bill grows faster than traffic. This tab is my checklist, split into compute, network and storage.

Compute

Scenario. Half the nodes average 20% CPU, and the GPU bill keeps growing.

What the picture shows. Right-size with Kubecost, Goldilocks, StormForge or KRR. Choose purchase options deliberately: on-demand, Reserved Instances, Savings Plans, Spot (2-minute notice, good for checkpointed training with Ray, Kubeflow or Horovod, with Karpenter falling back to on-demand), Graviton, Fargate, and Capacity Blocks to reserve GPUs for a planned window.

From the chapter: for GPU nodes, packing (MostAllocated with GPUs weighted highest) plus a matching descheduler policy creates empty nodes that the autoscaler can remove. At $10–30 per GPU node-hour, that matters. Weigh it against the cost of the checkpoint-and-restart that every eviction triggers.

Networking

Scenario. The data-transfer line on the bill is surprisingly large.

What the picture shows. Cross-AZ pod traffic costs money, so use topology-aware routing (EndpointSlice hints) and same-AZ provisioning with Karpenter. Use ALB IP mode, VPC endpoints instead of NAT for AWS services, and an ECR endpoint plus pre-cached images in a custom AMI.

Storage

Scenario. Old volumes and logs keep growing after the workloads that wrote them are gone.

What the picture shows. Ephemeral storage for scratch data, Mountpoint for S3 (a file system view of S3, not a block device), gp3 over gp2 (about 20% cheaper), reclaim policies, IOPS tiers (io2 for the hottest data, st1/sc1 for cold), smaller images through multi-stage builds, and log retention policies.

Security asks for one picture of how a model-serving platform is protected before launch. This tab answers it layer by layer.

What we protect

Scenario. Kickoff with the security team: what is in scope?

What the picture shows. The stack from host to containers, dependencies, code, configuration and data, and the two places container risk enters: the build pipeline and the runtime environment.

The build pipeline

Scenario. A base image with a critical CVE almost reaches production.

What the picture shows. Build (minimal or distroless base images, multi-stage builds, immutable tags) → test (Snyk in CI) → store (signing with Cosign or AWS Signer, OPA Gatekeeper) → encrypt (KMS, Vault, Secrets Store CSI) → scan (Inspector, Trivy) → deploy (private subnets, no SSH, IMDS blocked, hardened AMI) → monitor.

Runtime security

Scenario. A container is found running as root with CAP_SYS_ADMIN.

What the picture shows. Least privilege, no root or privileged containers, dropped capabilities in the security context, Pod Security Standards enforced through namespace labels, and runtime detection deployed as a DaemonSet.

Network security

Scenario. A compromised pod tries to scan the rest of the cluster.

What the picture shows. Namespaces plus NetworkPolicies, zero-trust pod-to-pod traffic with a service mesh, WAF and OIDC at ingress and egress, secure DNS, and traffic visibility through Cilium, Calico or Datadog.

Secret management

Scenario. Someone base64-decodes a Kubernetes Secret and asks, "is that all it takes?"

What the picture shows. Secrets are only base64-encoded. Encrypt etcd with KMS envelope encryption, restrict access with RBAC, consider external managers (Vault, AWS Secrets Manager), rotate secrets, and monitor through a SIEM.

Identity and model endpoints

Scenario. The inference service needs S3 access and a public HTTPS endpoint.

What the picture shows. IRSA vs. EKS Pod Identity (simpler setup through an agent DaemonSet), TLS everywhere with ACM certificates on the ALB or NLB, and WAF on the ingress.
