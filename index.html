Serving LLMs on Kubernetes

  1. From a Python script to a model server
  2. The serving runtimes worth knowing
  3. Deploying by hand
  4. KServe: separate the runtime from the model
  5. Ray Serve and KubeRay

Before the deep dives, here's the workload most of them end up hosting: a large language model behind an API. This post covers what it takes to go from a model on a laptop to a production endpoint on Kubernetes.

From a Python script to a model server

Loading a model with the Transformers library and calling it works for a demo, but it is one process, one hard-coded prompt and no API. Wrapping it in FastAPI is the next step, and at that point you are rebuilding a model server: a runtime that loads the model, exposes it over REST or gRPC, and is tuned for throughput and latency. Memory is the first constraint: as a rule of thumb, a 7B model needs a GPU with about 15 GB, and a 70B model needs about 140 GB.

The serving runtimes worth knowing

  • vLLM: the most widely used open-source server, with an OpenAI-compatible API, PagedAttention and continuous batching.
  • TGI (Hugging Face): similar, and can switch backends (CUDA, TensorRT-LLM, llama.cpp, AWS Neuron for Trainium/Inferentia).
  • llama.cpp: for laptops and edge devices; it is where the GGUF format comes from.
  • NVIDIA NIM: curated, pre-optimized images per model family, with a model cache on a PersistentVolume.
  • SGLang: strong at reusing the KV cache across requests that share a prompt prefix (agents, multi-turn chats).

A platform team doesn't need to master every inference optimization (quantization, speculative decoding, FlashAttention). Pick an actively maintained server and watch the settings that change the topology: multi-GPU and multi-node serving make the deployment stateful and need extra coordination.

Deploying by hand

A plain Deployment for vLLM already needs a GPU limit, a toleration for tainted GPU nodes, a Secret for gated models, and a PVC as a model cache so a restart doesn't re-download 100 GB. Multiply that by every model and the case for a controller is obvious. → See The NVIDIA device plugin.

KServe: separate the runtime from the model

KServe splits ServingRuntime (the model server image and defaults, owned by the platform team) from InferenceService (one model, owned by data scientists), so runtime upgrades and model releases can move at their own pace.

  • Standard mode creates plain Deployments, which is the usual choice for large LLMs.
  • Knative mode adds scale-to-zero.
  • ModelMesh packs many small models together.

The newer LLMInferenceService adds KV-cache-aware routing, disaggregated serving and tensor/data/expert parallelism for 7B–405B models. → See Workloads and node tiers and Placement, autoscaling and cost.

Ray Serve and KubeRay

Ray defines its own cluster (a head node plus workers) and its own scheduling, and KubeRay's RayService maps it onto Kubernetes. Python teams get full control from code, at the cost of a second orchestration layer on top of Kubernetes. → See How a Pod finds its scheduler.

Getting model weights into pods

  1. What's in a model file
  2. Model registries
  3. Four ways to get weights into a pod
  4. Why OCI images fit models well
  5. My rule of thumb

LLM weights range from a few GB (Mistral 7B is about 14 GB) to nearly a terabyte (Llama 3.1 405B is about 750 GB). Moving that much data into pods quickly and cheaply is a storage, network and startup-time problem. This post covers the formats, the registries, and four ways to get weights to a model server.

What's in a model file

  • Weight-only formats (PyTorch .pt/.pth, TensorFlow checkpoints, NumPy) need the original code to rebuild the network.
  • "Mostly self-contained" formats carry more:
  • Safetensors is safe to load (unlike pickle, it can't execute code), memory-maps tensors without copies, and shards large models into many files with an index.
  • GGUF packs quantized weights plus tokenizer data into one file for llama.cpp and vLLM.
  • ONNX carries the graph but not the tokenizer.

None is fully self-contained yet. config.json and tokenizer.json still travel alongside the weights. → See The build pipeline.

Model registries

A registry tracks versions, metadata, lineage, stage (experiment → staging → production) and access, but usually stores only pointers to the weights in object storage. Common choices are the Hugging Face Hub (public), MLflow, the Kubeflow Model Registry, and plain OCI registries.

Four ways to get weights into a pod

Approach How Good for Watch out for
Init-container copy Download (S3, HTTP, HF) into an emptyDir before the server starts Fastest reads, single replica Slow startup, one copy per pod per node
Shared PersistentVolume One copy on NFS/EFS/Ceph, mounted ReadOnlyMany by every replica Many replicas, models managed outside the cluster Every read crosses the network; struggles at hundreds of replicas
Modelcar Model in an OCI image, run as a sidecar; the server reads it through a /proc symlink Fine-tuned models sharing base layers Needs shareProcessNamespace (a security concern), startup races
OCI image volume Mount the model image directly as a read-only volume (beta in Kubernetes 1.35) The clean, native future Feature gates and runtime versions still required

→ See StorageClass, PV and PVC, Storage and StatefulSet mechanics and Storage (cost).

Why OCI images fit models well

Container images are layered, cached per node and content-addressed. Put a base model in one layer and LoRA adapters on top, and ten fine-tuned variants share one copy of the base on each node. The CNCF ModelPack spec is standardizing this. Pre-pulling or prefetching model images keeps scale-up predictable. → See Networking (cost).

My rule of thumb

Pick the access method per tier. Use PersistentVolumes in development for easy updates and OCI images in production for speed and repeatability. Always measure time from pod scheduled to model ready, because that is where large-model autoscaling breaks down.

Running LLMs in production

  1. 1. Choose the model with numbers, not vibes
  2. 2. Compress, then evaluate again
  3. 3. Do the memory math
  4. 4. Tune the runtime for the workload
  5. 5. Benchmark like production
  6. 6. Scale, start fast, route smartly

Getting a model to answer once is easy. Keeping it fast, affordable and correct under real traffic is the hard part. These are the steps I'd go through before calling an LLM deployment production-ready.

1. Choose the model with numbers, not vibes

Two models of the same size can behave very differently on your task. Use public leaderboards (MMLU for knowledge, HellaSwag for commonsense, TruthfulQA for truthfulness) only to build a shortlist, because published scores can't be verified. Then re-run the evaluations yourself with tools like EleutherAI's lm-evaluation-harness. Benchmarks take minutes to hours, so run them as asynchronous jobs in a pipeline. TrustyAI wraps the harness as an LMEvalJob custom resource. Add task-specific checks too: Ragas for RAG quality and garak for security probing.

2. Compress, then evaluate again

An 8B model at 16 bits needs about 16 GB for its weights alone. Quantization to FP8 or INT8 roughly halves that and can double or triple throughput on the same GPU, often keeping 99% or more of the accuracy. Two conditions apply: the runtime must have native kernels for the quantized format (vLLM does), and the result must be re-evaluated, because a bad quantization can quietly ruin quality. Pre-quantized, validated models are the low-risk option.

3. Do the memory math

A rough GPU memory budget for one replica:

  • the weights (parameters × bytes per parameter);
  • about 1 GB of runtime overhead;
  • activations, which grow quickly with sequence length;
  • the output tensor;
  • everything left goes to the KV cache.

Example: an 8B fp16 model with a 2k context and batch size 1 needs about 17 GB. At batch size 10 it needs about 28 GB. vLLM prints this breakdown at startup, and warns when it has to evict KV-cache blocks because it ran out of room.

4. Tune the runtime for the workload

vLLM's defaults are good. The settings that matter most are:

  • gpu-memory-utilization: how much of the GPU it may claim.
  • max-model-len: caps the context, which sizes the KV cache. Don't cut it below what RAG prompts need.
  • max-num-seqs: batch size, a trade between throughput and memory.
  • tensor-parallel-size / pipeline-parallel-size: more GPUs, and more KV-cache room.
  • cpu-offload-gb: lets bigger models fit, but is too slow for production.

5. Benchmark like production

Use LLM-aware load generators that report TTFT and inter-token latency: GuideLLM, inference-perf (from Kubernetes WG-Serving), MLPerf Inference, or vLLM's benchmark scripts. Run them in CI on the same GPU type and count as production, store the results, and use them for capacity planning, rate limits and autoscaling targets.

6. Scale, start fast, route smartly

Autoscaling, startup time and routing each have their own section with the details:

  • Placement, autoscaling and cost: scale on token metrics with KEDA.
  • Networking (cost): from minutes to seconds to ready.
  • kube-proxy: iptables vs. IPVS: KV-cache- and LoRA-aware routing.
  • Latency and EFA: disaggregated serving.

At the largest scale, disaggregated serving (llm-d, NVIDIA Dynamo) splits prefill (compute-heavy, drives time to first token) from decode (memory-heavy, drives time per token). The two pools scale separately and share a distributed KV cache (LMCache, NIXL) over very fast networks.

Observing LLMs

  1. 1. The usual stack still applies
  2. 2. Measure tokens, not requests
  3. 3. Fast isn't enough: watch quality
  4. 4. Responsible AI

Kubernetes heals crashed pods, but it can't tell you that answers got slow, or wrong. LLM observability starts with the usual logs, metrics and traces, then switches to tokens instead of requests, and finally adds a layer most services never need: checking that the answers are any good.

1. The usual stack still applies

  • Logs go to stdout and need a log store such as Loki. A vLLM startup log already tells you a lot: version and arguments, the model config, how much GPU memory the weights took and how much is left for the KV cache, and the routes it serves.
  • Metrics are scraped in Prometheus/OpenMetrics format. KServe has annotations that turn scraping on for a model, plus an aggregator for multi-container pods.
  • Traces: vLLM emits OpenTelemetry spans (send them to Jaeger, for example), and OpenTelemetry is defining semantic conventions specifically for generative AI.

2. Measure tokens, not requests

The GPU does the work, so CPU usage says little. The two phases also behave differently: prefill is compute-heavy and decode is memory-heavy. The core metrics:

  • Time to first token (TTFT): what a chat user feels as "waiting". It reflects the prefill phase.
  • Time per output token (TPOT), or inter-token latency: reading speed. About 4–5 tokens per second keeps up with a human reader.
  • Throughput: prompt and generated tokens per second.
  • End-to-end latency per request.
  • Queue: num_requests_waiting and num_requests_running, the earliest sign of overload.

Turn them into SLIs and SLOs (for example "TPOT under 0.3 s for 99.9% of requests"), alert on them with PrometheusRules, and link a runbook. GPU health comes from vendor exporters (NVIDIA DCGM, AMD, Intel) alongside these. → See What every scheduler relies on.

3. Fast isn't enough: watch quality

A model rarely crashes on bad input. It answers confidently and wrongly, which is a hallucination. Benchmarks before deployment help, but in production I'd sample 1–10% of responses into an asynchronous LLM-as-a-judge pipeline. Its quality scores are exported as Prometheus metrics, so they can be trended and alerted on like latency. For narrow tasks a cheap metric can work instead, such as ROUGE overlap for summaries. Judges work best with specific questions ("Does this reply include personal data?") rather than "Is this answer good?"

4. Responsible AI

Explanations are expensive to compute, so capture requests and responses with an inference logger and explain only the disputed cases later. Bias can appear at runtime through data drift even if training was clean, so monitor fairness metrics on protected attributes continuously (KServe with TrustyAI can do this). Input and output guardrails are covered in Identity and model endpoints.

Customizing models: prompts, RAG, LoRA and training jobs

  1. 1. Try the cheap options first
  2. 2. Full fine-tuning vs. LoRA
  3. 3. Running tuning jobs on Kubernetes

Almost nobody trains an LLM from scratch. Pre-training takes thousands of GPUs for weeks, and alignment then teaches the base model to follow instructions safely. What platform teams actually run is post-training: adapting an already aligned model to their domain. The first question is whether you need to train at all.

1. Try the cheap options first

  • Prompt engineering: a system prompt that sets the scenario, the role and the boundaries. It is not a security control, because prompt injection can bypass it.
  • Context engineering and RAG: fetch relevant documents at request time and put them in the prompt. Update the knowledge base in minutes, with no training job.

Training becomes worth it when large, slow-changing knowledge would otherwise ride along in every prompt. Long contexts cost GPU memory on every request, so a bank might bake lending and risk knowledge into a model and keep RAG for fresh facts. A small, specialized model (8–16B parameters), possibly distilled from a large one, can match a big general model at a fraction of the serving cost.

2. Full fine-tuning vs. LoRA

  • Full fine-tuning updates every weight. It needs hundreds of thousands of labelled examples and many GPUs, risks "catastrophic forgetting", and produces a separate model that needs its own GPUs to serve.
  • Parameter-efficient fine-tuning (PEFT), mainly LoRA, freezes the base model and trains small adapter matrices, often under 1% of the parameters. It needs only 100–1,000 examples and finishes in hours. At serving time one base model can host many adapters (vLLM loads them side by side), which is why LoRA-aware routing matters. QLoRA adds quantization to cut training memory further.

Hugging Face TRL's SFTTrainer handles both, and newer methods (DPO, GRPO, reward modelling) show up as multi-step pipelines with several GPU components.

3. Running tuning jobs on Kubernetes

  • Even small fine-tunes usually span several GPUs and often several nodes. Sharded training (PyTorch FSDP2) moves weights between GPUs on every layer, so the network becomes the bottleneck.
  • Kubeflow Trainer separates the roles:
  • the platform team defines TrainingRuntimes (PyTorch, DeepSpeed, MLX, MPI);
  • data scientists submit TrainJobs from Python, where their function is serialized into the job, so there is no image rebuild per experiment;
  • the controller turns them into a JobSet.
  • Alternatives: Ray/KubeRay (RayJob on a RayCluster; code ships in images or repos), DeepSpeed as a training library, and Unsloth for fast single-GPU fine-tuning.
  • Checkpoints must go to persistent storage, and multi-node jobs need gang scheduling and quota.

RAG and agents on Kubernetes

  1. 1. Two application shapes
  2. 2. RAG, end to end
  3. 3. Agents

In a real product, the model is one service among many. The application owns the logic: it fetches context, calls tools, keeps state, and uses the LLM for generation and reasoning. This post maps those pieces onto Kubernetes.

1. Two application shapes

  • Chat apps: gateway → orchestrator → LLM → state store, all within one synchronous request. Latency rules, so everything stays warm, and browser-based sign-in (OAuth2) is easy.
  • Backend AI services: triggered by events (an order placed, a payment made) or by a schedule. They need idempotency, buffering and eventual consistency more than raw speed, and can scale to zero.

Around these sit nightly CronJobs, always-on agent loops (single-replica Deployments that watch a feed, like a controller with an LLM inside), and multi-step automations that run as Jobs. → See Workloads and node tiers and Thundering herd.

2. RAG, end to end

Ingestion (offline, as Jobs or CronJobs):

  1. parse documents (e.g. with Docling);
  2. split them into chunks by sentence, paragraph or heading;
  3. embed each chunk;
  4. upsert the vectors with metadata (source, section, version) into a vector database.

Query time: embed the question with the same embedding model, run a similarity search (optionally hybrid with keyword ranking), optionally rerank, build the prompt from a template, generate, then add citations and run guardrails before returning.

Component Kubernetes shape
Vector DB (Milvus, Weaviate, Qdrant, pgvector) StatefulSet + PVC, snapshots, NetworkPolicy
Embedding model Deployment, sidecar, or in-process
Orchestrator Deployment + Service/Ingress; prompts in ConfigMaps, keys in Secrets
Reranker Optional Deployment for high-stakes queries
Ingestion CronJob / Job with limits so it can't starve users

If you change the embedding model, you must re-embed every document. → See Workloads, node groups and scheduling.

3. Agents

An agent wraps the model in a loop: perceive → think → act (call a tool) → observe → reflect → remember. ReAct is the classic form.

  • Tools run either on the client (the model asks your code to run a function) or on the server, increasingly through MCP servers.
  • Frameworks: client-side libraries (LangChain, LangGraph, CrewAI) or server-side runtimes behind an API (the OpenAI-style Responses API, Llama Stack, vLLM's emerging support). Server-side runtimes handle state and human approval steps for you.
  • On Kubernetes: operators like Kagent declare agents, tools and A2A skills as custom resources. Agents are Deployments, tools are Services, memory lives in StatefulSets, and heavy work goes to Jobs.
  • Multi-agent systems use either a coordinator or peer-to-peer messaging, plus shared memory. Plan for failures (sagas) and require human approval for risky actions.

Running agents in production

  1. 1. MCP: one protocol for tools
  2. 2. Whose identity reaches the backend?
  3. 3. A2A: agents talking to agents
  4. 4. Memory and long-running work

Agents bring three problems that plain microservices don't: who they act as, how they talk to each other, and what they remember. The protocols are still young, but the operational patterns below hold regardless of framework.

1. MCP: one protocol for tools

The Model Context Protocol replaces one-off integrations between every agent and every tool (M×N) with a single protocol (M+N). Tools describe themselves with a name, a description and a JSON schema, and calls use JSON-RPC. On Kubernetes:

  • Run each MCP server as a Deployment behind a Service, keep session state external, and scale with HPA.
  • Use a sidecar only when the tool must share the agent's files.
  • Group related tools into a single server to keep the number of services manageable. Watch the total tool count, because agents choose less well from very long lists.

MCP now sits under the Linux Foundation's Agentic AI Foundation, together with goose and AGENTS.md.

2. Whose identity reaches the backend?

Pattern How Strength Watch out for
Token passthrough Agent forwards the user's OAuth token Existing per-user RBAC and audit just work Token expiry on long tasks, broad scopes, stolen tokens
ServiceAccount delegation Pod ServiceAccount tokens; validate with TokenReview, authorize with SubjectAccessReview on app-specific "virtual" resources No extra identity provider inside the cluster Workload identity only, no user
Token exchange (RFC 8693) Identity provider issues a token with the user in sub and the agent in act User and agent visible; composite policies Run and cache an exchange service
SPIFFE/SPIRE mTLS SPIRE issues short-lived X.509 identities per pod via a node agent No secrets to steal; auto-rotation Significant setup and operations

Production setups combine them: SPIFFE mTLS between workloads, the user's identity in a header or exchanged token, and a policy engine (OPA) that requires both. MCP gateways (Envoy AI Gateway, agentgateway, ContextForge and others) centralize authentication, authorization, rate limits and audit, at the cost of an extra hop that must be highly available. → See Identity and model endpoints.

3. A2A: agents talking to agents

MCP connects an agent to tools. The Agent-to-Agent (A2A) protocol connects an agent to other agents, which can reason and take time. It has three building blocks:

  • an agent card that advertises skills and formats, like an OpenAPI spec;
  • a task lifecycle (created → in progress → completed / failed / cancelled) that outlives any single HTTP call;
  • streamed artifacts for partial results.

Each agent is its own Deployment, with NetworkPolicies between them and circuit breakers in the mesh. Treat the agent card as a contract you check in CI, and alert on tasks stuck in progress.

4. Memory and long-running work

  • In-memory state is fine for development and lost on the first restart or scale-out.
  • Short-term memory (the session) belongs in a key-value store such as Redis, run as a StatefulSet with a TTL per session, so any replica can serve the next turn.
  • Long-term memory (preferences, audit trail, cross-session analytics) belongs in a database, written asynchronously.
  • Long-running agents checkpoint after each major step to a PVC and run as Jobs with restartPolicy: OnFailure, so an evicted pod resumes where it left off. The checkpoints double as a debugging trail.

Start with plain Deployments, Services, RBAC and StatefulSets, and add meshes, gateways and operators only when a real limitation shows up.

How kube-scheduler picks a node

Every pod goes through the same decision: filter out the nodes that can't run it, score the ones that can, and bind it to the best one. This tab follows that decision step by step.

Phase 1: filtering

Scenario. A pod stays Pending with 0/12 nodes are available. The developer says there's "plenty of room".

What the picture shows. Filtering drops any node that fails a hard rule: requested CPU or memory doesn't fit, nodeSelector doesn't match, an untolerated taint, required affinity or anti-affinity, or a hostPort that's already taken. "Plenty of room" usually means free usage, but the scheduler only counts requests. The event message lists which rule removed how many nodes.

Going deeper. For GPUs, these same filters do the steering. nvidia.com/gpu: 1 is purely resource-based, so every GPU counts the same: a 16 GB T4 and an 80 GB A100 are both "1". A nodeSelector on GPU labels pins an exact model, node affinity can say "at least 40 GB, prefer Hopper", and a taint on GPU nodes keeps everything else off them. Dynamic Resource Allocation (stable since Kubernetes 1.34) lets a pod describe the device it needs, and the driver picks a match at scheduling time. Filtering also runs one pod at a time: a distributed job's workers are judged separately, which is the root of the gang problem.

Filtering outcomes at a glance

Scenario. On-call needs a quick way to map an event message to a cause.

What the picture shows. A cheat sheet linking each kind of constraint (resources, taints, affinity, selector) to its consequence, and a funnel from all nodes to the feasible set that goes on to scoring.

Phase 2: scoring plugins

Scenario. Three nodes pass filtering. Why does the pod always land on the same one?

What the picture shows. Each plugin gives every node a 0–100 score: LeastAllocated (the spreader), BalancedAllocation (keeps CPU and memory even), ImageLocality (image already cached) and preferred affinity. The node with the highest weighted total wins. Preferred affinity is the only one you set directly in the pod spec.

Going deeper. For GPU training I switch NodeResourcesFit to MostAllocated (bin-packing) and give nvidia.com/gpu a higher weight than CPU and memory. Packing leaves whole nodes empty, so the autoscaler can remove them. That matters when a GPU node costs tens of dollars an hour. The catch is a bigger blast radius per node, so I offer it as a separate scheduler profile and let critical services keep spreading.

Score × weight

Scenario. You need to explain on a whiteboard how "points" become a decision.

What the picture shows. final score = Σ (plugin score × plugin weight). The score measures quality ("how empty is this node?") and the weight measures importance. Worked examples: LeastAllocated gives 80 for a node that's 80% free, and ImageLocality rises with how much of the image is cached.

When affinity loses to ImageLocality

Scenario. A pod has a soft affinity to run near its cache service, but keeps landing on a node far away that happens to have its big image.

What the picture shows. A weak affinity match times weight 2 can still lose to a strong image-cache score. There are two ways to fix it: make the rule required, which moves it into filtering, or raise the plugin weight cluster-wide in KubeSchedulerConfiguration.

A worked example

Scenario. Two candidate nodes and three plugins. Which one wins?

What the picture shows. Node 2 wins on the total even though Node 1 wins one plugin. The picture uses equal weights to keep the arithmetic simple. In the real default profile, affinity has weight 2, which only makes Node 2's lead bigger.

The weight field in your YAML

Scenario. A teammate asks what weight: 80 in a pod spec actually does.

What the picture shows. weight (1–100) only exists on preferred rules and tunes scoring. Required rules have no weight because they're filters. A high weight means "a strong suggestion", and a low one means "nice to have".

Scheduler score vs. OOM score

Scenario. "The scheduler gave this node a low score, so why did my important pod get killed there?"

What the picture shows. The scheduler's score only matters at placement time. Under memory pressure, the kubelet evicts pods by how far they're over their memory request (then by priority), and the kernel's OOM killer uses oom_score. These are separate systems that use separate numbers (see Memory: who gets killed).

When one scheduler isn't enough

  1. How a Pod finds its scheduler
  2. Gang scheduling
  3. Topology bin-packing
  4. Queueing and fair sharing
  5. Hardware-aware scheduling
  6. Volcano vs. Kueue
  7. The landscape

The default scheduler places pods one at a time and knows nothing about jobs, teams or GPU topology. This tab covers the problems that pushed the ecosystem toward Kueue, Volcano, KAI and YuniKorn, and how to choose between them.

How a Pod finds its scheduler

Scenario. On EKS, some pods run on Fargate and others on EC2 nodes, and nobody set schedulerName by hand.

What the picture shows. Every scheduler watches for unscheduled pods whose schedulerName matches its own. For Fargate, a mutating webhook sets fargate-scheduler on pods that match a Fargate profile. The table compares the default scheduler with an ML-oriented one.

Going deeper. Ray (through KubeRay) is another two-scheduler setup. Kubernetes places and restarts the Ray head and worker pods, and Ray's own scheduler places tasks and actors inside them. That suits Python teams well, but capacity accounting and debugging now span two layers.

Gang scheduling

Scenario. An 8-worker PyTorch job only fits 6 workers. Six GPUs sit allocated, and nothing trains.

What the picture shows. Pod-by-pod placement vs. all-or-nothing placement. A gang scheduler keeps every pod pending until the whole group fits.

Going deeper. The reason is the rendezvous barrier: distributed PyTorch workers wait until every rank has joined, so 7 of 8 workers will sit on their GPUs forever. The options sit at different layers:

  • the coscheduling plugin: a PodGroup with minMember and a timeout, inside kube-scheduler;
  • Kueue: decides at the job level whether a job may start;
  • KAI or Volcano: replace the scheduler.

Upstream is also designing a native Workload API for this. Model-parallel inference has the same property: if one shard's pod is missing or dies, the whole replica is down, so it needs all-or-nothing scheduling and group restarts too.

Topology bin-packing

Scenario. Two pods that exchange tensors constantly end up on different nodes, and step time doubles.

What the picture shows. Spreading vs. packing onto one NVLink-connected node. For tightly coupled training, the default spreader is the wrong instinct.

Going deeper. Placement depends on how the model is split:

  • Tensor parallelism splits every layer and exchanges results constantly. Keep it inside one node on NVLink/NVSwitch.
  • Pipeline parallelism splits by layers and only hands activations across once per stage, so it tolerates the slower links between nodes.
  • Hybrid: tensor parallelism inside nodes and pipeline parallelism between them is the common setup.

Even inside one server, not every GPU pair may share the same NVLink group. nvidia-smi topo -m shows it, and a job may rightly wait in the queue rather than start on badly connected GPUs.

Queueing and fair sharing

Scenario. One researcher submits 100 jobs on Friday night, and nobody else gets a GPU all weekend.

What the picture shows. A greedy FIFO vs. queues with priorities and fair share, and preemption of low-priority research work when inference needs capacity.

Going deeper. In Kueue terms:

  • ClusterQueues hold each team's nominal quota and borrowing limit.
  • Teams submit to LocalQueues.
  • A cohort lends idle quota between teams and takes it back by preemption when its owner needs it.

WorkloadPriorityClasses decide admission order, and fair sharing favors teams that have used less recently. Hard namespace ResourceQuotas can't do any of this: idle GPUs in one namespace never help another team's queue.

Hardware-aware scheduling

Scenario. An FP8 training job lands on older GPUs and runs at a fraction of the expected speed.

What the picture shows. A scheduler that matches workloads to hardware features (RDMA/InfiniBand switch, newer GPU generation) instead of only counting GPUs. Labels and selectors work to start with, and become painful across many hardware generations.

Going deeper. NVIDIA's GPU Feature Discovery labels every node with the GPU product (e.g. A100-SXM4-40GB), memory, architecture family, driver and CUDA versions, MIG capability, and the number of shared replicas. Kueue turns these labels into ResourceFlavors: the premium flavor (NVLink + InfiniBand) is listed first, with a fallback flavor and TryNextFlavor. Which hardware a job gets (flavor) and who goes first (priority) stay separate decisions.

Volcano vs. Kueue

Scenario. The team has to pick one, and the debate keeps going in circles.

What the picture shows. Volcano replaces the scheduler and understands dependencies between task types (start workers only once the master is placed). Kueue sits in front of the default scheduler and manages quota, borrowing and fairness between teams.

Going deeper. The production answer is usually "both layers": Kueue for admission and quota on top of a gang-aware or topology-aware scheduler (kube-scheduler with plugins, KAI or Volcano), with a workload API that groups the pods (PyTorchJob/TrainJob, JobSet, LeaderWorkerSet). Kueue stays vendor-neutral and keeps policy separate from mechanism. A replacement scheduler is worth it when GPU-specific features (fractional GPUs, deep topology awareness) pay for the extra moving part.

For fine-tuning, Kubeflow Trainer shows the same layering. The platform team publishes a TrainingRuntime (framework, image, defaults), and data scientists submit a TrainJob, often straight from a Python SDK. The controller turns the pair into a JobSet, a group of Jobs that Kueue can then admit as one gang.

The landscape

Scenario. Leadership asks for one page that compares the options.

What the picture shows. KAI, Volcano and YuniKorn compared on gang scheduling, GPU bin-packing, fair sharing and hardware awareness, plus a market matrix that includes Kueue and Armada.

What every scheduler relies on

Scenario. Whichever scheduler we choose, how does it know what hardware a node has?

What the picture shows. The NVIDIA device plugin advertises nvidia.com/gpu, and topology operators label nodes with InfiniBand/RDMA details. Every scheduler reads these labels and resources from the API server.

Going deeper. On NVIDIA nodes, one GPU Operator (configured through a ClusterPolicy) installs and maintains everything a scheduler depends on:

  • the driver container;
  • the container toolkit, which injects /dev/nvidia* into containers;
  • the device plugin;
  • GPU Feature Discovery labels;
  • the MIG manager;
  • the DCGM exporter, which sends GPU utilization, memory, ECC errors, temperature and power to Prometheus.

If the device plugin isn't running, GPU pods simply stay Pending.

One cluster runs a latency-critical web API next to cost-driven batch jobs. This tab follows the isolation stack from node tiers down to CPU, memory, network and disk.

Workloads and node tiers

Scenario. Every evening the batch wave arrives and the API's p99 latency jumps above 100 ms.

What the picture shows. Web services are latency-sensitive and need stability, while batch is retry-capable and opportunistic. Each gets its own tier: on-demand, tainted nodes for web (with placeholder pods for headroom), diversified Spot capacity for batch, and a shared, untainted tier for utilization.

Going deeper. For LLMs, the latency-critical tier is the model server: vLLM, TGI, SGLang or NVIDIA NIM, each exposing an OpenAI-compatible API behind a Service. Large models need whole, dedicated GPUs and minutes to load, so I run them as plain Deployments (KServe's Standard mode) on tainted GPU nodes with warm capacity, rather than relying on scale-to-zero.

AI applications follow the same split:

  • Chat-style apps are synchronous: the user waits, so the orchestrator and model server stay warm and close together.
  • Event-driven AI backends (for example, scoring every new order for fraud) run asynchronously off a message bus. They can scale from zero with KEDA or Knative, and can live in the cheaper tier.

Priority, preemption and QoS

Scenario. The cluster is full when a traffic spike hits. Who gets evicted, and who decides?

What the picture shows. Two different mechanisms. PriorityClasses are the scheduler's tool, applied cluster-wide (web-critical preempts, batch-low never does). QoS (Guaranteed > Burstable > BestEffort) is the kubelet's tool, applied on one node under resource pressure.

Going deeper. Kueue adds a job-level layer on top of these two. WorkloadPriorityClasses decide admission order, and preemption can reclaim quota that another team borrowed. Which hardware a job gets and who goes first are separate decisions.

Placement, autoscaling and cost

Scenario. Batch costs are climbing even though most nodes look half empty.

What the picture shows. Affinity for web, anti-affinity for batch, and requests and limits per workload type. Autoscaling uses HPA for web (fast up, slow down) and Karpenter for batch (diversified Spot, consolidation). Spot interruptions are handled by checkpointing, and the key alerts are pending pods, queue depth and p99.

Going deeper. Packing pairs with the descheduler, which periodically evicts pods so they can be placed again on a tighter set of nodes. Its strategy must match the scheduler's: HighNodeUtilization goes with MostAllocated, and LowNodeUtilization goes with LeastAllocated. Mix them and you get an eviction loop. For training, every eviction costs a checkpoint and restart, so PodDisruptionBudgets, maintenance windows and excluded namespaces matter. Model-parallel inference scales in whole groups (a 4-GPU replica can't become 3), so autoscale on requests per second or latency with HPA or KEDA, and keep replicas warm because model loading is slow.

LLM servers break the usual autoscaling signals. The default HPA watches CPU and memory, but the work happens on the GPU. Request-based scaling (Knative's KPA) treats a 10-token answer and a 10,000-token answer as the same. What works is KEDA on the model server's own metrics, such as vllm:num_requests_waiting or vllm:num_requests_running, or latency targets (TTFT, time per output token). Scale-to-zero rarely fits: a new replica can take minutes to pull and load the model, so keep a warm minimum and alert on token latency and queue depth rather than CPU.

CPU: shares and throttling

Scenario. The API's average latency looks fine, but p99 spikes every few seconds.

What the picture shows. Requests become CPU shares, which split the CPU under contention. Limits become a quota per 100 ms window. A multi-threaded pod can use up its quota early in the window and then freeze until the next one, which is where the p99 jitter comes from.

Kernel vs. Kubernetes

Scenario. "Why do requests matter if the kernel shares CPU fairly anyway?"

What the picture shows. Kubernetes sets the policy, the kubelet translates it into cgroups, and the kernel enforces it. The one thing the kernel can't do is stop a node from being overpacked. Only the scheduler's request accounting does that.

Memory: who gets killed

Scenario. A node runs out of memory. Which pod dies first, and why that one?

What the picture shows. Memory can't be compressed: the OOM killer runs at container or node level. QoS sets oom_score_adj (BestEffort 1000, Guaranteed -997, Burstable in between, depending on its memory request). Among Burstable pods, the kubelet evicts the one furthest over its request first.

Network: the unmanaged resource

Scenario. A backup pod starts a 10 Gbps transfer and the API on the same node starts dropping connections, yet CPU and memory look perfect.

What the picture shows. Kubernetes has no network requests or limits. The fixes are Linux tc shaping, CNI bandwidth annotations, and instance types with separate bandwidth for EBS.

Storage I/O: the other unmanaged resource

Scenario. A log archiver saturates a volume, and the database pod sharing it goes from 1 ms to 200 ms latency.

What the picture shows. EBS throttles per volume, not per pod, and Kubernetes doesn't expose the blkio controller. The symptoms are I/O wait, processes stuck in the D state, and failing liveness probes. The fixes are dedicated volumes per critical pod, EBS-optimized instances, and node-level guardrails.

From a YAML limit to a kernel quota

This tab follows how resources.requests and resources.limits turn into cgroup settings that the Linux CFS scheduler enforces.

Policy maker, translator, enforcer

Scenario. A web pod (request 1 core, limit 2) and a batch pod (request 250m, limit 500m) share a busy node. How much CPU does each get?

What the picture shows. The kubelet writes shares (1024 vs. 256) and quotas into each pod's cgroup. Under contention, CFS splits the CPU 80/20 by shares. When the batch pod hits its quota, it is throttled even if the CPU is otherwise idle.

From a limit to a quota

Scenario. "How can a pod use 200 ms of CPU inside a 100 ms window?"

What the picture shows. quota = limit in cores × 100,000 µs. A 2-core limit gives 200 ms per window because quota is counted across all cores, so two threads can run flat out for the whole window. On cgroup v2 (recent EKS AMIs) the files are cpu.weight and cpu.max, but the model is the same.

Volume attachment limit

Scenario. Database pods 29 and 30 stay Pending on a big node that has plenty of free CPU.

What the picture shows. Nitro instances can attach only about 28 volumes. The fix is to spread stateful pods with anti-affinity or topology spread constraints, so the scheduler stops piling them onto one node.

The stuck volume

Scenario. A node dies, and the database pod crash-loops on its replacement node.

What the picture shows. The EBS volume still appears attached to the dead node, so the new node can't attach it. The quick fix is to force-detach it. The lasting fix is to keep the EBS CSI driver up to date.

Snapshot restored in the wrong AZ

Scenario. A restored database never starts.

What the picture shows. EBS volumes are tied to one AZ. If you restore into the zone your nodes are in, or let WaitForFirstConsumer choose the zone, the volume and the pod end up in the same place.

Force delete and filesystem corruption

Scenario. Someone runs kubectl delete pod --force --grace-period=0 on a database mid-write.

What the picture shows. Never force-delete a database pod unless its node is already gone. To recover, restore the last good snapshot and replay the WAL.

IOPS throttling cascade

Scenario. Latency goes from 1 ms to over 100 ms, the connection pool fills up, and the whole app falls over.

What the picture shows. gp3 gives a 3,000-IOPS baseline. Provision the IOPS you actually need in the StorageClass, and watch IOPS (or BurstBalance on gp2) before you hit the limit.

Cross-AZ transfer costs

Scenario. The Kafka bill's networking line is bigger than its compute line.

What the picture shows. Every replicated message crosses AZs, and each crossing costs money. The fixes are compression (zstd or snappy) and rack-aware reads from replicas in the same AZ.

The page-cache memory trap

Scenario. An ML job that loops over the same dataset gets OOM-killed, but its own memory use looks small.

What the picture shows. Active page cache counts toward the container's working set. Watch container_memory_working_set_bytes, leave headroom between request and limit, and use posix_fadvise(DONTNEED) on data you have finished reading.

Thundering herd

Scenario. 100 batch jobs finish at the same moment, all write to the database, and the web service's queries start failing.

What the picture shows. The batch jobs effectively DDoS your own database. Put a queue (SQS or Kafka) in between with controlled consumers, or add random jitter to the batch jobs as a quick fix.

Going deeper. Event-driven AI services and agents hit the same problem when a burst of events arrives at once. Put a message queue in front so events wait while pods restart, make every handler idempotent so duplicate events are harmless, and use a compensating action (the Saga pattern) to undo half-finished multi-step work.

Scheduler thrashing

Scenario. A traffic spike makes HPA add 50 web pods, which preempt 50 batch pods. The Job controller recreates them, and they get preempted again, over and over.

What the picture shows. A feedback loop between controllers. Changing restartPolicy alone doesn't stop it. The fix is to queue instead of retry: admit batch jobs through Kueue only when capacity exists, give batch preemptionPolicy: Never, and set a Job podFailurePolicy.

Going deeper. The same kind of loop appears when a descheduler's strategy disagrees with the scheduler's scoring: pods get evicted, land back on the same node, and get evicted again. A steadily rising eviction count with no consolidation is the signal.

CPU limit vs. request gap

Scenario. Web latency spikes even though node CPU is only at 60%.

What the picture shows. A batch pod with a 1-core request and an 8-core limit can burst to 8 cores, but the scheduler only reserved 1 core for it. Neighbours see sudden contention. For CPU-heavy batch, set requests close to limits.

How GPUs become schedulable

The NVIDIA device plugin

Scenario. A new GPU node group joins the cluster, but pods that request nvidia.com/gpu: 1 stay Pending.

What the picture shows.

  1. The device plugin runs as a DaemonSet.
  2. It registers with the kubelet, which advertises GPU capacity.
  3. The scheduler can now count GPUs and place the pod.
  4. The kubelet asks the plugin to attach specific devices to the container.

In our setup, the plugin is installed by the EKS Terraform module.

Going deeper. Two discovery layers come first. Node Feature Discovery labels basic hardware facts (PCI vendor and class), and GPU Feature Discovery adds GPU details (model, memory, family, CUDA version). The device plugin then does four jobs:

  • it discovers devices;
  • it allocates them exclusively to containers;
  • it monitors their health;
  • it advertises them as nvidia.com/gpu for scheduling.

A minimal vLLM Deployment on such a node still needs a GPU limit, a toleration for the GPU taint, and a PVC as a model cache, so restarts don't re-download the weights. Plugins expose counts, not topology. That gap is why topology labels, Dynamic Resource Allocation and topology-aware schedulers exist.

A SaaS platform hosts standard, premium and regulated tenants on shared EKS. The question running through this tab: if one tenant is compromised, what can it reach?

Tenant classes, soft and hard isolation

Scenario. Sales has just signed a healthcare customer with HIPAA requirements. Can they live next to free-tier tenants?

What the picture shows. Tenants are classified by data sovereignty, compliance, blast radius and SLA. Soft isolation is namespace-based: ResourceQuotas and LimitRanges, default-deny NetworkPolicies, Pod Security Admission restricted, and namespace-scoped service accounts. Hard isolation means dedicated node groups with taints, subnets per tier, or a dedicated cluster for highly regulated tenants.

Going deeper. GPUs need the same soft vs. hard choice. Time slicing advertises several virtual GPUs per physical GPU, with no memory or fault isolation: one pod can exhaust the memory or crash the GPU for everyone. MIG (Ampere and newer) carves a GPU into hardware-isolated slices with their own memory, for example up to 7 on an A100-40GB. That's the right choice for strict multi-tenancy. Quota between tenants (who gets how many GPUs) is a separate problem, handled by Kueue's ClusterQueues and cohorts.

Identity, data, network and observability

Scenario. Tenant A's leaked credentials must not be able to read tenant B's data.

What the picture shows. The tenant boundary is enforced at three layers:

  • Identity: a per-tenant IAM role through IRSA.
  • Data: RDS with IAM auth and row-level security, per-tenant S3 bucket policies and VPC endpoints, and separate ElastiCache by tier.
  • Network: a shared ALB for the standard tier and a dedicated NLB plus PrivateLink for premium tenants.

Logs, metrics and traces all carry tenant labels.

Going deeper. For shared LLM endpoints, the unit of fairness is the token, not the request: one call can cost 10 tokens or 10,000. AI gateways (Envoy AI Gateway, Kuadrant) enforce token-based rate limits per user or API key. Tracing follows the same tenant-aware approach: model servers like vLLM emit OpenTelemetry spans that can be sent to Jaeger with the tenant in context.

Sandboxed runtimes: gVisor and Kata

Scenario. A premium tenant asks whether a kernel exploit in another tenant's container could reach their workload.

What the picture shows. With standard runC, all containers share the host kernel, so a kernel bug can lead to escape. gVisor puts a user-space kernel in between, and Kata runs each pod in a lightweight VM (similar in spirit to Fargate's Firecracker). You opt in per workload with a RuntimeClass.

Going deeper. AI agents that run generated code or untrusted tools need the same isolation. The Kubernetes community's agent sandbox project adds a pod-shaped, VM-isolated, single-instance runtime with a stable identity that can be paused and resumed. It's designed for interactive or untrusted agent workloads.

Hardening runC: seccomp, AppArmor, user namespaces

Scenario. Most workloads stay on runC. How do we shrink the attack surface without changing runtimes?

What the picture shows.

  • seccomp: an allow-list of the syscalls the app actually needs.
  • AppArmor/SELinux: mandatory access control, for example "nginx may only read /var/www".
  • User-namespace remapping: root inside the container is an unprivileged user on the host.

Control plane security

Scenario. An audit finds the EKS API endpoint is reachable from the internet.

What the picture shows. A private endpoint with VPC endpoint policies, admission webhooks (OPA Gatekeeper or Kyverno) for rules that built-in admission can't express, and audit logs to CloudWatch with tenant context for anomaly detection.

Network isolation and egress

Scenario. A regulated tenant needs encryption between pods and control over what its pods can call on the internet.

What the picture shows. Calico VXLAN overlays per tenant, Cilium's eBPF L7 and DNS-aware policies, and transparent WireGuard/IPsec encryption without a service mesh (or Nitro's hardware encryption in transit). Egress goes through VPC endpoints, or through a tenant-aware egress proxy that knows which pod sent each packet.

What the picture shows. The aws-node DaemonSet runs ipamd (which talks to the EC2 API and manages ENIs) and the CNI binary (which sets up the pod's network namespace and veth pair). Pod capacity comes from ENIs × IPs per ENI: 3 × (6 − 1) + 2 = 17 on a t3.medium.

Warm pools and prefix delegation

Scenario. A batch burst launches 200 pods at once, and they wait several seconds for IPs.

What the picture shows. WARM_ENI_TARGET (aggressive), WARM_IP_TARGET (balanced) and MINIMUM_IP_TARGET (a floor) trade IP waste against startup speed. Prefix delegation assigns /28 blocks instead of single IPs, so an m5.large goes from 29 to 110 pods.

Packet paths

Scenario. Is pod-to-pod traffic slower across nodes than within a node, and by how much?

What the picture shows. On the same node, traffic goes veth → host routing table → veth (microseconds). Across nodes, it goes through the primary ENI and native VPC routing with no overlay, then the destination node's ENI and veth.

kube-proxy: iptables vs. IPVS

Scenario. With 5,000 Services, every new connection gets slower.

What the picture shows. iptables mode walks a linear list of rules and picks backends with probabilistic NAT. IPVS uses hash lookups and real load-balancing algorithms (round robin, least connections). Both still rely on conntrack.

Going deeper. For LLM backends, round-robin is the wrong algorithm, whichever kube-proxy mode delivers it:

  • requests vary hugely in cost;
  • a replica that already holds a conversation's KV cache can skip most of the prefill work;
  • LoRA adapters mean one endpoint serves several models.

The Gateway API Inference Extension adds an InferencePool and an endpoint picker that chooses a pod by queue length, KV-cache contents or loaded adapter, and can shed low-priority requests when the pool is saturated.

conntrack: the connection ledger

Scenario. Under heavy load, a node starts dropping new connections even though CPU is fine.

What the picture shows. conntrack remembers every flow so reply packets find their way back. Entries expire on timeouts. An established TCP connection's default timeout is 5 days, so a busy node can fill the table. A shorter nf_conntrack_tcp_timeout_established is one fix.

Security groups for pods and network policies

Scenario. Compliance requires AWS security groups on the payment pods specifically.

What the picture shows. A trunk ENI and per-pod branch ENIs, each with its own security group. The cost is pod density, so use them only where AWS-level firewalls are required. Kubernetes NetworkPolicies need an engine: the VPC CNI's native one, Calico, or Cilium.

The packet's journey through netfilter

Scenario. "Where exactly does a Service IP get rewritten?"

What the picture shows. PREROUTING (DNAT from Service IP to pod IP), FORWARD (filtering, where policies live) and POSTROUTING (SNAT/masquerade when traffic leaves the VPC), with conntrack consulted at the entry and recorded at the exit.

From NetworkPolicy YAML to kernel rules

Scenario. A NetworkPolicy is applied, but traffic still flows.

What the picture shows. The YAML is only intent. Calico (the translator) turns it into iptables chains at the FORWARD hook (the enforcement). If no engine is running, nothing enforces the policy.

Calico vs. Cilium

Network optimization levers

Scenario. DNS timeouts and Service latency grow with the size of the cluster.

What the picture shows. SR-IOV (one NIC split into virtual functions), eBPF for observability and policy, IPVS instead of iptables at scale, and CoreDNS with a proportional autoscaler plus a node-local DNS cache.

Standard vs. SR-IOV vs. RDMA

Scenario. GPUs sit idle waiting on the network during gradient synchronization.

What the picture shows. Standard virtualization goes through the hypervisor and a software switch. SR-IOV gives a direct hardware path, but the TCP/IP stack still costs CPU. RDMA copies memory to memory between nodes with near-zero CPU.

Going deeper. For GPU collectives, NCCL is the library doing the all-reduce and all-gather. Across nodes it should run over RDMA (InfiniBand or RoCE, with GPUDirect RDMA moving data straight between GPU memories). On Kubernetes that often means setting NCCL_SOCKET_IFNAME and making sure pods can find each other by name. In a synchronized job the slowest node sets everyone's pace, so one congested link shows up as a fleet-wide slowdown.

Training stresses this path even more than inference. With sharded data parallelism (PyTorch FSDP2), every layer's forward and backward pass gathers weight shards from all GPUs, which adds up to many GB per second of steady traffic. A fine-tuning job that fits in a few GPUs can still end up network-bound if those GPUs sit on different nodes.

Latency and EFA

Scenario. Scaling a training job from 2 to 16 nodes makes each step slower.

What the picture shows. Cluster placement groups for latency, and EFA (RDMA with NCCL support) for throughput. On EKS, the aws-efa-k8s-device-plugin advertises EFA interfaces as a schedulable resource, so pods can request them like GPUs.

Going deeper. Disaggregated LLM serving pushes this further. When prefill and decode run on separate pods and pass the KV cache between them, the pods need on the order of hundreds of Gbps between them, far beyond a normal 10–20 Gbps pod network. That's why setups like llm-d or NVIDIA Dynamo assume RDMA, RoCE or NVLink fabrics, and behave more like an appliance than a typical Deployment.

Troubleshooting networking

  1. IP exhaustion
  2. Service connectivity drops
  3. DNS issues
  4. Latency by distance
  5. Bandwidth and MTU

Three tickets arrive in one morning: "pods stuck Pending", "service unreachable" and "everything is slow when calling external APIs". This tab is the runbook for all three.

IP exhaustion

Scenario. New pods stay Pending or ContainerCreating with "failed to assign an IP address".

What the picture shows. Start with the aws-node logs. Then pick a fix: a bigger subnet (the hard way), prefix delegation (17 → 110 pods on a t3.medium), or custom networking on a secondary CIDR such as 100.64.0.0/16 through ENIConfig.

Service connectivity drops

Scenario. One service can't reach another by its Service IP.

What the picture shows. Step A: does the Service have endpoints? An empty list usually means a selector typo. Step B: are the iptables or IPVS rules there? Also check readiness probes, NetworkPolicies, and whether kube-proxy is healthy.

DNS issues

Scenario. Calls to external APIs are slow, and CoreDNS CPU usage is high.

What the picture shows. Corefile mistakes and forward loops, CoreDNS running out of memory, Services with no endpoints, and ndots:5: one external lookup becomes several queries through the search domains. Fix it with fully qualified names (a trailing dot) or a lower ndots in dnsConfig.

Latency by distance

Scenario. Why does the same call take 0.1 ms, 1 ms or 5 ms?

What the picture shows. Same node: memory copy only. Same AZ: the top-of-rack switch (0.2–1 ms). Across AZs: the inter-AZ backbone (1–5 ms), plus a data transfer charge.

Bandwidth and MTU

Scenario. Three pods on one node want 12 Gbps together through a 10 Gbps ENI.

What the picture shows. Instance bandwidth caps all pods on a node together ("up to" vs. guaranteed). The VPC supports 9001-byte jumbo frames, but the internet uses 1500, so raising pod MTU helps east-west traffic and breaks internet traffic that has no translation.

Tab 12 · 3 sections

Cost optimization on EKS

  1. Compute
  2. Networking
  3. Storage

Finance asks why the EKS bill grows faster than traffic. This tab is my checklist, split into compute, network and storage.

Compute

Scenario. Half the nodes average 20% CPU, and the GPU bill keeps growing.

What the picture shows. Right-size with Kubecost, Goldilocks, StormForge or KRR. Choose purchase options deliberately: on-demand, Reserved Instances, Savings Plans, Spot (2-minute notice, good for checkpointed training with Ray, Kubeflow or Horovod, with Karpenter falling back to on-demand), Graviton, Fargate, and Capacity Blocks to reserve GPUs for a planned window.

Going deeper. For GPU nodes, the biggest waste is idle GPUs, not instance pricing:

  • Bin-pack (MostAllocated with GPUs weighted highest), so empty nodes can be removed.
  • Share GPUs that small models use only partly: MIG for isolation, time slicing for dev and bursty inference.
  • Quantize where quality allows: a 70B model needs about 280 GB at fp32 but about 35 GB at 4-bit.

Weigh every consolidation against the checkpoint-and-restart it forces on training jobs.

Networking

Scenario. The data-transfer line on the bill is surprisingly large.

What the picture shows. Cross-AZ pod traffic costs money, so use topology-aware routing (EndpointSlice hints) and same-AZ provisioning with Karpenter. Use ALB IP mode, VPC endpoints instead of NAT for AWS services, and an ECR endpoint plus pre-cached images in a custom AMI.

Going deeper. Model images are a special case: tens or hundreds of GB. Layered OCI images let ten fine-tuned variants share one cached copy of the base model on a node. Pre-pulling or prefetching images is what keeps scale-up times predictable (see Getting model weights into pods).

Startup time is a cost too: a slow-starting replica means paying for extra warm capacity. For model servers:

  • Use imagePullPolicy: IfNotPresent, and pin images by version or digest instead of latest.
  • Avoid downloading weights at startup (PVCs or OCI images instead).
  • Use a parallel loader (Run:ai Model Streamer, Tensorizer).

Together these cut a replica's time-to-ready from minutes to tens of seconds.

Storage

Scenario. Old volumes and logs keep growing after the workloads that wrote them are gone.

What the picture shows. Ephemeral storage for scratch data, Mountpoint for S3 (a file system view of S3, not a block device), gp3 over gp2 (about 20% cheaper), reclaim policies, IOPS tiers (io2 for the hottest data, st1/sc1 for cold), smaller images through multi-stage builds, and log retention policies.

Going deeper. For model weights, the storage choice is a cost-vs-speed trade-off. A shared ReadOnlyMany PersistentVolume stores one copy for all replicas but pays network latency on every read. Copying into an emptyDir gives fast local reads but stores one copy per pod per node. OCI images sit in between (see Getting model weights into pods).

EKS security from build to runtime

  1. What we protect
  2. The build pipeline
  3. Runtime security
  4. Network security
  5. Secret management
  6. Identity and model endpoints

Security asks for one picture of how a model-serving platform is protected before launch. This tab answers it layer by layer.

What we protect

Scenario. Kickoff with the security team: what is in scope?

What the picture shows. The stack from host to containers, dependencies, code, configuration and data, and the two places container risk enters: the build pipeline and the runtime environment.

The build pipeline

Scenario. A base image with a critical CVE almost reaches production.

What the picture shows. Build (minimal or distroless base images, multi-stage builds, immutable tags) → test (Snyk in CI) → store (signing with Cosign or AWS Signer, OPA Gatekeeper) → encrypt (KMS, Vault, Secrets Store CSI) → scan (Inspector, Trivy) → deploy (private subnets, no SSH, IMDS blocked, hardened AMI) → monitor.

Going deeper. Model files belong in the supply chain too. Classic PyTorch .pt files use Python pickle, which can execute arbitrary code when loaded. Safetensors stores only tensors and can't, which makes it the safer default for weights from outside the organization. Signing and scanning model images works the same way as for application images.

Runtime security

Scenario. A container is found running as root with CAP_SYS_ADMIN.

What the picture shows. Least privilege, no root or privileged containers, dropped capabilities in the security context, Pod Security Standards enforced through namespace labels, and runtime detection deployed as a DaemonSet.

Network security

Scenario. A compromised pod tries to scan the rest of the cluster.

What the picture shows. Namespaces plus NetworkPolicies, zero-trust pod-to-pod traffic with a service mesh, WAF and OIDC at ingress and egress, secure DNS, and traffic visibility through Cilium, Calico or Datadog.

Secret management

Scenario. Someone base64-decodes a Kubernetes Secret and asks, "is that all it takes?"

What the picture shows. Secrets are only base64-encoded. Encrypt etcd with KMS envelope encryption, restrict access with RBAC, consider external managers (Vault, AWS Secrets Manager), rotate secrets, and monitor through a SIEM.

Identity and model endpoints

Scenario. The inference service needs S3 access and a public HTTPS endpoint.

What the picture shows. IRSA vs. EKS Pod Identity (simpler setup through an agent DaemonSet), TLS everywhere with ACM certificates on the ALB or NLB, and WAF on the ingress.

Going deeper. Model endpoints also need guardrails: checks on the prompt before the model and on the answer after it. They catch prompt injection ("ignore all previous instructions"), jailbreaks, toxic output and leaked personal data. Small classifier models such as Llama Guard or Granite Guardian run as their own vLLM deployments. Frameworks like NeMo Guardrails, the FMS Guardrails Orchestrator, Guardrails AI or a moderation API wire them in. Every check adds latency and GPU cost, so keep the in-line checks small and sample the rest asynchronously.

Agents add an identity question: when an agent calls a tool (an MCP server) on a user's behalf, whose identity does the backend see? There are four common answers:

  • Pass the user's token through: full per-user audit, but long-running tasks outlive the token and the token needs very broad scopes.
  • Kubernetes ServiceAccounts: validated with TokenReview and authorized with SubjectAccessReview. Simple inside one cluster, but you lose the user.
  • OAuth2 token exchange (RFC 8693): one token carries both the user (sub) and the agent (act).
  • SPIFFE/SPIRE mTLS: short-lived workload certificates that can't be stolen like a token.

In practice teams layer them: workload mTLS plus user identity in the request, with a policy engine checking both. More in Running agents in production.

StorageClass, PV and PVC in one analogy

The furniture-shop analogy

Scenario. A new engineer asks why a pod needs a PVC, a PV and a StorageClass just to get a disk.

What the picture shows.

  • StorageClass: the catalogue of blueprints (gp3, io2, and so on).
  • PVC: the order slip ("I need a wooden desk").
  • PV: the desk that actually gets built, which is the real EBS volume, bound to the order.
  • Volume and volumeMount: where the pod sets the desk up.

The YAML examples show dynamic provisioning end to end. Mountpoint for S3 gives you a file-system view of a bucket; it is still object storage.

Going deeper. The same objects serve model weights. One PersistentVolume on NFS or EFS with ReadOnlyMany access, mounted readOnly: true by every replica, stores the model once and lets the OS cache it aggressively. It works well for tens of replicas. At hundreds, the shared backend becomes the bottleneck.
